# 11: 첫 실행과 읽기 실패 복구

**What to build:** 입사일이 없는 사용자는 필요한 설정만 완료하고, 저장 파일을 읽을 수 없는
사용자는 정상 탭과 분리된 화면에서 원본을 보존하며 복구할 수 있는 두 경계 상태.

**Blocked by:** 10/원장형 데이터 관리와 파괴적 확인.

**Status:** resolved

- [x] 입사일이 없으면 설정할 내용과 이유만 보이고 요약·이력은 사용할 수 없다.
- [x] 첫 설정을 저장하면 설정 맥락을 유지하면서 정상 탭과 계산 결과가 활성화된다.
- [x] 온보딩의 입력, 포커스와 오류 설명이 원장형 설정 계약을 따른다.
- [x] 읽기 실패 상태에서는 정상 헤더와 탭을 표시하지 않아 사용할 수 없는 기능을 약속하지 않는다.
- [x] 읽기 실패 종류가 사용자가 이해할 수 있는 문구로 구분된다.
- [x] 백업 복구와 저장 파일 위치 열기 행동이 원본을 덮어쓰지 않는 기존 계약을 유지한다.
- [x] 복구 성공 후 정상 상태가 다시 계산되고, 실패하면 복구 화면과 원본이 유지된다.
- [x] 키보드와 보조 기술만으로 온보딩과 복구의 주요 행동을 완료할 수 있다.
- [x] Electron 제품 흐름이 입사일 없는 데이터와 각 읽기 실패 fixture를 실제 앱에서 검증한다.

## Answer

- 입사일이 없는 동안 `SettingsTab`은 기본 설정만 보여주고 조정·데이터 영역을 숨긴다. 요약·이력은 비활성화하며, 입사일 입력에 자동 포커스를 두고 빈 값 저장 불가 상태와 이유를 역할·문구로 전달한다. 첫 저장 뒤에는 설정 탭을 유지하면서 계산 결과, 요약·이력 탭과 조정·데이터 영역을 다시 활성화한다.
- `UnreadableScreen`은 정상 헤더·탭을 대신하는 접근 가능한 `main` 화면으로 JSON 파싱 실패, 저장 구조 불일치와 미래 버전을 구분해 안내한다. 미래 버전은 업데이트 안내만 제공하고, 나머지는 백업 복구·파일 위치 열기를 제공하며 진행·성공·실패 상태와 포커스 복귀를 유지한다.
- 사용자가 행동을 고르기 전과 복구 검증이 실패한 뒤에는 `data.json` 원문을 보존한다. 유효한 백업을 명시적으로 선택한 성공 경로는 기존 원자적 `restoreBackupFile` 계약을 사용해 상태를 다시 읽고 계산하며, 파일 위치 열기는 기존 reveal 계약을 그대로 사용한다.
- `apps/desktop/DESIGN.md`에 온보딩 상태 전이와 읽기 실패 화면의 구조·오류 문구·복구·포커스 계약을 기록했다. 실제 Electron 제품 흐름은 격리된 임시 사용자 데이터와 결정론적 fixture로 온보딩, 세 읽기 실패 종류, 파일 위치 열기, 유효·무효 백업 복구를 검증한다.
- 검증은 `pnpm exec turbo run lint typecheck test --force --concurrency=1`의 6/6 작업 성공(코어 123개·데스크톱 18개 테스트), `pnpm test:product`의 비활성 실제 Electron 제품 흐름 32/32 통과, 새 6개 시나리오의 전면 제품 흐름 6/6 통과로 마쳤다. 전체 `pnpm test:product:foreground`에서는 기존 데이터·등록 흐름 4개가 전면 창의 OS 포커스·blur 타이밍에서 실패했으며, 이 티켓의 새 시나리오는 통과했다. 제품 흐름은 macOS에서 실행한 증거이며, 파일 관리자 호출은 테스트 대역이고 Windows 실제 팝오버·포커스·트레이 검증을 대신하지 않는다.
