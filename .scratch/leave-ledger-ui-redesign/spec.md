# 잔액 원장 UI 재설계

Status: ready-for-agent

제품 이름은 연차몇개다. 이 명세는 현재 기능과 데이터 계약을 유지하면서 macOS 메뉴 막대 및
Windows 시스템 트레이 팝오버의 사용자 화면과 사용 경험을 전면 재설계한다.

시각 방향은 사용자가 승인한 잔액 원장이다. 잔여와 그 근거를 은행 통장·가계부·사내 정산
원장처럼 한눈에 대조할 수 있어야 하며, 승인된 컴프를 구현의 시각 기준으로 삼는다.

용어는 저장소의 CONTEXT.md를 유일한 출처로 삼는다. 특히 화면에서는 남은 연차나 가용 연차 대신
잔여, 사용 내역 대신 휴가 이력, 휴가 신청 대신 휴가 기록을 사용한다.

## Problem Statement

사용자는 연차몇개를 열었을 때 현재 잔여를 즉시 확인하고, 방금 쓴 휴가나 앞으로 쓸 휴가를
최소한의 조작으로 기록하고 싶다. 현재 제품은 정확한 계산과 필요한 기능을 갖추고 있지만,
팝오버의 정보 위계와 등록 동선이 이 두 가지 핵심 행동을 가장 먼저 드러내지 못한다.

- 잔여는 트레이에 상시 표시되지만 팝오버를 열었을 때 잔여와 그 계산 근거, 휴가 등록 행동의
  관계가 한 덩어리로 읽히지 않는다.
- 휴가 등록은 요약 본문의 아래쪽 행동에서 시작하고 날짜 선택과 상세 입력이 별도 단계로
  갈라져 있어, 가장 흔한 오늘·종일 기록에도 세 번의 조작이 필요하다.
- 휴가 이력의 수정·삭제 기능은 존재하지만 화면 밀도가 높고 조작이 hover에 의존해 발견하기
  어렵다.
- 요약·이력·설정의 기능은 각각 완성되어 있으나 하나의 제품다운 시각 문법보다 기능별 행과
  컨트롤의 모음처럼 보인다.
- 현재 디자인 계약의 System Blue 중심 평면 도구 방향은 사용자가 승인한 잔액 원장 방향과
  충돌한다.

기능을 더 추가하는 것이 문제가 아니다. 정확성을 지키는 기존 기능을 유지하면서 잔여 확인과
휴가 기록의 깊이를 줄이고, 모든 화면을 하나의 신뢰 가능한 원장으로 다시 조직해야 한다.

## Solution

380px 팝오버 전체를 잔액 원장이라는 하나의 시각·상호작용 체계로 재설계한다.

첫 화면의 최상단에는 잔여와 휴가 등록을 함께 둔다. 사용자가 팝오버를 열면 스크롤 없이 잔여를
읽고 곧바로 기록을 시작할 수 있어야 한다. 발생·사용·예정·초과·잔여는 고정된 열과 얇은
구분선으로 연결해 숫자가 만들어진 근거를 위에서 아래로 검산하게 한다.

휴가 등록은 한 화면에서 이루어진다. 시작 시 오늘과 종일을 기본값으로 채워 오늘 종일 휴가는
휴가 등록과 등록의 두 번 조작으로 저장한다. 날짜, 기간, 반차, 반반차, 메모, 주말 제외는 같은
등록면에서 필요할 때만 조정한다. 휴가 이력의 수정·삭제도 현재 맥락 안에서 처리해 다른 화면으로
이동하지 않는다.

요약·이력·설정 탭, 발생분과 소멸 정보, 리스트·달력 이력, 조정, 데이터 내보내기·가져오기,
온보딩, 읽기 실패 복구 등 현재 제공하는 기능은 모두 유지한다. 계산 엔진, 저장 형식, 프로세스
간 통신 계약과 날짜 규칙은 바꾸지 않는다.

## User Stories

1. 사용자로서 트레이의 숫자만 보고 현재 잔여를 알고 싶다. 그래야 앱을 열지 않아도 된다.
2. 사용자로서 팝오버를 열자마자 잔여를 가장 먼저 보고 싶다. 그래야 화면을 탐색하지 않아도 된다.
3. 사용자로서 잔여가 소수 단위까지 그대로 보이기를 원한다. 그래야 반차와 반반차가 정확히 반영됐는지 알 수 있다.
4. 사용자로서 잔여와 휴가 등록 행동을 같은 첫 화면에서 보고 싶다. 그래야 다음 행동을 찾지 않아도 된다.
5. 사용자로서 잔여와 휴가 등록 행동이 스크롤 전에 보이기를 원한다. 그래야 기록을 시작하려고 본문 끝까지 내려가지 않아도 된다.
6. 사용자로서 발생·사용·예정·초과·잔여를 같은 열 구조로 보고 싶다. 그래야 잔여의 계산 근거를 빠르게 대조할 수 있다.
7. 사용자로서 각 숫자의 의미를 짧은 설명과 함께 보고 싶다. 그래야 비슷한 숫자를 혼동하지 않는다.
8. 사용자로서 초과가 있을 때 원인과 조정 경로를 숫자 가까이에서 보고 싶다. 그래야 음수를 오류로 오해하지 않는다.
9. 사용자로서 예정이 아직 생기지 않은 발생분에서 나가는 경우를 알고 싶다. 그래야 현재 잔여가 줄지 않은 이유를 이해한다.
10. 사용자로서 살아 있는 발생분을 소멸이 가까운 순서로 보고 싶다. 그래야 먼저 써야 할 연차를 판단한다.
11. 사용자로서 각 발생분의 출처, 남은 양, 총량과 소멸일을 한 행에서 보고 싶다. 그래야 기록의 근거를 검산한다.
12. 사용자로서 소멸이 임박한 발생분을 색 외의 문구와 기호로도 알아보고 싶다. 그래야 색을 구별하기 어려워도 상태를 이해한다.
13. 사용자로서 오늘 종일 휴가를 두 번의 조작으로 기록하고 싶다. 그래야 입력 비용 때문에 기록을 미루지 않는다.
14. 사용자로서 휴가 등록을 열면 오늘 날짜가 기본으로 선택되어 있기를 원한다. 그래야 가장 흔한 기록에 날짜 선택이 필요 없다.
15. 사용자로서 휴가 등록을 열면 종일이 기본으로 선택되어 있기를 원한다. 그래야 가장 흔한 단위를 다시 고르지 않는다.
16. 사용자로서 기본값을 저장하기 전에 오늘과 종일이 선택됐음을 분명히 보고 싶다. 그래야 의도하지 않은 기록을 만들지 않는다.
17. 사용자로서 다른 날짜를 같은 등록면에서 고르고 싶다. 그래야 화면을 오가거나 흐름을 다시 시작하지 않는다.
18. 사용자로서 기간의 시작일과 종료일을 같은 등록면에서 지정하고 싶다. 그래야 여러 날을 반복 입력하지 않는다.
19. 사용자로서 기간 등록 시 주말이 기본으로 제외되기를 원한다. 그래야 실제로 쉬지 않은 날이 차감되지 않는다.
20. 사용자로서 기간에서 실제로 생성될 휴가 기록의 수를 저장 전에 보고 싶다. 그래야 주말과 기존 기록이 빠진 결과를 확인한다.
21. 사용자로서 종일·반차·반반차를 한 자리에서 바꾸고 싶다. 그래야 실제 사용량을 정확히 기록한다.
22. 사용자로서 휴가 기록에 선택적으로 메모를 남기고 싶다. 그래야 오전·오후 반차 같은 맥락을 기억한다.
23. 사용자로서 이미 휴가 기록이 있는 날짜를 등록할 수 없음을 바로 알고 싶다. 그래야 저장 후 오류를 뒤늦게 보지 않는다.
24. 사용자로서 저장 중에는 중복 조작이 막히고 진행 상태가 보이기를 원한다. 그래야 같은 기록을 두 번 만들지 않는다.
25. 사용자로서 저장에 실패하면 입력한 값이 유지된 채 원인을 보고 싶다. 그래야 처음부터 다시 입력하지 않는다.
26. 사용자로서 등록이 끝나면 팝오버의 잔여와 휴가 이력이 즉시 갱신되기를 원한다. 그래야 저장됐음을 확인한다.
27. 사용자로서 휴가 이력에서 예정과 사용을 쉽게 구분하고 싶다. 그래야 앞으로 쓸 것과 이미 쓴 것을 섞어 보지 않는다.
28. 사용자로서 휴가 이력을 리스트와 달력 중 원하는 방식으로 보고 싶다. 그래야 날짜와 기록량을 상황에 맞게 파악한다.
29. 사용자로서 예정이 리스트 위에 따로 모이기를 원한다. 그래야 취소하거나 바꿀 기록을 빨리 찾는다.
30. 사용자로서 사용 기록이 연차 연도별로 접혀 있기를 원한다. 그래야 오래 쓴 기록에서도 스크롤이 과도하게 길어지지 않는다.
31. 사용자로서 현재 연차 연도만 처음 펼쳐지기를 원한다. 그래야 가장 관련 있는 이력부터 본다.
32. 사용자로서 이력 행에서 수정과 삭제 행동을 발견할 수 있기를 원한다. 그래야 hover 방법을 추측하지 않아도 된다.
33. 사용자로서 휴가 기록을 현재 행 안에서 수정하고 싶다. 그래야 목록의 위치와 맥락을 잃지 않는다.
34. 사용자로서 날짜와 단위를 수정한 뒤 잔여가 즉시 다시 계산되기를 원한다. 그래야 변경 결과를 바로 확인한다.
35. 사용자로서 예정 휴가를 현재 맥락에서 삭제하고 싶다. 그래야 별도 상태 변경 없이 안 쓰게 된 기록을 제거한다.
36. 사용자로서 달력의 날짜를 선택해 그날 기록을 수정하거나 삭제하고 싶다. 그래야 날짜 중심으로도 같은 작업을 한다.
37. 사용자로서 사용과 예정이 날짜에서 자동으로 정해지기를 원한다. 그래야 오래된 수동 상태 때문에 잔여가 틀리지 않는다.
38. 사용자로서 소멸된 발생분은 이력의 아래쪽에서 필요할 때만 보고 싶다. 그래야 현재 사용할 수 있는 연차에 집중한다.
39. 사용자로서 요약·이력·설정 탭의 위치와 모양이 일관되기를 원한다. 그래야 어느 화면에서도 길을 잃지 않는다.
40. 사용자로서 입사일이 없으면 설정해야 할 항목만 보고 싶다. 그래야 계산할 수 없는 요약을 보지 않는다.
41. 사용자로서 입사일과 기준방식을 기존과 같은 규칙으로 설정하고 싶다. 그래야 현재 계산 결과가 유지된다.
42. 사용자로서 조정을 추가·수정·삭제하고 싶다. 그래야 이월·사규 추가분·포상 휴가를 법정 발생과 분리해 기록한다.
43. 사용자로서 입사일 변경이 기존 기록에 미치는 영향을 저장 전에 알고 싶다. 그래야 데이터를 실수로 잃지 않는다.
44. 사용자로서 저장 파일 위치 열기, 내보내기와 가져오기를 계속 사용할 수 있기를 원한다. 그래야 로컬 데이터를 직접 관리한다.
45. 사용자로서 읽을 수 없는 저장 파일이 있을 때 원본을 덮어쓰지 않는 복구 화면을 보고 싶다. 그래야 손상된 데이터를 보존한다.
46. 사용자로서 모든 주요 조작을 키보드로 실행하고 현재 포커스를 볼 수 있기를 원한다. 그래야 마우스 없이도 사용할 수 있다.
47. 사용자로서 버튼·탭·입력의 이름과 상태를 보조 기술이 이해하기를 원한다. 그래야 화면 낭독기로도 같은 기능을 쓴다.
48. 사용자로서 상태가 색상에만 의존하지 않기를 원한다. 그래야 라이트·다크 테마와 색각 조건에 관계없이 의미를 읽는다.
49. 사용자로서 숫자와 날짜 열이 상태 변화 후에도 흔들리지 않기를 원한다. 그래야 잔여와 기록을 빠르게 대조한다.
50. 사용자로서 macOS와 Windows에서 같은 정보 위계와 조작 순서를 경험하고 싶다. 그래야 운영체제를 바꿔도 다시 배우지 않는다.
51. 사용자로서 팝오버가 화면 작업 영역을 넘지 않고 필요한 부분만 스크롤되기를 원한다. 그래야 작은 화면에서도 핵심 행동을 잃지 않는다.
52. 사용자로서 장식보다 정보가 먼저 보이는 차분한 원장형 화면을 원한다. 그래야 중요한 숫자와 날짜에 집중한다.

## Implementation Decisions

- 승인된 시각 방향은 잔액 원장이다. 은행 통장·가계부·사내 정산 원장의 정렬과 검산 가능성을
  차용하되, 금융 앱의 브랜드나 사실적인 종이 질감을 복제하지 않는다.
- 구현은 컴프 우선 방식으로 진행한다. 승인된 컴프는 구성 기준이며 처음부터 다시 생성하지
  않는다. 구현 전 변형안을 만들더라도 승인된 컴프와 함께 비교하고 최종 화면은 승인된 정보
  위계와 조작 위치를 보존한다.
- 현재 디자인 계약의 System Blue 중심 시각 토큰은 이번 재설계의 시각 범위에서 대체한다.
  구현 작업은 디자인 권위 문서를 잔액 원장 방향으로 갱신해 코드와 문서가 서로 다른 세계를
  지시하지 않게 해야 한다.
- 팝오버는 기존과 같이 고정 폭 380px이며 내용에 따라 높이가 바뀐다. 핵심 잔여와 휴가 등록
  행동은 첫 화면에서 스크롤 없이 보인다. 화면 작업 영역보다 길어지는 목록만 내부 스크롤한다.
- 정상적으로 읽힌 요약·이력·설정 탭의 `휴가 등록`은 헤더에 있는 전역 행동 하나다. 본문에 같은
  CTA를 반복하지 않으며 `Cmd/Ctrl+Shift+N`과 헤더의 플랫폼별 단축키 안내로 어디서든 시작한다.
  온보딩·로딩·읽기 실패 화면에는 이 행동을 노출하지 않는다.
- 정보 구조는 요약·이력·설정 세 탭을 유지한다. 별도 주 창이나 추가 내비게이션 계층을 만들지
  않는다.
- 최상단 원장 머리는 제품명, 잔여, 주요 휴가 등록 행동과 설정 진입 단서를 포함한다. 잔여가
  가장 강한 숫자이고 등록 행동이 같은 시야에 있어야 한다.
- 요약은 발생·사용·예정·조건부 초과·잔여를 같은 고정 열에 배치한다. 살아 있는 발생분과
  소멸 정보도 같은 날짜·수량 열 규칙을 사용한다.
- 요약의 잔여 직전에는 `발생 − 사용 − 예정 = 잔여`를 보이고, 초과가 있으면
  `발생 − 사용 − 예정 − 초과 = 잔여`를 보인다. 발생분 표에는 `출처`, `남은 양/총량`,
  `소멸일 또는 소멸까지` 헤더와 정확한 소멸일·D-day를 시각 및 접근성 텍스트로 함께 둔다.
- 숫자는 tabular numerals를 사용하고 수량과 날짜 열 폭을 고정한다. 값, 태그 또는 hover
  행동이 바뀌어도 행의 주요 열이 움직이지 않아야 한다.
- 기본 표면은 따뜻한 중립색, 본문은 짙은 잉크색, 주요 실행과 선택은 절제된 원장 녹색을
  사용한다. 경고와 소멸은 별도의 위험 역할색을 사용한다. 라이트·다크 테마는 동일한 역할
  구조를 유지한다.
- 얇은 기준선과 행 구분이 정보 그룹을 만든다. 과도한 카드, 그림자, 블러, 그라디언트,
  장식용 일러스트와 사실적인 통장 장식은 사용하지 않는다.
- 휴가 등록은 팝오버의 현재 구조를 대신하는 하나의 등록면으로 열린다. 기본값은 오늘·종일이다.
  사용자는 휴가 등록과 등록의 두 번 조작으로 오늘 종일 기록을 저장할 수 있다.
- 등록면은 날짜와 단위를 항상 보여주고, 다른 날짜·기간·메모·주말 제외를 같은 화면에서
  조정한다. 기간 선택 때문에 새로운 페이지나 중첩 모달을 추가하지 않는다.
- 기간 등록은 기존처럼 날짜별 휴가 기록 여러 건으로 펼친다. 기간 레코드를 새로 만들지 않으며
  주말 제외 기본값, 기존 기록 건너뛰기와 하루 한 건 불변식을 유지한다.
- 등록·수정·삭제는 기존 커밋 통로를 사용한다. 성공 후 셸이 다시 계산한 상태를 받아 잔여,
  휴가 이력과 트레이 표시가 함께 갱신된다.
- 등록 성공은 커밋과 상태 push가 끝나는 즉시 등록면을 닫고, 부모 정상 셸의 `role="status"`에
  완료 문구를 남긴다. 성공·취소·Escape 뒤 포커스는 전역 `휴가 등록` 트리거로 돌아가며, 실패는
  등록면과 사용자의 입력을 유지한다.
- 휴가 이력은 리스트·달력 두 보기를 유지한다. 예정, 연차 연도별 사용, 소멸된 발생분의
  구분과 정렬 규칙을 바꾸지 않는다.
- 리스트의 수정·삭제 행동은 포인터 상태와 무관하게 행 안에 항상 보이고, 자리를 확보해 열 폭을
  유지한다. 삭제는 대상 바로 아래에 삭제할까요?와 삭제·취소를 인라인으로 표시하며, 수정은
  현재 행 안에서 완료한다.
- 달력은 기존 날짜 계산과 장식을 재사용한다. 날짜를 고르면 현재 맥락 안에서 단위 변경과
  삭제를 수행한다. 단위 변경은 먼저 저장 전 초안으로 두고 `저장`을 눌렀을 때만 커밋하며,
  `취소`는 데이터와 잔여를 바꾸지 않는다. 저장·취소 뒤에는 같은 단위 편집 위치로 포커스를
  돌리고, 저장 실패 시 선택 날짜·초안·오류를 유지한다.
- 온보딩에서는 입사일과 기준방식을 설정하는 데 필요한 화면만 보여준다. 입사일이 생기기
  전까지 계산할 수 없는 요약과 이력은 활성화하지 않는다.
- 저장 파일 읽기 실패 화면은 정상 탭 셸과 분리한다. 복구, 파일 위치 열기와 오류 설명을
  원장형 시각 언어로 다시 표현하되 원본 보존 동작은 바꾸지 않는다.
- 조정, 데이터 내보내기·가져오기와 입사일 변경 확인은 기존 기능과 파괴적 조작 확인 규칙을
  유지한다. 일반 기록·조정 삭제도 확인 전에는 커밋하지 않고, 실패 시 대상과 오류 맥락을 남긴다.
- 키보드 포커스는 항상 보이고 탭, 선택 상태, 펼침 상태, 유효성 오류와 저장 중 상태는 의미에
  맞는 접근성 속성을 제공한다. 색은 상태의 유일한 신호가 될 수 없다.
- 용어 도움말은 인접한 용어 맥락을 구분하고 질문 버튼의 실제 hit target을 최소 24×24px로
  보장한다. 저장 행동은 primary, 취소는 neutral/mini, 삭제 확인은 danger로 역할을 분리한다.
- 파괴적 데이터 확인은 백업 사실을 자연어로 먼저 알리고 정확한 보조 파일명 `data.json.bak`을
  함께 제공한다. 기존 교체·복구 의미와 원본 보존 조건은 바꾸지 않는다.
- Electron 셸, 순수 TypeScript 계산 엔진, 로컬 JSON 저장, Asia/Seoul 기준 오늘,
  Temporal.PlainDate 날짜 처리와 프로세스 간 통신 계약을 유지한다.
- 저장 스키마, 도메인 타입, 계산 API와 마이그레이션은 변경하지 않는다. 이번 작업은 기존
  제품 상태를 읽고 쓰는 사용자 화면과 상호작용만 변경한다.

## Testing Decisions

- 테스트 명령의 무창·비활성·전면 실행 구분과 CI·릴리스·pre-push 정책은
  [데스크톱 테스트 실행선 분리](../desktop-test-execution/spec.md)를 권위 문서로 따른다. 이 절은
  잔액 원장 UI가 검증해야 할 제품 시나리오와 증거 경계만 정의한다.
- 이 기능의 새 테스트 경계는 하나다. 격리된 사용자 데이터와 결정론적 시드 JSON으로 실제
  Electron 앱을 실행하는 Playwright 제품 흐름에서 팝오버의 외부 동작을 검증한다.
- 테스트는 구현 세부, 컴포넌트 이름, CSS 클래스와 내부 상태를 관찰하지 않는다. 사용자가
  볼 수 있는 문구·역할·선택 상태·활성 상태·저장 결과·팝오버 내 위치와 스크롤 여부만
  검증한다.
- 첫 화면 검증은 잔여와 휴가 등록이 팝오버의 최초 뷰포트 안에 있고, 핵심 숫자를 읽기 위해
  스크롤하거나 탭을 바꿀 필요가 없음을 실제 기하 정보로 확인한다.
- 빠른 등록 검증은 휴가 등록과 등록의 두 조작으로 오늘 종일 휴가 기록이 저장되고, 잔여,
  요약과 이력이 함께 갱신되는 전체 흐름을 확인한다.
- 확장 등록 검증은 다른 날짜, 기간, 반차, 반반차, 메모, 주말 제외와 기존 기록 건너뛰기가
  기존 저장 계약을 유지하는지 확인한다.
- 변경 검증은 휴가 이력의 리스트에서 기록을 수정·삭제하고 잔여와 이력이 즉시 다시 계산되는
  전체 흐름을 확인한다. 달력에서도 선택한 날짜의 단위 변경과 삭제가 같은 결과를 내야 한다.
- 기능 보존 검증은 요약·이력·설정, 조정, 데이터 관리, 온보딩과 읽기 실패 복구 화면에
  계속 접근할 수 있고 기존 주요 조작을 완료할 수 있음을 확인한다.
- 접근성 검증은 키보드만으로 주요 흐름을 완료하고, 포커스 표시, 탭 선택, 세그먼트 선택,
  펼침 상태, 오류와 저장 중 상태를 역할과 속성으로 확인한다.
- 승인된 컴프와의 일치는 같은 제품 흐름에서 잔여 첫 화면, 등록면과 이력 수정 상태의
  결정론적 스크린샷을 수집해 검토한다. 운영체제 글꼴 차이 때문에 픽셀 일치만을 자동 통과
  조건으로 삼지 않고 정보 위계, 정렬, 주요 행동 위치와 시각 토큰을 검토한다.
- 기존 계산 엔진 단위 테스트와 기간 날짜 전개 단위 테스트는 회귀 안전망으로 그대로 유지한다.
  UI 재설계를 위해 같은 도메인 규칙을 새로운 단위 테스트 층에 중복 구현하지 않는다.
- 기존 선례는 실제 Electron을 격리된 사용자 데이터로 실행해 예정·소멸·달력·수정 흐름을
  확인한 이력 화면 검증과, 렌더러의 기간 날짜 전개를 순수 함수로 검증한 등록 흐름 테스트다.
- macOS에서 실행한 제품 흐름은 Windows 실제 팝오버의 렌더링·포커스·트레이 동작 증거가 아니다.
  동일한 시나리오를 Windows에서 별도로 실행하거나 수동 수용 검증하고 결과를 구분해 기록한다.
- 구현 완료 판단에는 마지막 UI 변경 이후의 정적 검사, 전체 자동 테스트와 실제 Electron
  제품 흐름이 모두 필요하다. 컴프 검토, macOS 검증과 Windows 검증의 경계를 각각 명시한다.
  자동 Electron/Chromium 검증은 화면·DOM·포커스 흐름의 증거이며, macOS VoiceOver·메뉴 막대
  실물·200% 확대와 Windows 실물 동작의 증거로 과장하지 않는다. 가능한 네이티브 검증은 별도로
  기록하고, 불가능한 경계는 미검증으로 남긴다.

## Out of Scope

- 발생, 배정, 초과, 잔여, 소멸과 연차 연도 계산 규칙의 변경
- 저장 형식, 스키마 버전, 데이터 마이그레이션 또는 로컬 파일 위치 변경
- 서버 백엔드, 계정, 로그인, 팀 공유, 클라우드 동기화 또는 다중 사용자
- 회사 그룹웨어, 캘린더나 외부 휴가 시스템 연동
- 소멸 알림, 운영체제 알림 또는 새로운 자동화 기능
- 새로운 휴가 단위, 승인 상태, 신청 워크플로 또는 관리자 기능
- 모바일 화면, PWA 또는 반응형 모바일 브레이크포인트
- 트레이 숫자의 계산·표기 규칙, 우클릭 종료와 앱 수명 주기 변경
- 패키징, 코드 서명, 공증, 자동 업데이트와 배포 산출물 변경
- 승인된 잔액 원장 외의 새로운 시각 방향 탐색
- 실제 금융 앱처럼 보이는 브랜드, 장식적 통장 복제 또는 과도한 스큐어모피즘

## Further Notes

- 승인된 기준 이미지는 [잔액 원장 컴프](../../apps/desktop/.impeccable/mocks/decision/model-pick.png)다.
  구현 과정에서 이 이미지를 처음부터 다시 생성하지 않는다.
- 구현 작업에서 이 명세와 기존 디자인 문서의 충돌을 해소하고 디자인 권위 문서를 함께 갱신한다.
- 이 명세의 UI 개선 구현은 기존 계산·저장·IPC 계약을 유지한 채 완료 대상으로 삼는다.
  구현 완료 여부는 최신 정적 검사와 제품 흐름 결과로 판단하며, macOS 네이티브·VoiceOver·Windows
  실물 결과는 자동 검증과 별도의 증거로 기록한다.
- 2026-09-04에는 macOS 전면 제품 흐름과 Electron 페이지 200% 확대 회귀를 자동 검증했다. 현재
  Mac이 잠겨 있고 VoiceOver가 꺼진 상태라 실제 메뉴 막대 클릭·운영체제 포커스·VoiceOver 낭독은
  수행하지 못했으며, 이 경계는 별도 수용 확인이 필요하다.
- 이후 티켓 분할 시 디자인 토큰과 셸, 요약·빠른 등록, 이력·수정, 설정·복구, 제품 흐름
  검증의 경계를 따르되 하나의 최종 Electron 제품 흐름으로 합류하게 한다.
