# 08. 데이터 저장 형식 결정

Type: grilling
Status: resolved
Blocked by: 03

## Question

사용자 데이터를 어디에 어떤 형식으로 저장하는가? v2 PWA로 넘어갈 때 그대로 이식돼야 한다는 제약이 있다.

1. **형식**. 단일 JSON 파일인가 SQLite인가? 개인 도구의 데이터 규모(연 20건 남짓의 사용 이력)를 감안하면 SQLite는 과할 수 있다. 단 소멸·회기별 집계 쿼리가 늘어나면 얘기가 달라진다.
2. **위치**. OS별 앱 데이터 디렉터리인가, 사용자가 지정하는 경로인가? 사용자가 파일을 직접 열어보고 고칠 수 있어야 하는가?
3. **스키마 버저닝**. 버전 필드를 두고 마이그레이션을 어떻게 하는가? v1에서 이걸 안 해두면 v2에서 반드시 후회한다.
4. **내보내기·가져오기 포맷**. 범위 안으로 확정된 기능이다. 저장 형식과 같은 포맷인가 별도인가? PWA(브라우저)가 읽을 수 있어야 하므로 JSON이 유력하다.
5. **저장 시점과 손상 대비**. 매 변경마다 즉시 쓰는가? 쓰는 도중 앱이 죽으면?
6. **코어 패키지와의 관계**. 순수 TypeScript 코어는 파일 시스템을 모른다는 게 전제다. 저장은 셸의 책임이고 코어는 값만 받는 구조가 맞는가?

## 참고

- v2 PWA는 IndexedDB나 localStorage를 쓰게 된다. 그쪽으로 옮겨탈 수 있는 형태여야 한다.

## Comments

- **2026-08-25 — [04번 티켓](04-accrual-rule-spec.md)의 영향**: 저장 대상이 확정됐다. **발생 레코드(월차·연차)는 계산으로 만들어지므로 저장하지 않는다.** **배정 결과도 저장하지 않는다**(조회 시점에 매번 계산). 저장되는 것은 설정(`hireDate` / `grantBasis`), 휴가 기록(`date` / `days` / `note`), 그리고 **조정 레코드**다. 조정은 03번이 적은 것보다 필드가 늘어 `발생일 / 소멸일 / 일수(음수 가능) / 메모` 넷을 갖는다(04번 6절). 지도의 "이직 이력 지원" 안개가 이 티켓 뒤로 옮겨왔다 — `hireDate`를 갈아끼울 때 기존 기록을 어떻게 하는지가 포맷에 걸린다.

## Answer

저장 대상은 셋뿐이다 — **설정 / 휴가 기록 / 조정 레코드**. 발생과 배정은 계산 결과라 저장하지 않는다([04번](04-accrual-rule-spec.md) 0절). 이 절은 `to-spec`의 Implementation Decisions에 그대로 들어간다.

### 0. 형식 — 단일 JSON 파일

`data.json` 하나다. SQLite를 쓰지 않는다.

티켓이 단 조건("소멸·회기별 집계 쿼리가 늘어나면 얘기가 달라진다")은 **04번이 지웠다.** 잔여는 SQL로 표현되는 집계가 아니라, 전체 레코드를 소멸 임박 순으로 순회하며 배정하고 초과의 수명까지 계산하는 순수 함수다(04번 3·4·5절). 어차피 전량을 메모리에 올린다. SQLite를 깔아도 계산 경로는 `SELECT *` 세 번 뒤로 똑같다. 규모는 연 20건 × 20년 = 400행에 설정 2필드로, 전부 수십 KB다.

**기각한 대안: SQLite + Prisma.** 얻는 것은 트랜잭션과 테이블 마이그레이션 도구이고 그건 진짜 이점이다. 치르는 값이 셋인데 전부 이 지도의 확정 전제를 건드린다.

1. **Prisma는 브라우저에서 실행되지 않고 SQLite도 브라우저에 없다.** 7절에서 검증·마이그레이션을 코어에 두기로 했으므로, SQLite를 고르면 코어가 Node에 묶이고 v2 PWA가 검증 규칙을 다시 쓴다. 규칙이 두 벌이 되는 순간 v1이 쓴 파일을 v2가 다르게 읽는 경로가 열린다.
2. **[05번](05-shell-framework-adr.md)의 근거가 무너진다.** Electron을 고른 결정적 이유가 "네이티브 모듈 0개, 전부 TypeScript"였다. SQLite는 어느 경로로 가든(Prisma 쿼리 엔진 바이너리든 `better-sqlite3` 드라이버 어댑터든) OS별 네이티브 바이너리를 번들에 넣게 만들고, [10번](10-release-build-pipeline.md)이 그만큼 무거워진다.
3. **Q4의 답(내보내기 = 저장 포맷)과 양립하지 않는다.** PWA는 SQLite 파일을 못 읽으므로 내보내기가 반드시 별도 포맷이 되고, 파서가 두 벌로 갈라진다.

JSON을 고르면 잃는 것은 트랜잭션인데, 4절의 원자적 쓰기가 그 자리를 대신한다(20줄쯤이다).

**추후 서버로 갈 길을 막지 않는다.** 사용자 인증과 클라우드 DB가 붙는 시나리오에서도 레코드가 이미 `id`를 갖고(2절) 파일이 곧 전송 포맷이라 저장 형식을 갈아엎지 않는다. 서버 자체는 지도의 Out of scope다.

### 1. 위치

Electron `app.getPath('userData')` **고정**이다. macOS `~/Library/Application Support/<앱이름>/data.json`, Windows `%APPDATA%\<앱이름>\data.json`.

경로를 설정값으로 열지 않는다. 열면 "그 경로가 사라졌을 때"와 "동기화 폴더에 두고 두 대에서 동시에 연 경우"를 앱이 다뤄야 하는데, **클라우드 동기화는 Out of scope인데 경로 설정이 그것을 뒷문으로 끌고 들어온다.**

파일을 직접 열어 고치고 싶은 요구는 설정 탭의 `[파일 위치 열기]` 버튼과 2칸 들여쓰기 저장으로 채운다.

앱은 **단일 인스턴스 락**을 건다. 두 개가 같은 파일에 쓰는 경우를 만들지 않는다.

### 2. 파일 모양

```json
{
  "schemaVersion": 1,
  "settings": { "hireDate": "2024-01-01", "grantBasis": "hireDate" },
  "entries": [
    { "id": "…", "date": "2025-03-10", "days": 1, "note": "" }
  ],
  "adjustments": [
    { "id": "…", "grantDate": "2025-01-01", "expiryDate": "2025-12-31", "days": 5, "note": "이월" }
  ]
}
```

- **키 이름은 [`CONTEXT.md`](../../../CONTEXT.md)의 영문 용어 그대로다.** `hireDate` / `grantBasis` / `grantDate` / `expiryDate` / `days` / `note`. 새 도메인 용어가 하나도 생기지 않았으므로 **`CONTEXT.md`는 고칠 것이 없다.**
- **저장 파일에 발생은 없다.** 월차·연차는 계산 결과이므로 나가지 않는다. 배열 이름이 `grants`가 아니라 `adjustments`인 이유가 이것이다.
- **날짜는 `YYYY-MM-DD` 문자열.** 시각도 시간대도 없다. `Temporal.PlainDate`와 1:1이라 [09번](09-project-structure.md)이 어느 라이브러리를 고르든 그대로 간다.
- **일수는 숫자**다. 열거형이 아니다(03번 3절). 조정은 음수를 허용한다(04번 6절).
- **`id`는 `crypto.randomUUID()`.** Node와 브라우저 양쪽에 있어 v2에서 그대로 쓴다.
- **휴가 기록에도 `id`를 둔다.** 하루 1건이라 `date`가 자연키지만, 조정 레코드에는 자연키가 없다 — 발생일·소멸일·일수가 같은 포상 휴가 2건이 가능하고 그러면 UI가 하나만 지울 수 없다. 한쪽만 `id`를 두면 UI가 키 종류로 분기하므로 둘 다 둔다. **"하루 1건" 불변식은 파서가 중복 `date`를 거부하는 것으로 지킨다**(5절).
- **`note`는 항상 존재하고 기본값은 빈 문자열.** 선택 필드보다 검증이 단순하다.

### 3. 스키마 버저닝

최상위 `schemaVersion` 정수 + 순차 마이그레이션 함수 체인(1→2→3). **v1 시점에 체인은 비어 있다.**

v1이 실제로 얻는 것은 함수가 아니라 **미래 버전 거부**다. 이것이 유일하게 실재하는 데이터 손실 경로다 — 신버전 앱이나 v2 PWA가 필드를 늘려 쓴 파일을 구버전 앱이 열어, 모르는 필드를 조용히 날린 채 저장하는 상황. `schemaVersion`이 앱이 아는 값보다 높으면 **읽지도 쓰지도 않고** "앱을 업데이트하세요"를 띄운다.

낮은 버전은 마이그레이션 체인을 통과시켜 올린다. 가져온 파일도 같은 경로를 탄다(6절).

이 검사는 SQLite를 썼어도 손으로 만들어야 했다. DB는 모르는 컬럼이 있는 파일을 그냥 열어주고, 클라이언트는 자기가 아는 컬럼만 읽고 쓴다. 오류 없이 지나간다.

### 4. 쓰기와 백업

**변경마다 즉시 원자적으로 쓴다.** 임시 파일에 쓰고 → `fsync` → `rename`. 반쯤 쓰인 파일이 생기지 않는다.

디바운스하지 않는다. 수십 KB를 하루 몇 번 쓰는데 지연을 두면 "앱이 죽으면 마지막 몇 초를 잃는다"만 새로 만든다.

**백업(`data.json.bak`)은 파괴적 조작 직전에만 남긴다.** 둘뿐이다 — 8절의 입사일 변경에 따른 기록 삭제, 6절의 가져오기 교체. 이 앱에서 되돌릴 수 없는 대량 삭제가 그 둘이 전부다.

기각한 대안:

- **저장할 때마다 회전.** "직전 저장 상태"는 조작 하나만 되돌린다. 팝오버에 삭제 버튼이 있는데 되돌릴 값어치가 낮다.
- **앱 시작 시 1회.** 트레이 앱이라 세션이 몇 주씩 간다. 백업이 3주 전 것이면 복구가 곧 손실이다.

깨진 파일이 백업을 덮는 경로는 5절의 규칙이 막는다.

### 5. 읽기 실패와 검증

**읽지 못한 파일에는 쓰지 않는다.** 이 규칙 하나가 나머지를 결정한다.

| 실패 | 동작 |
|---|---|
| **미래 버전** (`schemaVersion`이 앱보다 높음) | 읽기·쓰기 모두 중단. "앱을 업데이트하세요". **`[백업에서 복구]`를 띄우지 않는다** — 그 백업도 신버전 앱이 남긴 것이라 같이 미래 버전이다 |
| **깨진 파일** (JSON 파싱 실패 또는 구조 검증 실패) | 앱은 열되 오류 화면을 띄우고 `[백업에서 복구]` / `[파일 위치 열기]`를 사용자가 고른다. 고를 때까지 파일에 쓰지 않는다 |
| **파일 없음** | 첫 실행이다. 7절 아래 |

기각한 대안: **자동 백업 복구.** 사용자가 **일부러** 고친 경우를 조용히 되돌려 놓고 아무 말도 안 한다. **빈 상태로 시작.** 깨진 파일을 빈 데이터로 덮어써 원본을 죽인다.

**파서는 구조만 본다.** 형식, 타입, 필수 필드, `entries`의 중복 `date`. 도메인 이상치는 통과시킨다.

기각한 대안: 도메인 규칙까지 검증(입사일 이전 휴가, 0.25 배수가 아닌 일수, 소멸일이 발생일보다 이른 조정). 함정이 셋이다.

1. **앱이 자기가 쓴 파일을 못 읽게 된다.** 8절에서 입사일을 바꾸고 삭제 제안을 거절하면 입사일 이전 휴가 기록이 정상적으로 존재한다.
2. **03번 3절의 의도가 죽는다.** 일수를 열거형이 아니라 소수로 둔 이유가 "나중에 다른 단위를 열 때 마이그레이션이 필요 없게"였는데, 파서가 0.25를 강제하면 그 문이 닫힌다.
3. **04번이 이미 이상한 입력을 흡수한다.** 배정되지 못한 휴가는 초과가 되어 잔여에 음수로 뜬다(04번 5절). 그것이 사용자가 보는 신호이며, 파일을 못 열게 하는 것보다 낫다.

정리하면 **도메인 이상치는 입력 UI가 막고 파서는 막지 않는다.**

### 6. 내보내기·가져오기

**내보내기 파일 = 저장 파일이다.** 별도 포맷을 두지 않는다. 그러면 파서·검증·마이그레이션이 한 벌이고, v1과 v2가 같은 코드를 쓴다. 포맷이 갈리면 둘이 어긋나는 날 가져오기가 조용히 틀린다.

**가져오기는 전체 교체다.** 직전에 백업을 남기고(4절), 화면에 "지금 데이터가 대체됩니다"를 명시한다.

기각한 대안: 병합. 같은 날짜의 휴가 기록이 양쪽에 있고 일수가 다를 때, 설정의 입사일이 다를 때 — 충돌 규칙이 여럿 필요한데 사용자가 그걸 판단할 근거가 화면에 없다. 가져오기의 실제 용도 둘(기기 옮기기, v2 이관)이 모두 통째로 옮기는 것이다.

### 7. 코어와 셸의 경계

**코어는 순수 함수 둘만 내놓는다.**

```
parse(text: string): Result<Data, ParseError>
serialize(data: Data): string
```

`ParseError`는 셋을 구분한다 — `invalid-json` / `schema-mismatch` / `future-version`. 5절의 표가 셋을 다르게 다루기 때문이다.

파일 읽기, 원자적 쓰기, 백업 시점, 오류 화면 — 순서를 짜는 일은 전부 셸이 한다.

티켓이 적은 전제("코어는 파일 시스템을 모른다")는 **I/O**를 모른다는 뜻이지 **포맷**을 모른다는 뜻이 아니다. 통로는 플랫폼마다 다르지만(디스크 vs IndexedDB) "무엇이 올바른 데이터인가"는 같아야 한다. 코어가 그 판정을 쥔다.

기각한 대안: 코어가 `Storage` 인터페이스(`read`/`write`)를 정의하고 셸이 구현. 4절의 원자적 쓰기와 백업 시점이 코어로 딸려 들어가는데, 그 둘은 파일 개념이다. PWA에는 이름 바꾸기도 `.bak`도 없어 v2에서 뜻이 없는 추상이 된다.

**첫 실행에는 파일을 만들지 않는다.** 입사일을 처음 저장할 때 파일이 생긴다. 즉 **파일 없음 = 입사일 없음**이며, 이것이 [07번](07-popover-ui-spec.md)의 "입사일이 없으면 설정 탭만 활성"인 상태다.

기각한 대안: `hireDate: null`인 파일을 미리 만들기. 타입이 `string | null`이 되고 **04번이 만든 모든 순수 함수가 `null`을 받았을 때를 정의해야 한다.** 계산에 의미 없는 분기가 생긴다. 파일을 안 만들면 코어에서 `hireDate`는 언제나 날짜다.

### 8. 입사일 교체 — 이직

04번이 좁혀준 대로 **이직해도 잔여 계산은 새 `hireDate` 하나만 본다**(계속근로연수가 리셋된다). 스키마에 회사 개념을 넣지 않는다.

남는 것은 입사일을 바꿀 때 기존 기록을 어떻게 하느냐인데, **"새 입사일 이전의 휴가 기록과 조정 레코드를 지울까요?"를 묻고 사용자가 고른다.** 삭제 직전에 백업이 남는다(4절).

그냥 두면 전 직장 몇 년치 휴가 기록이 새 발생분에 배정을 시도해 잔여가 크게 음수로 뜨고(04번 5절), 사용자가 수십 건을 손으로 지워야 한다. 스키마는 바뀌지 않는다 — 마이그레이션이 아니라 그냥 데이터 삭제다.

**거절할 수 있어야 한다.** 그래서 5절의 파서가 "입사일 이전 휴가 기록"을 거부하지 않는다.

**"과거 회사 기록 보관"은 Out of scope로 확정했다.** 잔여를 틀리게 만들지 않으므로 지도의 관문("이게 없으면 잔여가 틀리는가")을 통과하지 못한다.

### 후속 영향

- **[07번](07-popover-ui-spec.md)에 화면이 하나 늘었다.** 5절의 **읽기 실패 화면**은 탭이 아니다 — 팝오버 전체를 차지하고 버튼 둘(`[백업에서 복구]` / `[파일 위치 열기]`)을 갖는다. 미래 버전일 때는 버튼 없이 안내만 띄운다. 07번이 확정한 탭 3개 구조와 층위가 다르며, "입사일이 없으면 설정 탭만 활성"과 같은 종류의 상태 분기다. [11번](11-write-spec.md)이 스펙에 적는다.
- **[09번](09-project-structure.md)**: 코어 패키지가 계산 함수 외에 `parse`/`serialize`를 갖는다. 날짜가 `YYYY-MM-DD` 문자열로 저장되므로 `Temporal.PlainDate`와의 1:1 대응이 라이브러리 선택의 근거 하나로 추가된다.
- **[10번](10-release-build-pipeline.md)이 가벼워졌다.** SQLite를 기각해 **네이티브 모듈 0개가 유지된다.** 05번이 Electron을 고른 근거가 그대로 살아 있고, OS별 바이너리 번들 문제가 파이프라인에 들어오지 않는다.
- **[`CONTEXT.md`](../../../CONTEXT.md)는 고치지 않는다.** 2절의 키 이름이 전부 기존 용어와 1:1이고, 새로 생긴 이름(`schemaVersion`, `settings`, `entries`, `adjustments`)은 구현 용어이지 도메인 용어가 아니다.
- **지도의 안개 두 패치가 해소됐다.**
  - *이직 이력 지원* — 8절이 `hireDate` 교체를 결정했고, 과거 회사 기록 보관은 Out of scope로 갔다.
  - *v2 PWA 데이터 이관 경로의 구체* — 6절에서 내보내기 파일이 곧 저장 파일이 됐고 7절에서 PWA가 같은 `parse`를 쓴다. 그 너머(PWA가 IndexedDB에 어떻게 넣는가)는 v2 구현이라 이미 Out of scope다.

사용자가 Q1에 (b) + Prisma를 제안하며 "Q3(버저닝)과 Q5(손상 대비)는 DB가 해결해주는 것 아닌가"를 물었다. 확인 결과 **하나는 맞고 하나는 틀렸다.**

- **Q5는 사용자가 옳다.** SQLite의 트랜잭션이 쓰기 도중 죽는 경우를 막아준다. 원자적 쓰기를 손으로 만들 필요가 없다.
