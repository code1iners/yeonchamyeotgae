# 07. 팝오버 UI 사양

Type: prototype
Status: resolved
Blocked by: 03

## Question

트레이 아이콘을 클릭하면 뜨는 패널의 구조와 흐름을 확정한다. "최대한 간단하게"가 요구사항이므로, 넣지 않을 것을 정하는 게 넣을 것을 정하는 것만큼 중요하다.

1. **패널의 구성**. 03번 Q7에서 `발생 / 사용 / 예정 / 잔여` **네 줄을 다 보여주기로** 했다(그래야 회사 시스템 숫자와 대조된다). 여기에 소멸일까지 보여야 한다(03번 Q1-b). 이게 한 화면에 다 들어가는가? `history`는 같은 화면인가 별도 뷰인가?
2. **휴가 등록 흐름**. 몇 번의 조작으로 "오늘 연차 씀"이 기록되는가? 날짜 선택 UI가 필요한가, 아니면 "오늘/내일" 같은 빠른 버튼으로 대부분 해결되는가? 단위가 0.25까지 있으므로 종일/반차/반반차 선택이 흐름 안에 들어간다.

   **하루 1건이 확정이므로**(03번) 사흘 휴가는 `entry` 세 건이다. 사용자가 세 번 등록하게 둘 것인가, 기간을 받아 UI가 펼쳐 넣을 것인가?
3. **예정 휴가의 시각적 구분**. 이미 쓴 것과 쓸 예정인 것이 같은 리스트에 섞이는가? (자동 전환 여부는 03번에서 이미 답이 나왔다 — 상태는 날짜에서 파생되므로 항상 자동이다. 남은 건 **어떻게 보이느냐**뿐이다.)
4. **수정·삭제**. 잘못 등록한 항목을 어떻게 고치는가?
5. **설정 진입**. `hireDate`·`grantBasis`를 어디서 입력하는가. 팝오버 안인가 별도 창인가?

6. **조정 입력**. 03번에서 이월·사규 추가분·포상 휴가가 전부 `source: 'adjustment'` 레코드로 통합됐다. 사용자는 이걸 어디서 넣는가? 일수와 소멸일 두 개를 받아야 하는데, "진짜 단순한 앱" 전제 안에서 이게 몇 번의 조작인가?
7. **패널 크기와 스크롤**. 이력이 수십 건 쌓이면 어떻게 되는가?

## 참고

- `ui-design` Skill을 적용한다. 전형적인 AI풍 디자인을 피하고, 실제 메뉴바 앱들(runcat, Itsycal, Stats 등)의 기성 패턴을 우선한다.
- 저장소에 `DESIGN.md`나 `docs/DESIGN.md`가 생겼는지 먼저 확인한다.
- 용어는 [`CONTEXT.md`](../../../CONTEXT.md)를 따른다.
- 지도 Notes의 **"진짜 단순한 앱"** 전제가 이 티켓에 가장 세게 걸린다. 넣지 않을 것을 정하는 게 넣을 것을 정하는 것보다 중요하다.
- 실제로 클릭해보고 결정한다. 정적 목업만으로는 "간단한가"를 판단할 수 없다.

## Answer

**탭 3개(요약 / 이력 / 설정) 팝오버, 폭 380px. 등록은 [휴가 등록] → 달력 시트 → 날짜 한 번
클릭 → 단위·메모 폼. 이력은 리스트와 달력 두 뷰로 본다. 별도 창은 만들지 않는다.**

`prototype` 티켓이므로 결론은 [프로토타입](#프로토타입)을 눌러보며 나왔다. 변형 6종(A~F)을
만들었고 F가 결론이다. 라운드별 기록은 아래 Comments에 있다.

### 1. 패널의 구성 — 탭 3개

| 탭 | 내용 |
|---|---|
| **요약** | 잔여(헤더 한 줄) · 4줄 표 · 각주 · 발생분 리스트 · [휴가 등록] |
| **이력** | [리스트 \| 달력] 전환. 리스트는 예정 섹션 + 연차 연도별 접기, 달력은 월 뷰 |
| **설정** | 입사일 · 기준방식 · 조정 목록과 입력 |

**잔여는 헤더 한 줄에 작게 둔다.** 큰 숫자로 반복하지 않는 이유는 트레이에 이미 있기
때문이다. 다만 [06번](06-tray-display-spec.md)이 넘긴 요구대로 **소수를 그대로 쓴다**
(`12.25일`). 반올림·절사 금지 — Windows에서는 이 값이 정확한 잔여를 볼 수 있는 유일한 곳이다.

**4줄은 `발생 / 사용 / 예정 / 잔여` 순의 표이고, 각 행 오른쪽에 무엇인지 한 줄로 적는다**
(`발생 18 — 지금 살아 있는 발생분`). 03번 Q7의 목적이 회사 시스템과의 대조이므로 숫자만
있으면 무엇과 대조하는지 알 수 없다. 초과가 있으면 그 위에 `초과` 행이 하나 더 붙는다.

**발생 이력은 요약 탭에 산다.** 살아 있는 발생분만 소멸 임박 순으로 놓고, 각 행에
`남은 양/총량`과 소멸일을 둔다. 소멸까지 60일 이내면 날짜 대신 `D-31`을 경고색으로 띄운다.
소멸분은 이력 탭 맨 아래로 보낸다 — 평소에 볼 것이 아니다.

### 2. 등록 흐름 — 달력 하나로 들어간다

```
[휴가 등록] → 달력 시트 → 날짜 클릭 → 단위·메모 → [등록]      하루: 3클릭
                              ↘ [기간으로] → 종료일 클릭 ↗       기간: 5클릭
```

- **날짜를 한 번 누르면 그 하루로 확정**되고 바로 2단계로 넘어간다. 기간은 2단계에서
  `[기간으로]`를 눌러 종료일을 하나 더 고른다. 흔한 쪽(하루)을 짧게 두는 선택이다.
- **`[오늘]` `[내일]` 바로가기는 만들지 않는다.** 진입은 달력 하나다. 대가는 아래 8번에 적었다.
- 2단계는 `종일 / 반차 / 반반차` + 메모(선택) + 기간일 때만 `주말 제외`(기본 켜짐).
- **기간은 UI가 하루 1건씩 펼쳐 넣는다**([03번](03-leave-domain-model.md) 5절). 3/20~3/24를
  주말 제외로 넣으면 `entry` 3건이 만들어지는 것을 프로토타입에서 확인했다.
- 시트는 팝오버를 덮는다. 즉 **등록은 모드 전환**이며, 달력은 등록 흐름 안에만 있는 것이
  아니라 이력 탭에도 있다(아래 3번).

### 3. 예정의 시각적 구분 — 뷰마다 다르다

| | 예정 | 사용 |
|---|---|---|
| 리스트 | 맨 위 **예정 섹션**으로 분리 + 파란 `예정` 태그 | 연차 연도별 섹션 |
| 달력 | 파란 점 | 회색 점 |

상태는 날짜에서 파생되므로(03번 4절) 사용자가 바꿀 수 있는 것은 없다. 표시만의 문제다.

### 4. 수정·삭제 — 뷰마다 다르다

- **리스트**: 행에 마우스를 올리면 오른쪽에 `수정 / 삭제`. 수정은 그 자리에서 날짜·단위를 고친다.
- **달력**: 날짜를 누르면 아래에 그날의 기록이 펼쳐지고 거기서 단위 변경(`1 / ½ / ¼`)과 삭제를 한다.
- 등록을 안 쓰게 되면 상태 변경이 아니라 **삭제**다(03번 4절).

### 5. 설정 진입 — 팝오버 안 탭. 별도 창은 없다

`hireDate`·`grantBasis`는 설정 탭에서 받는다. **입사일이 없는 상태에서는 설정 탭만 활성이고
요약·이력은 비활성**이며, 조정 섹션도 감춘다 — 입사일도 없는데 조정을 넣을 이유가 없다.
[06번](06-tray-display-spec.md) Q4가 넘긴 "팝오버가 온보딩의 입구"가 이것이다. 트레이에 숫자가
없는 상태에서 아이콘을 누르면 두 필드짜리 설정 탭이 열린다.

**별도 창을 만들지 않는다**는 것이 이 결정의 다른 절반이다. 창을 쓰는 안(C)을 만들어봤고,
등록이 1클릭까지 짧아지는 대신 "왜 그 숫자인지"가 전부 창으로 넘어갔다. 06번이 팝오버에
요구한 것과 어긋난다.

### 6. 조정 입력 — 설정 탭, 네 필드

`일수 / 발생일 / 소멸일 / 메모`. [04번](04-accrual-rule-spec.md) 6절대로 발생일과 소멸일을
사용자가 넣고, **소멸일의 기본값은 그 시점 살아 있는 발생분 중 가장 늦은 소멸일**이다.
음수도 넣을 수 있다. 03번이 "버튼 하나, 입력창 하나"라고 적은 것보다 늘었지만, 04번이
소급 적용과 이월 사용기한을 위해 두 날짜를 요구했으므로 줄일 수 없다.

초과(음수 잔여)일 때 요약 탭 상단의 경고 줄에 있는 `조정을 추가` 링크가 **설정 탭으로
점프하며 이 폼을 열어둔 채로 넘긴다.** 원인 표시와 조치가 한 동선이어야 한다.

### 7. 크기와 스크롤

- **폭 380px 고정.** 달력 한 주가 7칸 × 48px로 들어가는 최소 폭이다.
- **높이는 탭 내용에 맞춰 조절한다.** 고정으로 만들어보니 탭마다 요구 높이가 크게 달라
  (요약 ~340 / 이력 달력 ~455 / 설정 ~330 / 등록 시트 ~400) 어느 값으로 고정해도 세 탭 중
  둘이 헐렁하거나 잘린다. 메뉴바 앱의 통상 동작이기도 하다.
- **이력 리스트만 스크롤한다.** 연차 연도별로 접고 **현재 연도만 펼친 채로 연다.** 기록 58건
  시나리오에서 이것 없이는 스크롤이 끝나지 않는다.

### 8. 04번·06번이 넘긴 세 가지의 처리

| 넘어온 것 | 처리 |
|---|---|
| 미래 예정이 미래 발생분에서 나간다(04번 9절 J) | 4줄의 `예정`에는 **배정된 몫만** 적고, 표 아래 각주 한 줄로 `등록한 예정은 4일이지만 1일은 내년 발생분에서 나갑니다 — 올해 잔여에 없습니다` |
| 잔여가 음수로 뜬다(04번 5절) | 헤더 잔여를 경고색으로, 4줄에 `초과` 행 추가, 요약 상단에 원인과 `조정을 추가` 링크 |
| 조정이 세 필드다(04번 6절) | 위 6번 |

**각주 방식을 고른 이유**: 예정에 등록 총량(4)을 쓰면 `발생 − 사용 − 예정 ≠ 잔여`가 되어
4줄이 검산되지 않는다. 배정분(3)만 쓰면 산술은 맞지만 사용자가 등록한 4일째가 요약에서
사라진다. 각주는 둘 다 만족시키는 유일한 배치다.

### 9. 소멸을 알아채는 경로

트레이가 소멸에 아무 표시를 하지 않기로 했으므로(06번 Q4) 이 티켓이 그 경로 전부를 갖는다.

1. 요약 탭 발생분 행의 **D-day 배지**(60일 이내, 경고색)
2. 이력 달력에서 소멸일 아래의 **빨간 밑줄**. 그날을 누르면 `2025년 이월 3일 소멸`이 뜬다

OS 알림은 만들지 않는다(03번에서 Out of scope).

### 10. 기각한 것

| | 기각 이유 |
|---|---|
| **A. 한 판 스크롤** | 사용자가 탭을 골랐다. 덧붙여 설정·조정 패널이 스크롤 영역을 덮어, 조정을 넣는 동안 무엇을 고치는 중인지(잔여·초과)가 화면에서 사라진다 |
| **C. 미니 팝오버 + 별도 창** | 등록 1클릭은 가장 짧았지만 "왜 그 숫자인지"가 전부 창으로 넘어가 06번 요구와 어긋난다. 달력 요구가 들어오며 300×240 전제도 깨졌다 |
| **E. 상시 월 뷰** | 팝오버가 620px로 커지고, 달력이 요약을 차지하면서 발생분 리스트가 이력 탭으로 밀려 **소멸 D-day가 요약에서 사라진다** |
| **`[오늘]` `[내일]` 바로가기** | 사용자가 진입을 달력 하나로 유지하기로 했다 |
| **끌어서 기간 지정** | 380px 팝오버의 30px 셀에서 오조작이 생긴다. 두 번 클릭으로 간다 |

### 11. 남긴 구멍

- **오늘 등록이 3클릭이다.** 가장 흔한 조작인데 C안의 1클릭보다 비싸다. 써보고 거슬리면
  트레이 우클릭 메뉴나 바로가기를 다시 검토한다 — 지금 넣지 않기로 한 것이지 불가능한 게 아니다.
- **Windows에서 실측하지 못했다.** 달력 셀 30px, 폭 380px, 시스템 폰트 13px은 전부 macOS 기준이다.
  06번과 같은 구멍이며 같은 시점에 함께 확인해야 한다.
- **다크·라이트는 시스템 테마를 따르는 수준까지만 봤다.** 트레이 아이콘 글리프는 별도 결정이다
  → [12번](12-icon-glyph.md)으로 승격했다.

- **2026-08-25 — [04번 티켓](04-accrual-rule-spec.md)의 영향**: 팝오버가 인지시켜야 할 것이 세 가지 늘었다. (1) **미래 예정은 미래 발생분에서 나간다.** 2025-12월에 2026-02월 휴가를 등록해도 올해 잔여가 줄지 않는다(04번 9절 J). 사용자가 이 규칙을 승인하면서 "인지만 시킬 수 있으면 된다"는 조건을 달았다. (2) **잔여가 음수로 뜰 수 있다**(04번 5절). 그 원인과 조치(조정 입력)를 보여줘야 한다. (3) **조정 입력은 일수·발생일·소멸일 세 필드**다(04번 6절) — 03번이 "버튼 하나, 입력창 하나"라고 적은 것보다 늘었다. 04번 8절대로 계산 엔진이 발생 레코드별 내역을 통째로 반환하므로 표시할 데이터는 이미 있다.

### 06번 결정에서 넘어온 것 (2026-08-25)

[06번](06-tray-display-spec.md)이 트레이 표시를 확정하면서 팝오버에 요구사항 두 개를 넘긴다.

- **Windows에서는 팝오버가 정확한 잔여의 유일한 화면이다.** 트레이가 내림 정수(`12`)만
  띄우므로 소수(`12.75`)를 볼 수 있는 곳이 팝오버와 툴팁뿐이다. 잔여를 절대 정수로
  반올림해 보여주지 말 것. macOS는 트레이에 이미 정확한 값이 있어 이 압력이 없지만
  팝오버는 양쪽 공통이다.
- **입사일 미설정 상태에서 팝오버가 온보딩의 입구다.** 06번 Q4가 그 상태의 트레이를
  "앱 아이콘, 숫자 없음"으로 정했고, 사용자가 다음에 하는 행동은 아이콘 클릭이다.
  이 티켓 5번(설정 진입)과 지도 Fog의 "온보딩 흐름"이 여기서 만난다 — 잔여를 계산할 수
  없는 상태에서 팝오버가 무엇을 보여주는지 정해야 한다.

트레이는 소멸 임박에 아무 표시를 하지 않기로 했으므로(06번 Q4), 소멸을 사용자가 알아채는
경로는 이 티켓이 정하는 발생 이력 표시가 전부다.

### 프로토타입 라운드 기록 (2026-08-26)

변형을 만들어 보여주고, 답을 받아 다음 변형에 반영하는 식으로 세 라운드를 돌았다.
사용자 답변은 원문 그대로 옮겼다.

#### 라운드 1 — 구조 (A / B / C)

A 한 판 스크롤, B 탭 3개, C 미니 팝오버 + 별도 창을 만들었다. 만들면서 나온 사실 다섯 가지를
먼저 보고했다: (1) 4줄의 산술이 예정 표기를 강제한다, (2) B의 "탭마다 짧게"가 균등하지 않다
(요약은 늘 짧고 설정의 조정 폼은 스크롤이 생긴다), (3) C는 등록이 1클릭이지만 근거가 전부
창으로 간다, (4) A는 온보딩에서 620px에 3필드만 뜬다, (5) 소멸 인지 구멍은 세 안 다 못 메운다.

| | 질문 | 답변 |
|---|---|---|
| Q1 | 구조 A / B / C | *"탭3개가 무난한데 달력 UI 가 있었으면 좋겠는데 이건 별도인가?"* |
| Q2 | 미래 발생분 예정을 요약에 어떻게 적는가 | **배정분만 + 각주** |
| Q3 | 등록의 기본 조작 | *"휴가 등록 버튼 누르면 달력 UI 가 표시되고 해당 일을 누르면 다음 입력 스텝 폼으로 전환 후 휴가 생성."* |
| Q4 | 설정·조정의 자리 | **팝오버 안 탭** |

Q1의 달력 물음에는 "별도 티켓이 아니다"로 답했다 — Q3의 답이 등록 흐름 자체를 달력으로
정의하므로 이 티켓 안이다. 다만 **달력을 어디에 두느냐**가 요약 탭 구조를 바꾸므로 결정이
하나 늘었고, 그래서 2라운드를 만들었다.

#### 라운드 2 — 달력 (D / E)

D(등록할 때만 뜨는 시트)와 E(요약 탭에 상주)를 만들었다. 둘 다 1라운드 확정분을 반영했다.
조작 횟수를 프로그램으로 눌러 셌다: 오늘 하루 종일 등록이 D 4클릭 / E 3클릭이고,
1라운드 C안은 1클릭이었다. **달력은 기간·과거·미래에 강하고 오늘에 약하다**는 것을 이때 쟀다.

| | 질문 | 답변 |
|---|---|---|
| Q5 | 달력의 자리 | *"등록할 때 시트로 보여주고, 달력 UI 로 내 연차 사용 이력을 확인 할 수 있었으면 좋겠음. list ui, 달력 ui 모두 제공해야함."* |
| Q6 | 날짜 한 번 클릭 후 | **단일 우선 (바로 2단계)** |
| Q7 | `[오늘]` 바로가기 | **안 넣는다 — 달력 하나로** |
| Q8 | 소멸일 밑줄 | **유지** |

Q5가 D도 E도 아닌 답이었다. 달력이 **등록용과 조회용 두 몫**을 해야 하는데 D는 등록에만,
E는 요약에만 뒀기 때문이다. 이력 탭을 리스트/달력 전환으로 만드는 것이 세 번째 답이 됐다.

#### 라운드 3 — 확정안 F

F = D의 등록 시트 + 이력 탭의 리스트/달력 전환 + 단일 우선 클릭. 눌러서 확인한 것:

- 하루 등록 **3클릭**, 기간 등록 **5클릭**(3/20~3/24 주말 제외 → `entry` 3건)
- 이력 달력에서 날짜를 눌러 그날 기록의 단위 변경·삭제가 된다
- 온보딩에서 설정 탭이 강제되고 조정 섹션이 숨는다
- 고정 높이로는 세 탭을 다 담을 수 없다 → 7번의 "높이는 내용에 맞춘다"가 여기서 나왔다
