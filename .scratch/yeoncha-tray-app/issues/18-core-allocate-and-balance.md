# 18. 배정과 잔여 (allocate / computeBalance)

Type: task
Status: resolved
Blocked by: 17

## What to build

휴가 기록을 발생 레코드에 **배정**하고 조회일의 **잔여**와 내역을 내는 순수 함수 둘. 이 티켓이
닫히면 **제품의 전부가 계산 가능해진다** — [검증 케이스 14건](../spec.md)의 잔여 열 전부가 여기서 나온다.

**잔여는 합계끼리의 뺄셈이 아니다**([스펙 3.1절](../spec.md)). 뺄셈으로 구현하면 소멸일이 다른
발생분이 겹칠 때 같은 입력에 잔여가 둘 나오고, 과거 휴가 기록이 누적되어 매년 1월에 이중
차감이 난다. **배정 결과는 저장하지 않고 조회 시점에 매번 계산한다.**

**계산 엔진은 잔여 숫자 하나를 반환하지 않는다**(1절). 발생 레코드마다
`발생일 / source / 일수 / 배정된 사용량 / 남은 양 / 소멸일 / 소멸 여부`를 담은 내역과, 여기에
**초과 일수**와 **미래 발생분에 배정된 예정**을 얹어 돌려준다 — 트레이용·팝오버용으로 나눠
부르면 같은 일을 두 번 한다.

배정 규칙(3.4절)과 잔여 공식(3.5절), 초과의 수명(3.6절)이 이 티켓의 본문이다. 특히
**초과 일수는 그 휴가 날짜에 유효했던 발생 레코드들의 소멸일 중 가장 늦은 것까지 살아 있다가
사라진다** — 수명을 주지 않고 영구히 빼면 3.1절의 누적 오차가 그대로 돌아온다.

## Answer

[balance.ts](../../../packages/core/src/balance.ts)의 `allocate` / `computeBalance` + 표 기반
테스트 41건으로 구현했다. 코어 테스트 90건(배정·잔여 41 + 발생 12 + 직렬화 25 + 표시 4 +
Temporal 8), `turbo run lint typecheck test` 전체 통과.

- **시그니처** — `allocate({ grants, entries }): AllocationResult`,
  `computeBalance({ grants, entries, today }): Balance`. `allocate`는 "오늘"을 모른다 —
  배정은 조회일과 무관하고, **사용과 예정은 날짜에서 파생**되므로(`CONTEXT.md`) 그 갈림은
  조회일을 아는 `computeBalance`가 한다. 그래서 `Allocation`이 레코드별 총량뿐 아니라
  휴가 기록별 몫 `draws`를 들고 있다 — 4줄 표의 사용·예정이 여기서 갈린다.
- **날짜 비교는 문자열 비교다.** 양쪽 다 길이가 같은 YYYY-MM-DD라 사전순이 곧 시간순이고,
  이 파일에는 날짜 **산술**이 없다(산술은 전부 17번의 `computeGrants`에 있다).
- **정렬 키 하나를 배정과 내역이 공유한다** — `sortByAllocationOrder`가
  `소멸일 ↑ → 발생일 ↑ → source → 입력 순서`로 세우고, 배정은 여기서 양수만 걸러 쓴다.
  5.1절의 "살아 있는 발생분 리스트를 소멸 임박 순으로"가 내역 순서와 같아진다.
- **잔여는 3항 공식 그대로다** — `balance = Σ(유효 레코드의 남은 양) − 살아 있는 초과`.
  음수 조정은 `allocated`가 0이라 남은 양이 곧 일수이고, 그래서 별도 항 없이 합산된다.
  `발생 − 사용 − 예정 − 초과 = 잔여`가 검산되는 것을 테스트가 고정한다.
- **초과의 수명은 발생 레코드 전부에서 나온다**(양수 후보만이 아니다). 음수 조정만 유효했던
  날의 초과가 수명을 못 받아 영구히 잔여를 깎는 것이 3.1절 누적 오차의 재발이기 때문이다.
  수명이 `null`인 초과는 **아직 어떤 발생 레코드도 없는 상태**뿐이며, 첫 발생분이 생기는
  순간 그 소멸일을 물려받으므로 첫 발생일을 넘겨 이어지지 않는다(전용 테스트 2건).
- **초과에 하한을 두지 않았다** — 3.5절이 "조회일에 아직 **살아 있는** 초과분"이라고만 쓰고,
  3.6절도 상한(소멸일)만 준다. 미래 예정이 배정에 실패해 생긴 초과도 오늘 잔여에서 빠진다.
- **`Balance`에 `plannedTotal`을 실었다.** 5.1절 각주(`등록한 예정은 4일이지만 1일은 내년
  발생분에서 나갑니다`)의 앞쪽 숫자다. `planned + plannedOnFutureGrants`로는 복원되지
  않는다 — 배정되지 못하고 초과로 떨어진 예정이 어느 쪽에도 안 잡히기 때문이다.
- **`GrantDetail`은 티켓이 열거한 7필드 그대로 두었다.** 5.1절의 "살아 있는 발생분"은
  `expired`만으로 안 갈린다(미래 발생분도 `expired: false`다). 필드를 늘리는 대신 남겨
  두었으니, 24번 요약 탭이 실제로 필요하면 그때 `valid`를 얹는다.
- **조회일 당일의 휴가 기록은 사용으로 센다.** `CONTEXT.md`가 사용/예정을 "오늘 이전/이후"로만
  갈라 당일이 비어 있다. 잔여 값에는 영향이 없고 4줄 표의 행만 갈리는 선택이다.

### 스펙 케이스 I의 산수 오류

**스펙 표와 이 티켓 AC의 케이스 I가 케이스 D와 모순이다.** 2024-01-01 입사자의 2027-01-01
발생분은 케이스 D가 **16일**로 고정하고(`min(25, 15 + floor((3−1)/2))`), 3.2절 공식도 16을
낸다. 그런데 케이스 I는 같은 입사일의 2027-01-05 잔여를 **15**(단순 뺄셈이면 −7)로 적었다 —
역산하면 `15 − 22 = −7`이라 저자가 그 해 발생분을 15로 잡고 두 칸을 함께 적었다.

케이스 I가 고정하려는 것은 "연초에 이중 차감이 나지 않는다 = 그 해 발생분 전액이 그대로
남는다"이므로, **발생 일수를 따라 16(단순 뺄셈 −6)으로 구현**했다. 3.1절 본문에도 같은 −7이
적혀 있으므로 `spec.md`를 고치려면 **1231행 근처 케이스 I 표와 3.1절 본문 두 곳**을 함께
고쳐야 한다. 이 티켓에서는 고치지 않았다 — 확정된 스펙 문서의 검증 표를 구현이 단독으로
갈아치우지 않는다. 코드 리뷰 두 축이 모두 독립적으로 같은 결론(16이 맞다)을 냈다.
