# 06. 트레이 표시 사양

Type: prototype
Status: resolved
Blocked by: 03, 05

## Question

트레이/메뉴바에 상시 무엇이 어떻게 보이는가? runcat처럼 항상 눈에 띄는 게 이 앱의 존재 이유이므로, 여기가 흐리면 제품이 흐려진다.

1. **표시할 값**. `잔여`(balance, 예정까지 차감한 값)를 띄우는 게 전제지만, 숫자만인가 아이콘 + 숫자인가? 단위 표기("4" vs "4일" vs "연차 4")는?
2. **소수점 처리**. 03번에서 **반반차(0.25)까지** 확정되어 최대 표기가 `12.75` **다섯 글자**다. Windows는 작은 아이콘 이미지에 렌더링해야 하므로 이대로는 거의 확실히 안 읽힌다. 절사·반올림하고 팝오버에서만 정확히 보여주는 쪽이 유력한데, 그러면 트레이 숫자와 팝오버 숫자가 달라진다. 그 불일치를 사용자가 어떻게 알아채는가?
3. **macOS/Windows 차이 흡수**. macOS는 텍스트, Windows는 이미지 렌더링이라는 비대칭을 코어가 아는가, 셸이 숨기는가?
4. **경계 상태**. 잔여가 0일 때, 음수일 때(초과 사용), 설정이 아직 없을 때(입사일 미입력), 소멸 임박일 때 각각 무엇이 보이는가?
5. **갱신 시점**. 날짜가 바뀌면 자동으로 갱신되는가? 앱이 며칠간 켜져 있을 때 자정을 넘기면?

## Comments

- **2026-08-25 — [04번 티켓](04-accrual-rule-spec.md)의 영향**: 이 티켓이 실측할 문자열이 바뀌었다. [03번](03-leave-domain-model.md)이 남긴 "최대 `12.75` 다섯 글자"는 틀렸다 — 회계연도 겹침에서 발생만으로 `24.75`가 나오고(04번 9절 N), 발생 상한 25일에 상한 없는 조정 레코드가 더해진다. 그리고 **04번 5절이 잔여의 음수를 허용**했으므로 `−3.75` 처럼 부호가 붙는다. 음수는 버그가 아니라 "사용자가 조정을 아직 안 넣었다"는 신호로 의도적으로 노출하는 값이니, 트레이가 이를 표시할 수 있어야 한다. 절사 여부를 정할 때 이 폭을 기준으로 삼을 것.

### 05번 결정에서 넘어온 것 (2026-08-25)

셸은 **Electron**으로 확정됐다([05번](05-shell-framework-adr.md)). macOS에서 실측된 것:

- `setTitle()`로 아이콘 없이 텍스트만 띄울 수 있다. `12.75`는 상태 항목 폭 **53pt**,
  `-1.25`는 51pt, `0`은 29pt다. 상태 항목이 문자열 길이에 맞춰 스스로 늘어나므로,
  이 티켓 위 Comment가 교정한 최악 폭(`-24.75` 여섯 글자)도 약 64pt로 들어간다.
  **macOS 쪽 Q2는 문제가 아니다** — 절사할 이유가 없다. (여섯 글자는 재보지 않았고,
  글자당 약 10pt 선형에서 추정한 값이다.)
- canvas로 그린 이미지를 트레이에 올리는 경로도 확인됐다(왕복 0.9ms). 16px 높이로 렌더한
  `12.75`는 **63×32 px @2x**로 나오고, 실제 메뉴바에서 읽힌다.
- 따라서 **트레이 숫자와 팝오버 숫자가 달라지는 상황을 macOS에서는 만들 필요가 없다.**
  Q2의 "절사·반올림하고 팝오버에서만 정확히" 안은 macOS만 놓고 보면 근거가 없다.

**반드시 확인해야 하는 가정 — Windows 알림 영역 아이콘은 정사각형이다.**
Win32 `Shell_NotifyIcon`은 `SM_CXSMICON` 크기의 정사각 아이콘을 받는다(100% DPI에서 16×16,
150%에서 24×24). 우리가 그린 63×32 이미지를 16×16에 밀어넣으면 글자당 3px가 되어 거의 확실히
안 읽힌다. **05번은 Windows에서 아무것도 실행하지 못했으므로 이건 사실이 아니라 가정이다.**
프레임워크와 무관한 제약이라 05번을 뒤집지는 않지만, 사실이면 이 티켓 Q2의 답이 바뀐다:

- 정사각 제약이 **사실이면** → 다섯 글자는 애초에 불가능하다. 선택지는 두 줄 배치
  (`12` 위 `.75`), 정수만(`12`), 또는 아이콘+툴팁으로 후퇴다. "절사냐 반올림이냐"가 아니라
  **"소수를 트레이에서 포기하느냐"** 가 질문이 된다.
- 제약이 **아니면**(Electron이 가로로 긴 아이콘을 통과시키면) → macOS와 같은 답으로 통일된다.

이 티켓을 여는 세션이 가장 먼저 할 일은 이 가정을 확정하는 것이다. Windows 실행이
불가능하면 문서 근거로라도 판정한다.

## Answer

### 결론

트레이는 **잔여를 숫자로만** 상시 띄운다. 아이콘도 단위 표기("일", "연차")도 없다 —
Windows 예산이 두 글자뿐이라 아이콘이 들어갈 자리가 없고, macOS만 아이콘을 붙이면
비대칭이 정밀도를 넘어 "무엇을 보여주는 물건인가"까지 갈라진다.

| | macOS | Windows |
| --- | --- | --- |
| 경로 | `setTitle()` (네이티브 텍스트) | 정사각 canvas → `nativeImage` → `setImage()` |
| 표시 | 잔여 **그대로**: `12.75`, `-24.75`, `0` | 잔여의 **내림 정수**: `12`, `-25`, `0` |
| 정확한 값 | 트레이에 이미 있다 | 툴팁과 팝오버 |
| 입사일 미설정 | 앱 아이콘(정사각), 숫자 없음 | 같음 |
| 소멸 임박 | 아무것도 하지 않는다 | 같음 |

**툴팁은 양쪽 다 정확한 값을 갖는다** — `연차몇개 — 잔여 12.75일` 형태. Windows에서
트레이 숫자와 팝오버 숫자가 갈리는 유일한 경우이고, 그 간극을 메우는 게 툴팁의 존재 이유다.

### 1. Windows 정사각 제약은 사실이다 — 05번이 남긴 가정을 확정한다

세 갈래 근거가 같은 방향이다.

- **Win32 계약**: 알림 영역 아이콘은 `SM_CXSMICON × SM_CYSMICON` 크기다. 정의상 정사각이다.
  ([NOTIFYICONDATAW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw))
- **Electron 메인테이너 zcbenz가 우리와 같은 사례에 답했다** — macOS 메뉴바에 숫자를
  띄우는 앱을 Windows로 옮긴 케이스에, 알림 영역 아이콘은 정사각으로만 보이며 이는
  Windows의 제약이고, 원하는 걸 하려면 taskbar toolbar API가 필요한데 Electron 범위를
  넘는다고 했다. ([electron#9267](https://github.com/electron/electron/issues/9267))
- **그 탈출구도 막혔다**: taskbar toolbar(deskband)는 Windows 11에서 제거됐다.

**소스를 보면 더 나쁘다.** `Tray.setImage`는 Windows에서
`native_image->GetHICON(GetSystemMetrics(SM_CXSMICON))`을 부르지만
(`shell/browser/api/electron_api_tray.cc`), `GetHICON`은 `.ico` **파일 경로**가 없으면
그 size 인자를 **무시하고** `IconUtil::CreateHICONFromSkBitmap(image_.AsBitmap())`으로
원본 크기 그대로 HICON을 만든다(`shell/common/api/electron_api_native_image.cc`).
우리 canvas 경로는 파일이 아니므로 63×32 HICON이 셸에 그대로 넘어가고, 찌그러지는 건
셸에서 일어난다. **Electron이 대신 맞춰주는 게 없으니 정사각 비트맵을 우리가 직접 그려
넘겨야 한다.**

### 2. 실측 — 정사각 예산은 "편한 두 글자"다

정사각 캔버스에 후보를 그려 잰 cap height(device px). 05번의 63×32 가로 캔버스와 달리
정사각을 강제한 값이다.

| 후보 | 16px (100%) | 20px (125%) | 24px (150%) | 32px (200%) |
| --- | --- | --- | --- | --- |
| `12.75` 그대로 (대조군) | **3.3** | 4.4 | 5.5 | 7.4 |
| 절사 `12` (2글자) | **9.0** | 11.9 | 14.8 | 18.3 |
| 절사 `-24` (3글자, 최악) | **5.4** | 6.9 | 8.7 | 11.6 |
| 두 줄 `-24` / `.75` | 6.1 / 6.9 | 6.9 / 8 | 8.7 / 10.1 | 12.3 / 14.4 |
| 음수 반전 `24` | 6.5 | 7.6 | 10.1 | 13.7 |

**구조적으로 중요한 발견: 한 줄일 때 병목은 높이가 아니라 폭이다.** 16px 정사각에
세로 여유는 남는데 글자 수가 늘면 폭이 먼저 막힌다. 2글자면 cap 9px로 넉넉하고,
3글자(부호가 글자 하나를 먹는다)면 5.4px로 빠듯하고, 5글자는 3.3px로 죽는다.

그래서 **이 티켓 본문 Q2의 질문 형태가 틀렸다.** "절사냐 반올림이냐"가 아니라
**"두 글자에 무엇을 담느냐"** 다. 절사와 반올림은 같은 픽셀 예산을 쓰므로 픽셀이
가르지 않는다 — 아래 5번의 방향 논거가 가른다.

### 3. Q1 — 표시할 값: 숫자만

아이콘 없음, 단위 없음. Windows 예산이 두 글자라 아이콘이 물리적으로 안 들어간다.
macOS만 아이콘을 붙이는 안은 기각했다: 6번에서 정밀도의 비대칭은 받아들이지만,
그건 "같은 종류의 것을 다른 정밀도로" 보여주는 것이고 아이콘 추가는 표시물의 종류가
갈리는 것이다. 지도의 "진짜 단순한 앱" 전제와도 맞지 않는다.

앱 아이콘은 **폴백 글리프로만** 존재한다 — 입사일 미설정 상태(Q4)에서 숫자 자리를 대신한다.
숫자와 상시 동반하지 않는다.

### 4. Q2 — 소수: Windows는 버린다, macOS는 버리지 않는다

**Windows는 내림 정수.** 두 줄 배치는 값이 정확한 유일한 후보였지만 16px에서
두 줄 사이 여백이 사실상 0이라 두 줄이 붙어 보인다(근거 캡처 2·3번). 24px(150%,
요즘 노트북 기본)부터는 읽히지만, 100% DPI를 포기할 근거가 없다. 아이콘만 후보는
"runcat처럼 항상 눈에 띄는 게 이 앱의 존재 이유"라는 이 티켓의 전제와 정면 충돌해 기각.

**macOS는 잔여를 그대로 띄운다.** 05번이 실측했듯 상태 항목이 문자열 길이에 맞춰
늘어나므로 `-24.75` 여섯 글자도 약 64pt로 들어간다. 정보를 버릴 이유가 없다.

**불일치를 사용자가 어떻게 알아채는가** — 세 겹으로 답한다.

1. **툴팁이 정확한 값을 갖는다.** Windows에서 트레이 숫자에 마우스를 올리면 `12.75`가 나온다.
2. **팝오버가 정확한 값을 갖는다.** 잔여를 소수까지 그대로 보여준다(07번의 몫).
3. **내림은 한 방향으로만 틀린다.** 아래 5번 때문에 트레이 숫자는 **항상 실제 잔여
   이하**다. 그래서 "적어도 이만큼"으로 읽으면 트레이만 봐도 틀리지 않는다. 이 불변식이
   무너지면 불일치가 버그가 되므로, 이건 표기 취향이 아니라 계약이다.

### 5. 내림(floor)이다, 0 방향 절사(trunc)가 아니다

같은 "절사"로 불리지만 음수에서 갈리고, 갈리는 방향이 결정적이다.

| 잔여 | `Math.floor` | `Math.trunc` |
| --- | --- | --- |
| `12.75` | `12` | `12` |
| `-24.75` | `-25` | `-24` |
| `-0.25` | `-1` | **`0`** |

`trunc`는 `-0.25`를 `0`으로 보여준다 — **초과 사용을 트레이에서 완전히 숨긴다.**
[04번 5절](04-accrual-rule-spec.md)이 음수를 "사용자가 조정을 아직 안 넣었다"는 신호로
의도적으로 노출하기로 했으므로 이건 그 결정을 무효화한다. `floor`는 `-1`을 보여줘
신호를 살린다.

`floor`는 4번의 불변식(**표시값 ≤ 실제 잔여**)을 부호와 무관하게 지키는 유일한 선택이기도
하다. `trunc`는 음수에서 실제보다 큰 값을 보여줘(−24.75인데 `-24`) 초과를 실제보다
덜해 보이게 만든다. 반올림은 양수에서도 이 불변식을 깨므로(`11.6` → `12`) 같은 이유로 기각.

**대가**: `-0.25`가 `-1`로 보인다. 0.75일을 과장하지만, 과장 방향이 "문제가 실제보다
심각해 보인다"는 안전한 쪽이고, 정확한 값은 툴팁과 팝오버에 있다.

프로토타입 코드는 `Math.trunc`로 구현했다 — 구현에 옮길 때 `Math.floor`로 고칠 것.

### 6. Q3 — 비대칭은 코어가 모른다, 셸도 분기하지 않는다

지도의 확정 전제는 "코어 계산 엔진은 순수 TypeScript 패키지, 브라우저·Node·웹뷰
어디서든 동작"이다. 코어에 `process.platform`이 들어가면 그 전제가 깨지고 v2 PWA가
못 받는다. 그렇다고 셸에 `if (isMac)` 두 갈래 포매팅을 두면 규칙이 두 곳에 흩어진다.

**비대칭을 분기가 아니라 파라미터로 만든다.** 코어 패키지가 순수 함수 하나를 내보낸다:

```
formatTrayLabel(balance: number, opts: { maxGlyphs: number }): string
```

- `maxGlyphs`가 잔여의 정확한 표기를 담을 수 있으면 그대로 돌려준다.
- 담지 못하면 내림 정수를 돌려준다.

셸은 예산만 정한다 — macOS는 `Infinity`, Windows는 `3`(부호 한 글자 + 숫자 두 글자).
플랫폼 지식은 셸의 상수 두 개로 줄고, 규칙은 코어에 한 곳만 산다. v2 PWA는 자기 예산을
넣어 같은 함수를 쓴다.

**렌더링은 셸의 몫이다.** `setTitle` 대 정사각 canvas는 문자열이 정해진 뒤의 문제이므로
코어가 알 필요가 없다. 이 경계는 [09번](09-project-structure.md)이 패키지 구조를 정할 때
지켜야 할 제약이다.

### 7. Q4 — 경계 상태

| 상태 | 트레이 |
| --- | --- |
| 잔여 `0` | `0`. 한 글자라 예산에 여유가 있다. 특별 취급 없음 |
| 잔여 음수 | 부호 그대로 `-3`, 최악 `-25`. 16px에서 cap 5.4px로 빠듯하지만 읽힌다 |
| 입사일 미설정 | 앱 아이콘(정사각), 숫자 없음. 클릭하면 온보딩이 열린다 |
| 소멸 임박 | **아무것도 하지 않는다** |

음수의 반전 표시(검은 사각에 숫자 파냄)와 Windows 한정 빨강은 검토 후 기각했다.
반전은 항상 두 글자여서 cap 6.5px로 나아지지만 16px에서 파낸 획이 뭉개져 대비를 잃고
(근거 캡처 3번), "반전 = 음수"를 학습해야 한다. 빨강은 macOS 템플릿 이미지가 알파만
쓰므로 라이트/다크 메뉴바 자동 대응을 포기해야 색이 생겨 비대칭이 하나 더 늘어난다.
현실적으로 `-24.75`는 극단값이고 흔한 음수는 `-3` 같은 두 글자다.

**소멸 임박에 아무것도 하지 않는 건 이 티켓의 새 결정이 아니다** — 지도가 "소멸 알림·
사용 촉진"을 Out of scope로 이미 닫았고, [03번](03-leave-domain-model.md)이 소멸일 노출을
발생 이력까지로 한정했다. 두 글자 예산에 경고 표식을 넣을 자리도 없다.

### 8. Q5 — 갱신 시점

**잔여는 날짜가 바뀌면 실제로 변한다.** 발생일(매월 개근, 1년+1일, 회계연도 1월 1일)과
소멸일이 모두 날짜 경계에 걸려 있고, [04번](04-accrual-rule-spec.md)에 따라 발생분이
소멸하면 그 발생분에 배정된 초과도 함께 사라진다. 자정을 넘겨도 그대로면 트레이가 틀린다.

세 가지 트리거로 다시 계산한다.

1. **데이터 변경** — 휴가·조정 레코드나 설정이 바뀔 때.
2. **로컬 자정** — 다음 자정까지의 지연을 매번 새로 계산해 한 번씩 예약한다.
   `setTimeout(24시간)` 반복은 틀린다. 드리프트가 쌓이고, 절전 중에는 타이머가 멈추며,
   시간대·서머타임 변경으로 자정 간격이 24시간이 아닐 수 있다.
3. **절전 복귀와 시각 변경** — Electron `powerMonitor`의 `resume`, `shutdown` 계열과
   시스템 시각·시간대 변경. 며칠간 뚜껑을 덮어둔 노트북이 실제 사용 패턴이고, 이 경우
   2번의 예약된 타이머는 이미 지나가 있다. 복귀 시 무조건 다시 계산한다.

계산 자체가 순수 함수이므로 재계산은 싸다. **"오늘"을 코어가 스스로 읽지 않고 인자로
받는 것**이 전제다 — 그러지 않으면 이 트리거들이 아무 효과가 없고 테스트도 못 한다.

### 프로토타입

`prototype/tray-display-spike` 브랜치의 `prototype-electron-tray/`에 있다(05번 스파이크
위에 얹었다). main에 병합하지 않으며 구현에 재활용하지 않는다 — 위 실측치의 **근거
원본**으로만 남긴다.

```
git switch prototype/tray-display-spike
cd prototype-electron-tray && pnpm install
pnpm exec vite build && pnpm start
```

팝오버에 후보 × DPI 격자가 뜬다. 각 칸은 위가 1:1, 아래가 확대, 아래 숫자가 cap height다.
후보 이름을 누르면 그 후보가 실제 메뉴바에 올라간다. `evidence/`에 판단 근거가 된 캡처
세 장이 있다.

읽어볼 값이 있는 건 `renderer/drawTraySquare.js` 한 파일이다 — 정사각 안에 글자를
맞추는 `fitFont`(폭·cap height 양쪽으로 이진 탐색)와, cap height 기준 세로 중앙 정렬이
`textBaseline: 'middle'`과 다른 이유가 거기 있다. import가 아니라 보고 새로 쓰는 것이다.

### 검증하지 못한 것

- **Windows에서 아무것도 실행하지 못했다.** 정사각 제약은 Win32 계약·Electron
  메인테이너 답변·Electron 소스 세 갈래 문서 근거로 확정했지만, 16px에서 `-25`가
  실제로 읽히는지는 macOS에서 16px 캔버스를 확대해 본 것이다. 물리적 크기는 비슷하나
  래스터라이저와 폰트가 다르다(Segoe UI 대 SF Pro, ClearType 대 macOS 렌더링).
  **Windows 실물이 잡히면 가장 먼저 확인할 것은 `-25`와 `12`의 16px 가독성이다.**
  틀렸을 때의 후퇴는 24px 이상에서만 숫자를 쓰고 16px에서는 아이콘으로 내려가는 것이며,
  그건 이 결정의 구조를 바꾸지 않는다.
- **Windows 알림 영역의 실제 DPI 분포를 모른다.** 16px(100%)이 여전히 흔한지, 대부분
  24px(150%)인지에 따라 위 후퇴가 필요한지가 갈린다.
- 폰트를 실제로 어느 것으로 그리는지 정하지 않았다. 프로토타입은 플랫폼 기본 스택을
  썼다. 숫자만 그리므로 tabular numerals 여부가 폭에 영향을 준다.
