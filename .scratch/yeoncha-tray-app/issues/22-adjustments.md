# 22. 조정 — 설정 탭의 조정 입력과 목록

Type: task
Status: resolved
Blocked by: 20

## What to build

사용자가 **이월·사규 추가분·포상 휴가**를 직접 넣고 고치고 지우는 화면. 법정 계산과 회사 규정의
차이를 메우는 유일한 통로이며, 초과가 났을 때의 조치 경로다.

**조정 입력은 네 필드다** — `일수 / 발생일 / 소멸일 / 메모`([스펙 5.4절](../spec.md)).

- **소멸일이 입력인 이유**: 이월 사용기한이 회사마다 다르다(1년 더 / 6개월 / 무기한). 규칙이
  정하면 조용히 틀리고, 소멸시키지 않으면 이월분이 영원히 남아 매년 잔여를 부풀린다.
  **기본값은 그 시점 살아 있는 발생분 중 가장 늦은 소멸일**이다.
- **발생일이 입력인 이유**: 배정은 "휴가 날짜에 유효한 레코드"에만 하므로, 발생일이 입력한 날로
  고정되면 **과거의 초과를 조정으로 풀 수 없다**(케이스 L이 이것을 고정한다). 기본값은 입력한 날.
- **음수를 넣을 수 있다** — 회사가 법정보다 덜 주는 해를 표현한다.
- **조정은 덮어쓰기가 아니라 덧붙이기다.** 계산이 만든 발생 레코드는 사용자가 고칠 수 없다.

**도메인 이상치는 입력 UI가 막고 파서는 막지 않는다**(2절). 일수의 0.25 배수 같은 검증이
여기 있어야 하는 이유가 그것이다.

## Acceptance criteria

- [x] 설정 탭에 조정 목록과 입력 폼이 있고, 입사일이 없으면 이 섹션이 보이지 않는다
- [x] 네 필드(`일수 / 발생일 / 소멸일 / 메모`)로 조정을 추가하면 즉시 저장되고 트레이 숫자가 바뀐다
- [x] 소멸일 기본값이 그 시점 살아 있는 발생분 중 가장 늦은 소멸일로 채워져 있다
- [x] 발생일 기본값이 입력한 날이고, 과거 날짜로 소급할 수 있다
- [x] 음수 일수를 넣을 수 있고, 소멸일이 지나면 그 음수 레코드가 잔여에서 사라진다
- [x] 조정을 수정·삭제할 수 있고 각 항목이 `id`로 식별된다
- [x] 계산이 만든 발생 레코드(월차·연차)를 화면에서 고칠 수 없다
- [x] 케이스 L을 화면에서 재현했다 — 초과 −3 상태에 `2025-01-01 / 2025-12-31 / +5`를 넣으면 잔여가 2가 된다
- [x] 일수·날짜 입력의 도메인 검증이 이 폼에 있다(파서에 넣지 않는다)

## Answer

조정을 **판정과 화면 둘로 갈랐다.** 판정(`packages/core/src/adjustment-input.ts`의
`validateAdjustmentDraft`, `balance.ts`의 `latestLivingExpiry`)은 코어에, 화면
(`apps/desktop/src/renderer/src/AdjustmentsSection.tsx`)은 설정 탭 안에 뒀다.

- **네 필드가 그대로 폼이다** — `일수 / 발생일 / 소멸일 / 메모`. 발생일 기본값은 조회일,
  소멸일 기본값은 `latestLivingExpiry`가 낸 "그 시점 살아 있는 발생분 중 가장 늦은
  소멸일"이다. `isValidOn`을 쓰므로 **아직 발생하지 않은 레코드는 세지 않는다** — 미래
  예정 때문에 만들어진 내년 발생분이 기본값을 밀면 이월이 1년 더 살아버린다.
- **살아 있는 발생분이 없으면 소멸일을 비워둔다.** 규칙이 날짜를 지어내지 않는다 —
  이월 사용기한은 회사마다 다르고, 정하면 조용히 틀린다. 대신 빈 칸은 검증이 막는다.
- **판정은 걸린 필드를 한 번에 전부 돌려준다.** 하나씩 알려주면 네 필드짜리 폼에서
  저장을 네 번 눌러야 한다.
- **커밋은 조정 배열 통째로다.** 추가는 뒤에 덧붙이고 수정은 `id` 자리에서 갈아끼우며
  삭제는 걸러낸다. 커밋 하나가 저장·재계산·트레이 갱신을 전부 태운다(19·21번).
- **`useCommit` 훅을 뺐다** — 설정 저장과 조정 저장이 진행 중 잠금·실패 문구·오류
  접두 걷어내기를 같은 모양으로 두 번 쓰고 있었다.
- **`iso-date.ts`를 뺐다** — 파서의 `requireIsoDate`와 입력 판정이 같은 "YYYY-MM-DD이면서
  실재하는 날짜"를 봐야 한다. 형식 검사와 `overflow: "reject"`가 한 자리에 있다.

### 케이스 L을 화면에서 재현했다

임시 하네스(렌더러를 Vite로 띄우고 `window.yeoncha`를 코어 계산으로 채운 것)로 실제
`App` → `SettingsTab` → `AdjustmentsSection`을 브라우저에 올려 확인했다. 하네스는 확인
뒤 지웠으므로 코드에 남아 있지 않다.

| 조작 | 화면 |
| --- | --- |
| 시작(K 데이터, 조회일 2025-11-05) | 잔여 **−3일** |
| `조정 추가` | 발생일 `2025-11-05`, 소멸일 `2025-12-31`이 채워져 있다 |
| 일수 `0.3`으로 추가 | `일수는 0.25 단위로 넣어주세요`, 커밋 없음(잔여 그대로) |
| 소멸일을 발생일보다 이르게 | `소멸일이 발생일보다 이릅니다` |
| `5 / 2025-01-01 / 2025-12-31 / 이월` 추가 | 잔여 **2일** — **케이스 L** |
| 그 레코드를 `6`으로 수정 | 잔여 3일 |
| 음수 `−2`(소멸일 2024-12-31, 이미 지남) 추가 | 잔여 그대로 — 소멸한 음수는 빠진다 |
| 같은 레코드의 소멸일을 2025-12-31로 수정 | 잔여 1일 — 살아난 음수가 깎는다 |
| 삭제 | 잔여 **−3일**로 복귀 |

## Comments

- **코어 공개 API가 다섯에서 일곱으로 늘었다.** 스펙 1절의 "코어가 내보내는 이름은
  다섯 개다"와 부딪히는 선택이고, 의식적으로 골랐다. 같은 절의 경계 표가 셸에 대해
  **"알면 안 되는 것: 연차 규칙, 표기 규칙"** 이라고 적고 있고, "무엇이 올바른 데이터인가는
  코어가 쥔다"도 같은 절이다. `0.25` 배수(3.9절)와 소멸일 경계(3.3절)는 둘 다 연차
  규칙이므로 셸에 두면 그 표를 어긴다. 티켓 AC의 "이 폼에 있다"는 **파서와의 대비**
  (파이프라인 위치)로 읽었고, 어느 패키지인가로 읽지 않았다. 덕분에 판정이 테스트를
  받는다 — 셸에는 러너가 없다(21번과 같은 판단).
- **테스트는 계산 seam 안에 뒀다.** `latestLivingExpiry`는 `balance.test.ts`에 있고,
  `adjustment-input.test.ts`만 새 파일이다. 네 번째 seam을 연 것이 아니라 코어가 이미
  쥔 도메인 규칙을 같은 방식(표 기반·순수 함수)으로 고정한 것으로 본다.
- **`0일`을 막지 않는다.** 처음에는 막았다가 뺐다 — 스펙에도 티켓에도 없는 규칙이고,
  0은 0.25의 배수라 명시된 검증도 통과한다. 잔여를 바꾸지 않는 레코드가 목록에 남을
  뿐이며, 그것을 지우는 방법은 삭제다.
- **목록에 `소멸` 표시를 넣지 않았다.** 만들었다가 뺐다 — 스펙 5.7절이 "소멸을 알아채는
  경로는 둘뿐이다"(요약 탭 D-day, 이력 달력 밑줄)라고 못 박았고, 세 번째 경로를 여기서
  여는 것은 이 티켓의 몫이 아니다. 행에 소멸일이 그대로 적혀 있다.
- **목록은 넣은 순서 그대로다.** 배정 순서(3.4절)와 다르다 — 저장 순서는 그 정렬의
  **마지막** 키이므로 소멸일이 다른 조정 둘이면 두 순서가 갈린다. 소멸 임박 순 리스트는
  요약 탭(24번)의 몫이다.
- **24번이 쓸 진입점은 아직 없다.** 5.1절의 "`조정을 추가` 링크가 설정 탭으로 점프하며
  조정 폼을 열어둔 채로 넘긴다"는 폼 열림이 `AdjustmentsSection` 안의 로컬 상태라
  prop 하나가 더 필요하다. 24번에서 붙인다.
- **셸에는 여전히 자동 테스트가 없다**(스펙 Testing Decisions). 화면 재현은 위 표대로
  임시 하네스로 눈으로 확인한 것이고, 회귀를 잡아주지 않는다.
