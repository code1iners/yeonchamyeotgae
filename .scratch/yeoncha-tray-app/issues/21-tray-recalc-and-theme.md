# 21. 트레이 재계산과 테마 추종

Type: task
Status: resolved
Blocked by: 19

## What to build

앱을 며칠 켜둬도, 노트북 뚜껑을 덮었다 열어도, 시스템 시각이나 테마가 바뀌어도 트레이 숫자가
맞는 상태.

**잔여는 날짜가 바뀌면 실제로 변한다**([스펙 4.5절](../spec.md)) — 발생일(매월 개근, 1년+1일,
회계연도 1/1)과 소멸일이 모두 날짜 경계에 걸려 있고, 발생분이 소멸하면 그 발생분에 배정된
초과도 함께 사라진다. 자정을 넘겨도 그대로면 트레이가 틀린다.

**`setTimeout(24시간)` 반복은 틀린다** — 드리프트가 쌓이고, 절전 중에는 타이머가 멈추며,
시간대·서머타임 변경으로 자정 간격이 24시간이 아닐 수 있다. **다음 자정까지의 지연을 매번 새로
계산해 한 번씩 예약한다.** 타이머는 **KST 자정**에 건다.

**두 축을 섞지 마라**(6.2절). 재계산 트리거 셋은 **값이 바뀌는 것**이고
`nativeTheme.on('updated')`는 **같은 값을 다시 그리는 것**이다. macOS는 후자의 리스너가 필요 없다.

## Acceptance criteria

- [x] 데이터가 바뀔 때(휴가 기록·조정·설정) 즉시 재계산한다
- [x] 다음 KST 자정에 한 번 예약하고, 발화하면 재계산한 뒤 다시 다음 자정을 계산해 예약한다
- [x] 시스템 날짜를 넘겨 자정을 지나게 하면 트레이 숫자가 갱신되는 것을 확인했다
- [x] `powerMonitor`의 `resume`·`shutdown` 계열과 시스템 시각·시간대 변경에서 **무조건 다시 계산한다**(예약된 타이머가 이미 지나가 있다)
- [x] Windows에서 `nativeTheme.on('updated')`에 글리프·숫자를 다시 그린다. 이 리스너에 재계산을 넣지 않았다
- [x] macOS는 테마 리스너 없이 템플릿 이미지 한 장으로 라이트/다크가 해결된다
- [x] 절전 복귀 후 며칠 지난 값이 아니라 오늘 값이 뜨는 것을 확인했다

## Answer

두 축을 **파일 두 개로 갈랐다**. 값이 바뀌는 축은 `apps/desktop/src/main/recalc.ts`,
같은 값을 다시 그리는 축은 `tray.ts`의 `startThemeRedraw`이고, `index.ts`가 그 둘을 나란히
부르는 자리에서 축이 다르다는 것이 보인다.

- **`clock.ts`가 셸의 시계다** — `todayInSeoul()`을 `store.ts`에서 꺼내 여기로 옮기고
  `msUntilNextMidnight()`을 나란히 뒀다. 오늘을 만드는 함수와 자정을 계산하는 함수가 같은
  시간대 상수 하나를 본다(7.3절의 "셸에서 이 함수 하나가 만든다").
- **하루를 상수로 적지 않는다** — 다음 자정은 `now.add({ days: 1 }).startOfDay()`이고 지연은
  그 epoch 밀리초의 차다. `startOfDay()`가 "그 하루가 몇 시간인가"를 시간대에게 묻는 자리다.
- **모든 트리거가 `recalcNow` 하나로 모인다** — 다시 계산하고 다음 자정을 새로 예약한다.
  예약이 이미 지나갔는지를 트리거마다 따지지 않기 위해서다.
- **`index.ts`의 `publishState`가 상태가 화면에 닿는 유일한 통로**다. 커밋·자정·절전 복귀·
  시각 변경이 전부 이 하나를 타므로 트레이와 팝오버가 갈릴 자리가 없다.

### 시각 변경에는 이벤트가 없어서 감시를 하나 뒀다

`setTimeout`은 **단조 시계**로 잰다. 사용자가 시스템 날짜를 내일로 넘겨도 예약된 자정 타이머는
원래 남은 실시간만큼 그대로 기다리고, Electron `powerMonitor`에는 시각 변경 이벤트가 없다.
그래서 60초마다 **오늘이 바뀌었는지만 본다**(`PlainDate` 하나를 만들어 문자열 비교). 자정
타이머를 대체하는 것이 아니라 — 그쪽이 정확한 시점을 맡고 이쪽이 시계가 튀는 경우를 맡는다.

### `shutdown`은 구독하지 않았다

AC는 `resume`·`shutdown` 계열을 적었지만 구독한 것은 `resume`과 `unlock-screen` 둘이다.
`shutdown`은 시스템이 곧 꺼진다는 신호라 그 시점에 다시 계산해도 사용자가 볼 트레이가 없고,
AC가 괄호로 적은 근거("예약된 타이머가 이미 지나가 있다")도 그쪽에는 해당하지 않는다.
대신 그 근거가 그대로 해당하는 `unlock-screen`을 넣었다 — 잠들지 않은 데스크톱도 화면만 잠근
채로 며칠이 지날 수 있다. **판단이 갈릴 수 있는 자리라 여기 남긴다.**

### 실측 (Electron 44, macOS, 메인 프로세스 인스펙터에 CDP로 붙어 확인)

`Tray.prototype`의 `setTitle`/`setImage`/`setToolTip`과 전역 `setTimeout`을 감싸 호출과 예약
지연을 기록했다. 저장 파일은 `hireDate: 2026-05-28`(월차만 있는 근속 1년 미만)이라 **8/28에
월차 한 건이 더 발생해 잔여가 2 → 3으로 변한다.**

| 확인한 것 | 결과 |
| --- | --- |
| 부팅·resume 시 예약 | KST 14:15:21에 `35078381ms = 9.744h` → **정확히 다음 자정 00:00:00** |
| 자정 타이머 발화 | 23:59:30에 `29999ms` 예약 → 30초 뒤 **실제로 발화** → 트레이 `2` → **`3`**, 툴팁 `잔여 3일` |
| 발화 후 재예약 | 같은 자리에서 `86399996ms = 24.000h` → 다시 다음 자정 |
| 날짜 40일 점프(이벤트 없음) | +5초에 **트레이 변화 없음**(예약된 타이머는 단조 시계라 발화하지 않는다) → **63초 안에 감시가 잡아** `3` → **`4`**, 재예약 `23.977h` |
| `powerMonitor.emit('resume')` (40일 점프 직후) | **감시 60초를 기다리지 않고 즉시** `2` → **`4`** — 며칠 지난 값이 아니라 오늘 값이다 |
| `powerMonitor.emit('unlock-screen')` | 같은 경로로 재계산·재예약 |
| 데이터 변경 | 렌더러에서 휴가 기록 0.5일 커밋 → 즉시 `2` → **`1.5`**, 렌더러도 `STATE_CHANGED`를 받는다 |
| macOS 테마 | `nativeTheme.listenerCount('updated') === 0`, `emit('updated')`에 **트레이 호출 0건** |
| 테마 재그리기(플랫폼 가드만 임시로 풀고 확인) | 앱 시계를 40일 앞으로 민 상태에서 `emit('updated')` → **`1.5`를 그대로 다시 그린다.** 재계산했다면 `3.5`가 나왔어야 한다 → **이 리스너에 재계산이 없다** |

`clock.ts`의 산술은 따로 다섯 경계에서 확인했다(14:10 / 23:59:59.999 / 정각 자정 / 월말 넘김 /
연말 넘김) — 전부 KST `00:00:00`에 정확히 떨어지고, 정각 자정에서 `0`이 아니라 `24h`가 나와
같은 자정을 두 번 잡지 않는다.

## Comments

- **시스템 시계 자체는 바꾸지 않았다.** 관리자 권한이 필요하고 사용자 기계의 시계를 건드리는
  일이라, 앱이 읽는 시각원(`Temporal.Now`)을 메인 프로세스에서 앞으로 미는 방식으로 확인했다.
  **`setTimeout`은 그대로 두었으므로 조건은 실제 시각 변경과 같다** — 예약된 타이머는 발화하지
  않고 오늘만 바뀐다. 위 표의 "+5초에 변화 없음"이 그것을 그대로 보여준다.
- **Electron 44의 V8에는 네이티브 `Temporal`이 있다.** `temporal-polyfill` 1.0.4는
  `const Temporal = NativeTemporal || 폴리필`이라 **메인 프로세스에서는 폴리필이 비켜서고
  네이티브가 쓰인다**(번들에서 확인). 동작은 같고 [ADR-0002](../../../docs/adr/0002-temporal-plaindate-for-dates.md)의
  결정도 그대로지만, "폴리필을 정식 의존성으로 둔다"는 문장이 실행 시점에는 이미 절반만
  사실이다. 되돌리기 비용의 비대칭이라는 ADR의 근거는 오히려 강해진다.
- **Windows 실물은 여전히 확인하지 못했다.** 위 표의 마지막 행은 플랫폼 가드만 임시로 풀어
  **리스너가 재계산 없이 같은 값을 다시 그린다는 것**을 확인한 것이고, 잉크 톤이 실제로 바뀌어
  그려지는 것(`drawGlyph`/`drawNumber`의 `tone`)은 Windows에서 눈으로 봐야 한다.
- **감시 주기 60초는 근거가 약한 값이다.** 하는 일이 `PlainDate` 하나를 만드는 것뿐이라 더
  짧게 잡아도 비용이 없고, 더 길게 잡아도 자정 정확도는 타이머가 지킨다. 사용자가 시계를
  고친 뒤 1분 안에 맞아지면 충분하다고 봤다.
- **셸에는 자동 테스트를 두지 않았다**(스펙 Testing Decisions — seam은 계산·표시·직렬화 셋이고
  전부 코어에 있다). `msUntilNextMidnight`은 순수 함수라 테스트가 어울리지만, 그것 하나 때문에
  `apps/desktop`에 러너를 들이는 것은 스펙이 정한 경계를 옮기는 결정이라 하지 않았다.
