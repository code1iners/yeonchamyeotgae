# 03. 연차 도메인 모델 확정

Type: grilling
Status: resolved
Blocked by: -

## Question

이 앱이 다루는 개념들의 이름과 관계를 확정하고 `CONTEXT.md` 용어집으로 남긴다. 이후 모든 티켓·스펙·코드가 이 용어를 쓴다.

결정해야 할 것:

1. **발생·사용·예정·잔여**의 정확한 정의. 특히 "잔여 = 발생 − (사용 + 예정)"이 확정 전제인데, 그렇다면 "오늘 기준 실제 남은 개수"를 가리키는 별도 용어가 필요한가, 아니면 그 개념 자체가 필요 없는가?
2. **연차 회기(leave year)**의 경계. 입사일 기준이면 입사기념일마다, 회계연도 기준이면 1/1마다 끊긴다. 이 회기를 무엇이라 부르고, 회기가 바뀔 때 무슨 일이 일어나는가?
3. **발생 레코드와 소멸의 짝**. 01번 조사에 따르면 발생분마다 소멸일이 다르다(특히 1년 미만 월차 11일). 발생을 하나의 숫자로 뭉갤 것인가, 소멸일을 가진 여러 건의 레코드로 볼 것인가?
4. **사용 단위**. 종일(1일)만인가, 반차(0.5)까지인가, 반반차(0.25)까지인가? 이 결정이 트레이 표기와 데이터 모델을 동시에 흔든다.
5. **사용 이력 레코드의 모양**. 연속된 3일 휴가는 레코드 1건인가 3건인가? 날짜·단위·메모 외에 필요한 필드가 있는가?
6. **수동 오버라이드**의 위치. 회사 규정이 법정과 다를 때 사용자가 무엇을 덮어쓰는가 — 발생 총량인가, 회기별 부여일수인가, 개별 발생 레코드인가?

## 참고

- [01번 티켓](01-labor-law-accrual-rules.md)의 법정 규칙 조사 결과가 이 모델의 제약 조건이다.
- `domain-modeling` Skill을 적용하고, 결론은 저장소 루트 `CONTEXT.md`에 기록한다. `CONTEXT.md`는 용어집이며 구현 세부는 넣지 않는다.

## Answer

용어집은 저장소 루트 [`CONTEXT.md`](../../../CONTEXT.md)에 기록했다. 아래는 그 결론에 이르게 한 결정과 근거다.

### 0. 법 해석 교정 — "1년+1일에 26일"은 동시 보유가 아니다

[01번 티켓](01-labor-law-accrual-rules.md)이 "입사 1년 + 1일 시점의 누적 발생량은 26일"이라고 적었는데, 제60조 제7항 괄호(2020-03-31 개정)상 월차의 사용 기한은 **최초 1년의 근로가 끝날 때까지**이고 15일은 **그 직후**에 발생한다.

입사 2024-01-01 기준:

| 시점 | 월차 | 연차 | 동시 보유 |
|---|---|---|---|
| 2024-12-01 | 11일 | 0 | 11 |
| 2024-12-31 (최초 1년 종료) | 11일 → 소멸 | 0 | 11 |
| 2025-01-01 | 0 | 15일 발생 | **15** |

**26이 잔여로 뜨는 순간은 없다.** 26은 "입사 후 2년간 총 발생량"이다.

다만 **회계연도 기준에서는 실제로 겹친다**. 2024-07-01 입사자는 월차가 2025-06-30까지 살고 비례분 7.5일이 2025-12-31까지 사는데, 2025년 상반기에는 두 종류가 동시에 유효하다. 이것이 아래 2번의 근거다.

### 1. 잔여 공식과 소멸

확정 전제 `잔여 = 발생 − (사용 + 예정)`에 소멸 항이 없었다. **"발생"을 조회 시점에 유효한(아직 소멸하지 않은) 발생분의 합으로 정의**해서 공식을 3항으로 유지한다. 소멸분은 애초에 발생에 들어가지 않는다.

기각한 대안: `잔여 = 발생 − 사용 − 예정 − 소멸`. 소멸은 1년에 한 번 뭉텅이로 일어나는 사건이라, 매일 보는 공식에 상주시킬 값이 없다.

**소멸일 산정 규칙은 둘이다.**

| | 근거 | 소멸일 |
|---|---|---|
| 월차 | 제60조 제2항 + 제7항 괄호 | 최초 1년의 근로가 끝나는 날. 11건이 한꺼번에 |
| 연차 | 제60조 제1항·제4항 + 제7항 | 각 발생일 + 1년 |

**앱이 판단할 수 없는 경계** — 전부 무시한다:
- 사용자 귀책 미사용(제7항 단서) → 법적으로 소멸하지 않지만 앱은 알 수 없다
- 출근율 80% 미달 → 소멸이 아니라 **미발생**. 01번의 100% 출근 가정이 덮는다
- 사용 촉진 미실시(제61조) → 휴가는 소멸하되 미사용수당 청구권이 남는다. 앱은 "쓸 수 있는 연차"만 센다

**소멸의 노출 수준**: 발생 이력에 소멸일과 소멸 여부가 보이는 선까지. **OS 알림은 만들지 않는다** — 알림 권한과 백그라운드 스케줄링을 끌고 들어오고, "진짜 단순한 앱" 전제와 맞지 않는다. 지도의 Out of scope로 옮겼다.

**이월 정책**: 이월을 자동 규칙으로 만들지 않는다. 이월은 "회사가 법정보다 더 준다"의 한 사례일 뿐이고, 사규 추가분·포상 휴가와 성격이 같다. 셋 다 **조정 레코드**로 표현한다(아래 7번). 근거: 이월 규칙은 법정이 아니라 사규라 변종이 많고(한도, 사용기한, 조건), 자동화하면 설정이 서너 개 늘고도 다 못 담는다. 이월은 1년에 한 번이라 손으로 넣는 비용이 낮다. 자동화는 나중에 켤 수 있다.

**남는 구멍과 완화책**: 사용자가 이월 넣기를 까먹으면 잔여가 실제보다 적게 보인다. 발생 이력에 소멸일이 보이는 것으로 타이밍을 알린다(그래서 위의 노출 수준이 (A)가 아니라 (B)여야 했다).

### 2. 발생의 구조 — 숫자가 아니라 레코드

발생은 **소멸일을 가진 레코드 여러 건**이다. 하나의 숫자로 뭉개지 않는다.

근거: 회계연도 기준에서 월차와 연차가 서로 다른 소멸일을 가진 채 동시에 유효한 구간이 생긴다(위 0번). 숫자 하나로는 "이 중 어느 게 6월에 소멸하는지" 표현할 수 없다. 뭉갠 숫자는 입사일 기준에서만 우연히 맞고 회계연도 기준에서 조용히 틀린다.

**휴가 기록은 발생 레코드를 참조하지 않는다.** 차감은 저장하는 값이 아니라 조회 시점에 계산한다. 그래야 차감 순서 규칙([04번](04-accrual-rule-spec.md))이 바뀌어도 과거 데이터를 고칠 일이 없다.

### 3. 사용 단위 — 반반차(0.25)까지

종일 1 / 반차 0.5 / 반반차 0.25.

저장은 열거형이 아니라 **소수 일수(number)** 로 둔다. 나중에 다른 단위를 열 때 마이그레이션이 필요 없다.

**파급**: 잔여 최대 표기가 `12.75` — 다섯 글자다. Windows 트레이는 이걸 작은 아이콘 이미지에 그려야 하므로 [06번](06-tray-display-spec.md)에서 "트레이는 절사, 팝오버만 정확히"가 유력해진다.

### 4. 사용과 예정 — 한 종류의 두 상태

같은 휴가 기록이고 **날짜에서 파생**된다. 오늘 이전이면 사용, 이후면 예정. 사용자가 상태를 지정할 수 없다.

기각한 대안: 사용자가 "예정 → 사용"을 확정하는 방식. 확정을 안 누른 과거 예정, 즉 **썩은 상태**가 반드시 생기고 그때 잔여가 조용히 틀린다.

**따라 나오는 결론**: 등록한 휴가를 안 쓰게 되면 상태 변경이 아니라 **삭제**다. [07번](07-popover-ui-spec.md)의 "예정일이 지나면 자동으로 사용됨이 되는가"는 질문 자체가 사라졌다(항상 그렇다).

### 5. 휴가 기록의 모양 — 하루 1건

`date` / `days` / `note` 세 필드. 사흘 휴가는 세 건이다.

근거: 기간 레코드는 "월 종일 + 화 반차"를 표현할 방법이 없다. 일수를 기간에 어떻게 배분하는지가 미정의다. 하루 1건이면 잔여 계산이 단순 합산이고 항상 정확하다.

긴 휴가 등록의 번거로움은 UI가 "기간 선택 → 여러 건 생성"으로 흡수한다([07번](07-popover-ui-spec.md)). 그건 표시 문제지 모델 문제가 아니다.

오전·오후 반차 구분은 잔여에 영향이 없으므로 `note`로 충분하다.

**연차 차감분만 기록한다.** 병가·경조사는 받지 않는다. 받는 순간 매 건마다 "이건 연차에서 까이나?"를 물어야 하고, 그 답이 회사 사규마다 달라 앱이 판정할 수 없다.

### 6. 연차 연도 — 1급이 아니라 파생

발생분을 묶어 보여줄 때 쓰는 표시용 이름이다. 저장되지 않는다. 진실은 각 발생 레코드의 소멸일이다.

근거: 회계연도 기준에서 회기가 어긋난다. 2024-07-01 입사자의 월차는 2025-06-30까지, 비례분은 2025-12-31까지 산다. "2025년 연차"라는 상자를 만들면 월차를 어느 상자에 넣을지 답이 없다. 소멸일만 들고 있으면 두 기준 다 문제없이 돌아간다.

이름은 "회기"가 아니라 **연차 연도**다. 입사일 기준의 "3년차"와 회계연도 기준의 "2025년도"를 둘 다 담아야 하는데 "회기"는 일상어에서 너무 멀다.

### 7. 사용자 조정 — 덮어쓰기가 아니라 덧붙이기

원래 선택지가 셋이었는데 앞선 결정이 둘을 지웠다.

| 선택지 | 상태 |
|---|---|
| 회기별 부여일수를 덮어쓴다 | 불가. 6번에서 회기를 파생으로 정했다. 붙일 곳이 없다 |
| 발생 총량 한 숫자를 덮어쓴다 | 불가. 소멸일이 사라진다. 2번과 충돌 |
| 발생 레코드를 건드린다 | 남은 하나 |

**계산이 만든 발생 레코드는 사용자가 고칠 수 없다.** 사용자는 `source: 'adjustment'`인 레코드를 **더한다**. 음수도 된다.

```
법정 발생   15
조정        -3
──────────────
             12
```

근거: 고쳐쓰기 방식은 계산 결과와 사람 입력이 같은 자리에 섞인다. 입사일이나 기준방식을 나중에 고쳐 재계산하면 사용자가 손으로 넣은 값이 조용히 덮어써진다. 이를 막으려면 "재계산할 때 사용자가 고친 건 건드리지 마라"는 규칙과 "고친 값인지 구분하는 방법"을 따로 만들어야 한다. **덧붙이기는 그 규칙이 아예 필요 없다. 두 줄을 더할 뿐이다.**

덤으로 "왜 12지?"가 이력에 그대로 남는다.

**사용자가 보는 화면은 두 방식이 같다.** 버튼 하나, 입력창 하나. 차이는 저장 방식뿐이므로 이 결정이 UI를 복잡하게 만들지 않는다.

### 8. 용어표

| 한국어 | 영문 | 비고 |
|---|---|---|
| 발생 | `grant` | 소멸일을 가진 레코드 1건 |
| ├ 월차 | `source: 'monthly'` | |
| ├ 연차(좁은 뜻) | `source: 'annual'` | |
| └ 조정 | `source: 'adjustment'` | 음수 가능 |
| 소멸일 | `expiryDate` | |
| 소멸 | `expired` | |
| 휴가 기록(한 건) | `entry` | `date` / `days` / `note` |
| 휴가 이력(모음) | `history` | |
| 사용 | `used` | 파생 |
| 예정 | `planned` | 파생 |
| 잔여 | `balance` | |
| 연차 연도 | `leaveYear` | 파생 |
| 기준방식 | `grantBasis` | `'hireDate'` / `'fiscalYear'` |
| 입사일 | `hireDate` | |

**이름 규칙: 시각 없는 날짜는 `~Date`로 끝낸다.** `~At`은 관례상 시각까지 있는 값을 가리킨다(`createdAt`). 이 앱의 날짜에는 시각이 붙을 일이 없다. 이 규칙은 취향이 아니라 [09번](09-project-structure.md)의 날짜 라이브러리 선택(`Temporal.PlainDate` vs `Date`)에 직접 걸린다.

**기각한 이름**: `criteria`(복수형이고, 판정 조건이라는 뜻이 안 맞는다), `accrualBasis`(회계의 발생주의와 충돌), `expiredAt`(과거형인데 미래 날짜를 담는다), `history`를 한 건에 쓰는 것(미래 항목이 들어가고 단위가 안 맞는다), `leaveDay`(검토했으나 `entry`로 확정).

### 후속 영향

- [04번](04-accrual-rule-spec.md): 0번의 교정을 반영했다. 차감 순서 질문은 회계연도 기준에서 여전히 살아 있다.
- [06번](06-tray-display-spec.md): 사용 단위가 0.25로 확정되어 소수점 질문이 선명해졌다.
- [07번](07-popover-ui-spec.md): 예정/사용 자동 전환 질문이 사라졌다. "수동 오버라이드"는 "조정"으로 바뀌었다.
- 지도 Notes에 "진짜 단순한 앱" 전제를 추가했다.
- 지도 Out of scope에 "소멸 알림·사용 촉진"을 추가했다.
