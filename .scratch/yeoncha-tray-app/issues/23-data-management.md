# 23. 데이터 관리 — 내보내기·가져오기·읽기 실패 화면

Type: task
Status: resolved
Blocked by: 20

## What to build

내 데이터를 확인하고, 옮기고, 깨졌을 때 되찾는 경로 전부.

- `[파일 위치 열기]`와 **2칸 들여쓰기 저장**이 "직접 열어보고 싶다"는 요구를 채운다. 저장 경로를
  설정값으로 열지 않는다([스펙 2절](../spec.md)).
- **내보내기 파일 = 저장 파일이다.** 별도 포맷을 두지 않으므로 파서·검증이 한 벌이고 v1과 v2가
  같은 코드를 쓴다.
- **가져오기는 전체 교체**이며 직전에 백업을 남기고 화면에 **"지금 데이터가 대체됩니다"** 를
  명시한다. 병합은 기각했다 — 실제 용도 둘(기기 옮기기, v2 이관)이 모두 통째로 옮기는 것이다.
- **읽기 실패 화면은 탭이 아니다**(5.5절). **팝오버 전체를 차지**하고 버튼 둘
  (`[백업에서 복구]` / `[파일 위치 열기]`)을 갖는다. **미래 버전일 때는 버튼 없이 안내만** 띄운다 —
  그 백업도 신버전이 남긴 것이다.
- **입사일을 바꿀 때** "새 입사일 이전의 휴가 기록과 조정 레코드를 지울까요?"를 묻고 사용자가
  고른다. 삭제 직전에 백업이 남는다. **거절할 수 있어야 한다** — 그래서 파서가 "입사일 이전 휴가
  기록"을 거부하지 않는다(16번).

## Acceptance criteria

- [x] 설정 탭에 `[파일 위치 열기]`가 있고 OS 파일 관리자에서 해당 폴더가 열린다
- [x] 저장 파일이 2칸 들여쓰기로 사람이 읽을 수 있게 쓰인다
- [x] 내보내기 산출물이 저장 파일과 **같은 포맷**이고, 그 파일을 그대로 가져올 수 있다
- [x] 가져오기가 전체 교체이고, 실행 전에 "지금 데이터가 대체됩니다"가 화면에 뜨며, 직전에 `data.json.bak`이 남는다
- [x] `invalid-json` / `schema-mismatch`에서 팝오버 전체가 오류 화면이 되고 버튼 둘이 뜬다. 고를 때까지 파일에 쓰지 않는다
- [x] `[백업에서 복구]`가 `data.json.bak`을 복원하고 정상 화면으로 돌아온다
- [x] `future-version`에서는 버튼 없이 "앱을 업데이트하세요" 안내만 뜬다
- [x] 입사일 변경 시 이전 기록 삭제 여부를 묻고, **거절하면 기록이 그대로 남으며 앱이 그 파일을 정상적으로 읽는다**
- [x] 삭제를 수락하면 삭제 직전에 백업이 남는다

## Answer

**저장 파일 하나를 두고 하는 일 넷**으로 구현했다 — 열어보기 · 내보내기 · 가져오기 · 되찾기.
포맷이 하나이므로 파서·검증이 한 벌이고, 넷이 전부 같은 `parse`를 지난다(2절).

- **코어에 `splitRecordsByHireDate` 하나를 뒀다**(`packages/core/src/hire-date-change.ts`).
  **지우지 않고 가르기만 한다** — 묻는 화면에는 지울 것의 수가, 거절한 쪽에는 원본 그대로가
  필요해서 양쪽을 한 번에 낸다. 조정은 **발생일**로 가른다(소멸일로 가르면 입사 전에 생긴
  이월분이 새 발생분 옆에 살아남아 잔여를 부풀린다). 입사일 당일은 남긴다 — 소멸일 경계와
  같은 셈법이다(3.3절).
- **내보내기는 저장 파일 원문 복사다.** 다시 직렬화하지 않으므로 별도 포맷이 생길 자리가 없고
  바이트가 같다. 여기만 원자적으로 쓰지 않는다 — 덮을 옛 파일이 없고, 사용자가 고른 폴더에
  `.tmp` 잔여물을 남기지 않는 편이 낫다.
- **백업을 남기는 자리 둘이 각자 통로를 갖는다** — `data:import`와 `data:drop-before-hire-date`.
  처음엔 `commit`에 `backupFirst` 스위치를 뒀다가 뺐다. 스위치는 어느 호출자든 켤 수 있어
  "파괴적 조작 직전에만"(2절)을 **주석만이** 지킨다. 통로를 나누면 타입이 지킨다.
- **읽기 실패 화면은 탭 구조 자체를 그리지 않는다**(`UnreadableScreen.tsx`, 5.5절). 온보딩과
  뭉뚱그리면 화면이 거짓말을 한다 — 입사일은 있는데 파일이 깨진 것이라 `입사일을 넣으면…`이
  사실이 아니다. `future-version`에만 버튼이 없다.
- **대화상자가 열려 있는 동안 팝오버를 붙잡는다**(`withPopoverHeld`). 그러지 않으면 대화상자가
  뜨는 순간 blur로 닫혀 **파일을 고른 뒤 결과를 보여줄 화면이 사라진다.** 중첩 대비로 불리언이
  아니라 카운터다.
- **온보딩에는 `[데이터 가져오기]` 하나만 남겼다.** 5.4절의 축소 지시와 사용자 스토리 45(새
  기기에서 처음부터 넣지 않는다)가 부딪히는 자리다 — 나머지 둘은 저장 파일이 없어 눌러도
  실패하므로 감췄고, 가져오기는 그 시점이 정확히 그 기능의 용도라 남겼다.

22번과 같은 방식(Vite로 렌더러를 띄우고 `window.yeoncha`를 메모리 상태로 채운 것)으로 실제

## Comments

- **스펙 5.4절과 어긋난 자리가 하나 있다.** "온보딩이 말해야 하는 것은 한 줄이다"는 축소
  지시인데 온보딩에 `[데이터 가져오기]` 버튼을 남겼다. 문자 그대로 지키면 새 기기 사용자는
  **가짜 입사일을 저장해 파일을 만든 뒤 가져와 덮어써야** 하고, 그것이 사용자 스토리 45가
  없애려던 경로다. 5.4절을 고칠지는 별도 판단이 필요하다.
- **확인하지 못한 경계 둘.** ① `[파일 위치 열기]`가 실제 Finder·탐색기 창을 여는 것 —
  `shell.showItemInFolder`(파일이 없으면 `shell.openPath(userData)`) 호출까지만 확인했다.
  ② 내보내기·가져오기의 **네이티브 파일 대화상자** 자체 — 화면 하네스에서는 stub이고 Electron
  하네스에서는 대화상자를 열지 않았다. 팝오버를 붙잡는 `withPopoverHeld`의 실효도 같이 미확인이다.
- **셸에는 여전히 자동 테스트가 없다**(스펙 Testing Decisions). 위 두 하네스는 눈으로 확인한
  것이고 회귀를 잡아주지 않는다. 코어의 `splitRecordsByHireDate`만 테스트가 고정한다.
- **`ParseErrorKind` → 문구 표가 두 벌이다** — 메인(`data-transfer.ts`, 가져올 파일이 깨졌을 때)과
  렌더러(`UnreadableScreen.tsx`, 저장 파일이 깨졌을 때). 같은 갈래지만 사용자가 할 일이 달라
  문장이 다르다(`다른 파일을 고르세요` 대 `앱을 업데이트하세요`). 네 번째 갈래가 생기면 두
  자리를 고쳐야 한다.
- **복구는 읽지 못하던 원본을 덮는다.** 사용자 스토리 47이 막는 것은 앱이 **조용히** 덮는
  것이고, 여기까지는 사용자가 오류 화면에서 직접 고른 길이다. 원본을 먼저 챙기고 싶으면 같은
  화면의 `[파일 위치 열기]`가 그 경로다. `data.json.broken` 같은 세 번째 파일은 만들지 않았다 —
  2절이 파일 이름을 둘로 못 박았다.
- **가져오기가 `schemaVersion`을 앱이 아는 값으로 정규화한다.** 낮은 버전 파일을 가져오면 다음
  저장부터 지금 버전이다. 마이그레이션 체인은 v1에 비어 있으므로(2절) 옮길 것이 없다.
