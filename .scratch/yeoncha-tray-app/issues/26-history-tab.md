# 26. 이력 탭 — 리스트와 달력

Type: task
Status: resolved
Blocked by: 25

## What to build

무엇을 언제 썼는지 훑는 화면. **뷰가 둘**이고 서로 전환된다.

| | 예정 | 사용 |
| --- | --- | --- |
| 리스트 | 맨 위 **예정 섹션**으로 분리 + 파란 `예정` 태그 | 연차 연도별 섹션 |
| 달력 | 파란 점 | 회색 점 |

- **달력이 두 몫을 한다** — 25번의 등록 시트이자 이력 탭의 두 번째 뷰다. 컴포넌트를 재사용한다.
- **연차 연도별로 접고 현재 연도만 펼친 채로 연다.** 기록 58건 규모에서 이것 없이는 스크롤이
  끝나지 않는다([스펙 5.3절](../spec.md)). **이력 리스트만 스크롤한다.**
- **연차 연도는 파생이다**(3.10절). 저장되지 않으며 각 발생 레코드의 소멸일에서 나온다.
- **소멸분은 이력 탭 맨 아래로 보낸다.** 평소에 볼 것이 아니다.
- **수정·삭제는 뷰마다 다르다.** 리스트는 행에 마우스를 올리면 오른쪽에 `수정 / 삭제`가 뜨고
  수정은 그 자리에서 날짜·단위를 고친다. 달력은 날짜를 누르면 아래에 그날의 기록이 펼쳐지고
  거기서 단위 변경(`1 / ½ / ¼`)과 삭제를 한다.
- **등록한 휴가를 안 쓰게 되면 상태 변경이 아니라 삭제다**(3.9절). 확정 방식(예정 → 사용)은
  **썩은 상태**를 반드시 만들고 그때 잔여가 조용히 틀린다. 사용·예정은 날짜에서 파생되며
  사용자가 지정할 수 없다.

이 탭이 **소멸을 알아채는 두 번째 경로**를 갖는다(5.7절) — 달력에서 소멸일 아래의 빨간 밑줄이며,
그날을 누르면 `2025년 이월 3일 소멸`이 뜬다.

## Acceptance criteria

- [x] 리스트 뷰에서 예정이 맨 위 별도 섹션에 모이고 파란 `예정` 태그가 붙는다
- [x] 사용이 연차 연도별 섹션으로 접혀 있고 현재 연도만 펼쳐진 채로 열린다
- [x] 소멸분이 맨 아래에 있고 평소 화면에서 눈에 띄지 않는다
- [x] 리스트와 달력 뷰를 전환할 수 있고, 달력은 25번의 컴포넌트를 재사용한다
- [x] 달력에 예정은 파란 점, 사용은 회색 점으로 뜬다
- [x] 달력에서 소멸일 아래에 빨간 밑줄이 뜨고, 그날을 누르면 무엇이 몇 개 소멸하는지 뜬다
- [x] 리스트 행 호버에 `수정 / 삭제`가 뜨고 수정이 그 자리에서 날짜·단위를 고친다
- [x] 달력에서 날짜를 누르면 그날의 기록이 아래에 펼쳐지고 단위 변경(`1 / ½ / ¼`)·삭제가 된다
- [x] 사용/예정을 손으로 전환하는 UI가 **없다** — 안 쓰게 된 예정은 삭제한다
- [x] 이력 리스트만 스크롤하고 팝오버 전체가 스크롤되지 않는다
- [x] 수정·삭제 직후 트레이 숫자와 요약 탭이 갱신된다

## Comments

- **연차 연도 파생은 코어의 새 모듈 `history.ts`다.** 기록이 속한 연도는 "그날 유효한
  발생분의 소멸일 중 가장 늦은 것"이 경계이고, 그 소멸일을 공유하는 발생분의 **가장 이른
  발생일의 연도**가 이름이다 — 입사일 기준(발생일의 해)과 회계연도 기준(그 해 1/1) 모두에서
  사람이 부르는 연도와 맞고, 월차 11건이 한 상자에 들어간다(3.10절). **배정 기반이 아니다** —
  배정 기반이면 기록을 하나 더할 때마다 과거 기록의 소속 연도가 재배정을 따라 움직인다.
  첫 발생 전의 기록은 날짜 자신의 연도로 둔다. vitest 7건이 고정한다.
- **소멸분은 `expiryLosses`가 만든다** — 소멸했고(remaining>0) 남은 발생분만, 소멸일·출처·메모
  별로 합산. 리스트 맨 아래 섹션과 달력의 빨간 밑줄이 **같은 목록**을 쓴다. 미래 소멸일에는
  밑줄을 긋지 않는다 — 임박 경고는 요약 탭 D-day(경로 1)의 몫이고, 이 탭은 "이미 사라진 것"을
  말한다(5.7절). 음수 조정은 손실을 상쇄하지 않는다 — 사라지는 것은 미사용 양수 잔량뿐이다.
- **조정의 메모는 값(발생일·소멸일·일수)으로 짝짓는다.** 발생 레코드에 조정 `id`가 남지
  않기 때문이고, 같은 값의 조정이 여럿이면 한 건씩 소비한다. 같은 값에 메모만 다른 두 조정은
  메모가 서로 바뀔 수 있으나 다른 표시 값이 전부 같아 화면에서 구별되지 않는 엣지다.
- **달력은 25번의 `CalendarGrid`를 그대로 재사용한다.** `DayDecoration`에 `dot`(예정 파랑 /
  사용 회색)과 `expired`(빨간 밑줄)를 넓혔고, 점·밑줄은 CSS ::after/::before라 격자 마크업이
  그대로다. 예정·사용 점의 경계는 렌더러가 다시 판정하지 않고 `groupHistory`의 예정 목록
  하나에서 나온다 — 리스트 섹션과 달력 점이 갈릴 수 없다.
- **수정·삭제는 뷰마다 다르다.** 리스트는 행 호버 → 그 자리 인라인 폼(날짜·단위)이고, 저장
  전에 하루 1건 불변식을 검사해 이미 기록이 있는 날짜를 막는다. 달력은 그날 패널에서 단위
  세그(`1 / ½ / ¼`)를 누르는 즉시 커밋한다. 리스트의 수정과 삭제는 커밋 통로(`useCommit`)를
  나눴다 — 한 통로면 다른 행의 삭제 실패 문구가 열려 있는 수정 폼 안에 뜬다.
- **코드 리뷰(Standards/Spec 두 축)에서 고친 것**: ① `compareDate`를 `iso-date.ts`로,
  3.3절 유효 판정 `isValidOn`을 balance.ts 공개로 올려 중복 구현을 지웠다. ② `UNITS`·
  `unitLabel`을 렌더러 공용 `units.ts`로 모아 등록 시트와 한 벌이 됐다. ③ 달력 점의 3.9절
  경계 재구현을 제거했다. ④ 삭제 실패 문구 위치를 분리했다.
- **확인 방법**: 코어 `history` vitest 7건 + `pnpm verify` 전체 통과. 실제 화면은 Playwright
  `_electron`으로 **격리 userData**(임시 시드 데이터)에서 빌드 산출물을 구동해 확인했다 —
  예정 섹션·파란 태그, 2026년만 펼침, 소멸 섹션 4줄(`2025년 이월 1.75일 소멸` 등), 리스트만
  스크롤, 달력 점 두 색과 8/20 빨간 밑줄, 그날 패널의 소멸 문구·단위 변경 즉시 커밋(반차→반반차
  반영 + 소멸 줄 0.5→0.75 갱신), 인라인 수정 저장(예정 날짜 이동)과 중복 날짜 차단 문구.
