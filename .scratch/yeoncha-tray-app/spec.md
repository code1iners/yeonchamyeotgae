# 연차몇개 (yeonchamyeotgae) v1 스펙

Status: ready-for-agent

한국 근로기준법상 연차 유급휴가를 추적하는 macOS·Windows 트레이 앱. 이 문서는
[wayfinder 지도](map.md)의 결정 티켓 열두 개를 종합한 것이며, 구현 에이전트가 **빈 저장소에서
스캐폴딩을 시작해 v1을 완성**할 수 있는 수준을 목표로 한다.

용어는 [`CONTEXT.md`](../../CONTEXT.md)가 유일한 출처다. **발생 / 월차 / 연차 / 조정 /
발생일 / 소멸일 / 소멸 / 휴가 기록 / 휴가 이력 / 사용 / 예정 / 반차 / 반반차 / 배정 / 초과 /
잔여 / 연차 연도 / 기준방식 / 입사일** — 이 문서와 코드가 전부 이 이름을 쓴다.

관련 ADR: [ADR-0001 셸 프레임워크로 Electron을 쓴다](../../docs/adr/0001-electron-as-shell-framework.md),
[ADR-0002 날짜는 Temporal.PlainDate로 다룬다](../../docs/adr/0002-temporal-plaindate-for-dates.md).

## Problem Statement

직장인은 자기 연차가 **지금 몇 개 남았는지** 모른다.

- 회사 그룹웨어는 숫자 하나만 보여주거나, 아예 없거나, 로그인해야 나온다. 매번 확인하러
  들어가는 비용 때문에 실제로는 확인하지 않는다.
- 연차는 **한 덩어리가 아니다.** 근속 1년 미만에는 매달 1일씩(**월차**), 1년이 지나면
  해마다 15일 이상(**연차**)이 생기고, 각각 소멸일이 다르다. 회계연도 기준 회사에서는 두
  종류가 동시에 살아 있는 구간이 생긴다. 사람이 머리로 셀 수 있는 계산이 아니다.
- **써야 하는 것을 모른 채 소멸시킨다.** 발생분은 1년만 살아 있고, 남은 것을 알아채는
  시점은 보통 이미 늦은 뒤다.
- 이미 등록해둔 **예정** 휴가를 잔여에서 빼고 세지 않으면, "남았다고 생각한 3일"이 실제로는
  이미 쓸 자리가 없다.

즉 필요한 것은 기능이 많은 휴가 관리 시스템이 아니라, **지금 몇 개인지가 눈에 항상 보이는
숫자 하나**다.

## Solution

트레이(macOS 메뉴 막대 / Windows 알림 영역)에 **잔여를 숫자로 상시 표시**하는 상주 앱.
아이콘도 단위 표기도 없다. 숫자 하나가 제품의 전부다.

숫자를 누르면 폭 380px 팝오버가 열리고 탭 세 개가 있다.

| 탭 | 하는 일 |
| --- | --- |
| **요약** | 잔여 · `발생 / 사용 / 예정 / 잔여` 4줄 표 · 살아 있는 발생분과 소멸 D-day · `[휴가 등록]` |
| **이력** | 휴가 이력을 리스트 또는 달력으로. 소멸분은 맨 아래 |
| **설정** | 입사일 · 기준방식 · 조정 |

데이터는 사용자 기기의 JSON 파일 하나에 있다. 서버도, 계정도, 동기화도 없다.
계산 엔진은 플랫폼을 모르는 순수 TypeScript 패키지로 분리해, v2 PWA가 같은 파일에서 같은
숫자를 낼 수 있게 한다.

**이 앱의 설계 원칙은 "진짜 단순한 앱"이다.** 기능 추가 제안은 *"이게 없으면 잔여가
틀리는가"* 를 통과해야 한다. 통과하지 못한 것들은 [Out of Scope](#out-of-scope)에 있다.

## User Stories

**온보딩과 설정**

1. 사용자로서 앱을 처음 실행하면 입사일을 넣는 화면이 바로 열리기를 원한다. 그래야 무엇부터 해야 하는지 찾지 않아도 된다.
2. 사용자로서 기준방식(입사일 기준 / 회계연도 기준)을 고르고 싶다. 그래야 우리 회사가 실제로 연차를 주는 방식과 앱의 계산이 맞는다.
3. 사용자로서 입사일을 넣기 전에는 요약·이력 탭이 잠겨 있기를 원한다. 그래야 계산할 수 없는 상태에서 빈 화면을 보고 헤매지 않는다.
4. 사용자로서 입사일을 넣기 전 트레이에 무언가가 떠 있기를 원한다. 그래야 앱이 살아 있고 누를 수 있다는 것을 안다.
5. 이직한 사용자로서 입사일을 새 값으로 바꾸고 싶다. 그래야 계속근로연수가 리셋된 상태로 계산된다.
6. 이직한 사용자로서 새 입사일 이전의 휴가 기록과 조정을 지울지 스스로 고르고 싶다. 그래야 전 직장 기록이 새 발생분을 잠식하지도, 내 의지와 무관하게 사라지지도 않는다.

**트레이**

7. 사용자로서 잔여가 트레이에 항상 떠 있기를 원한다. 그래야 앱을 열지 않고도 몇 개 남았는지 안다.
8. macOS 사용자로서 트레이에 `12.75`처럼 소수까지 그대로 보이기를 원한다. 그래야 정확한 값을 보러 팝오버를 열 필요가 없다.
9. Windows 사용자로서 트레이 숫자가 좁은 정사각 안에서도 읽히기를 원한다. 그래야 숫자가 뭉개져 쓸모없어지지 않는다.
10. Windows 사용자로서 트레이 숫자에 마우스를 올리면 정확한 값이 나오기를 원한다. 그래야 내림 때문에 잃은 소수를 확인할 수 있다.
11. 사용자로서 초과 사용 중일 때 트레이에 음수가 그대로 뜨기를 원한다. 그래야 넣지 않은 조정이 남아 있다는 것을 알아챈다.
12. 사용자로서 앱을 며칠 켜둔 채 자정을 넘겨도 숫자가 맞기를 원한다. 그래야 어제 값을 오늘 값으로 착각하지 않는다.
13. 노트북 사용자로서 뚜껑을 덮어뒀다 열었을 때 숫자가 갱신되기를 원한다. 그래야 며칠 지난 값을 보지 않는다.
14. 사용자로서 트레이 숫자를 누르면 팝오버가 열리기를 원한다. 그래야 창을 찾을 필요가 없다.
15. macOS 사용자로서 이 앱이 Dock을 차지하지 않기를 원한다. 그래야 상주 도구가 작업 공간을 어지럽히지 않는다.

**요약 탭**

16. 사용자로서 팝오버에서 잔여를 소수까지 보고 싶다. 그래야 Windows에서도 정확한 값을 볼 곳이 있다.
17. 사용자로서 `발생 / 사용 / 예정 / 잔여` 네 줄을 함께 보고 싶다. 그래야 회사 시스템의 숫자와 항목별로 대조할 수 있다.
18. 사용자로서 네 줄의 각 행이 무엇을 뜻하는지 한 줄로 설명되기를 원한다. 그래야 무엇과 대조하는 중인지 안다.
19. 사용자로서 내년 발생분에서 나가는 예정이 있으면 그 사실을 알고 싶다. 그래야 올해 잔여가 줄지 않은 이유를 안다.
20. 초과 사용 중인 사용자로서 그 원인과 조치 경로를 요약 화면에서 보고 싶다. 그래야 음수를 버그로 오해하지 않는다.
21. 사용자로서 살아 있는 발생분을 소멸 임박 순으로 보고 싶다. 그래야 무엇이 먼저 사라지는지 안다.
22. 사용자로서 각 발생분의 남은 양과 총량, 소멸일을 함께 보고 싶다. 그래야 어디까지 썼는지 안다.
23. 사용자로서 소멸이 60일 안으로 다가온 발생분이 눈에 띄기를 원한다. 그래야 쓸 계획을 세울 시간이 있다.

**휴가 이력**

24. 사용자로서 휴가 이력을 리스트로 보고 싶다. 그래야 무엇을 언제 썼는지 한 번에 훑는다.
25. 사용자로서 예정이 리스트 맨 위에 따로 모여 있기를 원한다. 그래야 앞으로 쓸 것과 이미 쓴 것을 섞어 보지 않는다.
26. 오래 쓴 사용자로서 이력이 연차 연도별로 접혀 있고 올해만 펼쳐지기를 원한다. 그래야 수십 건에서 스크롤이 끝나지 않는 일이 없다.
27. 사용자로서 휴가 이력을 달력으로도 보고 싶다. 그래야 어느 달에 몰아 썼는지가 한눈에 보인다.
28. 사용자로서 달력에서 소멸일이 표시되기를 원한다. 그래야 날짜 감각으로 소멸을 인지한다.
29. 사용자로서 소멸된 발생분이 평소 화면에 보이지 않기를 원한다. 그래야 지금 쓸 수 있는 것에 집중한다.

**휴가 등록과 수정**

30. 사용자로서 오늘 연차를 썼다는 것을 세 번의 조작으로 남기고 싶다. 그래야 기록하는 비용이 기록을 미루게 만들지 않는다.
31. 사용자로서 달력에서 날짜를 골라 등록하고 싶다. 그래야 과거·미래 날짜를 같은 방법으로 넣는다.
32. 사용자로서 사흘 휴가를 한 번에 넣고 싶다. 그래야 같은 입력을 세 번 반복하지 않는다.
33. 사용자로서 기간 등록에서 주말이 기본으로 빠지기를 원한다. 그래야 쓰지 않은 날이 차감되지 않는다.
34. 사용자로서 종일·반차·반반차를 고르고 싶다. 그래야 실제로 쓴 만큼만 차감된다.
35. 사용자로서 휴가에 메모를 달고 싶다. 그래야 오전 반차인지 오후 반차인지 같은 것을 남긴다.
36. 사용자로서 잘못 넣은 기록을 그 자리에서 고치고 싶다. 그래야 지우고 다시 넣지 않는다.
37. 사용자로서 쓰지 않게 된 예정을 삭제하고 싶다. 그래야 잔여가 실제와 맞는다.

**조정**

38. 사용자로서 이월분·사규 추가분·포상 휴가를 직접 넣고 싶다. 그래야 법정 계산과 회사 규정의 차이를 메운다.
39. 사용자로서 조정에 일수·발생일·소멸일·메모를 넣고 싶다. 그래야 회사마다 다른 이월 사용기한과 소급 적용을 표현할 수 있다.
40. 사용자로서 조정의 소멸일 기본값이 채워져 있기를 원한다. 그래야 흔한 경우에 날짜를 고민하지 않는다.
41. 사용자로서 음수 조정을 넣고 싶다. 그래야 회사가 법정보다 덜 주는 해를 표현할 수 있다.
42. 사용자로서 조정이 계산 결과를 덮어쓰지 않고 옆에 더해지기를 원한다. 그래야 "왜 12인지"가 이력에 남는다.

**데이터**

43. 사용자로서 데이터 파일의 위치를 열어보고 싶다. 그래야 내 데이터가 어디 있는지 확인하고 직접 백업할 수 있다.
44. 사용자로서 데이터를 파일로 내보내고 싶다. 그래야 기기를 옮기거나 나중에 웹 버전으로 이관할 수 있다.
45. 사용자로서 내보낸 파일을 가져올 수 있기를 원한다. 그래야 새 기기에서 처음부터 넣지 않는다.
46. 사용자로서 가져오기가 기존 데이터를 대체한다는 사실이 명시되기를 원한다. 그래야 모르고 덮어쓰지 않는다.
47. 사용자로서 데이터 파일이 깨졌을 때 앱이 조용히 덮어쓰지 않기를 원한다. 그래야 원본을 되찾을 여지가 남는다.
48. 사용자로서 최신 버전이 쓴 파일을 구버전 앱이 열었을 때 손대지 않기를 원한다. 그래야 모르는 필드가 조용히 날아가지 않는다.
49. 사용자로서 앱을 두 번 실행해도 하나만 뜨기를 원한다. 그래야 두 인스턴스가 같은 파일에 쓰지 않는다.

**설치와 릴리스**

50. 사용자로서 GitHub Release 페이지에서 내 OS용 파일 하나를 받고 싶다. 그래야 무엇을 받아야 할지 고민하지 않는다.
51. 사용자로서 실행할 때 뜨는 보안 경고를 통과하는 방법을 안내받고 싶다. 그래야 앱을 못 쓰고 포기하지 않는다.
52. 사용자로서 왜 그런 경고가 뜨는지 설명받고 싶다. 그래야 앱을 신뢰할지 스스로 판단한다.
53. 구현 에이전트로서 버전을 올리고 태그를 밀면 양 OS 바이너리가 하나의 릴리스로 올라가기를 원한다. 그래야 릴리스가 한 번의 의도로 끝난다.
54. 구현 에이전트로서 main에 푸시할 때마다 macOS·Windows 양쪽에서 검증이 돌기를 원한다. 그래야 Windows가 깨진 것을 릴리스를 자르는 순간에 알지 않는다.
55. 구현 에이전트로서 실패한 릴리스 워크플로를 다시 돌려도 같은 결과가 되기를 원한다. 그래야 재실행이 안전하다.

**v2 이관**

56. v2 PWA 구현자로서 계산 엔진을 수정 없이 가져다 쓰고 싶다. 그래야 규칙이 두 벌로 갈라져 두 앱이 다른 숫자를 내는 일이 없다.
57. v2 PWA 구현자로서 v1이 쓴 파일을 같은 파서로 읽고 싶다. 그래야 이관 과정에서 데이터가 조용히 틀리지 않는다.

## Implementation Decisions

### 1. 아키텍처 — 코어와 셸의 경계

패키지는 정확히 둘이다.

| | `@yeoncha/core` | `@yeoncha/desktop` |
| --- | --- | --- |
| 무엇 | 순수 TypeScript. 계산 · 표시 문자열 · 직렬화 | Electron 셸. 트레이 · 팝오버 · 파일 I/O |
| 의존성 | `temporal-polyfill` **하나뿐** | `electron`, `react`, `electron-vite`, `@yeoncha/core` |
| 알아도 되는 것 | 날짜, 도메인 규칙, 문자열 | 플랫폼, 파일 시스템, 창 |
| 알면 안 되는 것 | `process.platform`, 파일, 오늘 날짜 | 연차 규칙, 표기 규칙 |

**코어가 내보내는 이름은 다섯 개다.** [`CONTEXT.md`](../../CONTEXT.md)의 용어를 그대로 쓴다.

| 내보내기 | 하는 일 |
| --- | --- |
| `computeGrants` | 입사일 · 기준방식 · 조정 → **발생** 레코드 목록 |
| `allocate` | **휴가 기록**을 발생분에 **배정**하고 **초과**를 남긴다 |
| `computeBalance` | 조회일 기준 **잔여** + 발생분별 내역 |
| `formatTrayLabel` | 잔여 + 글리프 예산 → 트레이 문자열 |
| `parse` / `serialize` | 저장 파일의 구조 판정과 직렬화 |

**정확한 시그니처는 구현이 정한다.** 다만 아래 세 제약은 규칙이므로 어길 수 없다.

- **"오늘"은 인자다.** 코어가 내부에서 현재 날짜를 읽으면 4절의 재계산 트리거가 아무 효과가
  없고 검증 케이스 테이블을 표로 쓸 수 없다. 셸이 `Temporal.Now.plainDateISO('Asia/Seoul')`로
  만들어 넘긴다.
- **코어에 플랫폼 분기가 없다.** macOS와 Windows의 표기 차이는 `if`가 아니라
  `formatTrayLabel`의 **예산 파라미터**로 표현한다(4절).
- **코어는 I/O를 모르지만 포맷은 안다.** 파일 읽기·원자적 쓰기·백업 시점·오류 화면 순서는
  전부 셸이 짜고, "무엇이 올바른 데이터인가"는 코어가 쥔다. 통로는 플랫폼마다 다르지만
  (디스크 / IndexedDB) 판정은 v1과 v2가 같아야 한다.

**계산 엔진은 잔여 숫자 하나를 반환하지 않는다.** 발생 레코드마다
`발생일 / source / 일수 / 배정된 사용량 / 남은 양 / 소멸일 / 소멸 여부`를 담은 내역과, 여기에
**초과 일수**와 **미래 발생분에 배정된 예정**을 얹어 돌려준다. 배정은 어차피 한 번에 전부
계산되므로 트레이용·팝오버용으로 나눠 부르면 같은 일을 두 번 한다.

### 2. 저장 형식 — 단일 JSON 파일

저장되는 것은 셋뿐이다. **설정 / 휴가 기록 / 조정 레코드.** 발생과 배정은 계산 결과이므로
저장하지 않는다.

```json
{
  "schemaVersion": 1,
  "settings": { "hireDate": "2024-01-01", "grantBasis": "hireDate" },
  "entries": [
    { "id": "…", "date": "2025-03-10", "days": 1, "note": "" }
  ],
  "adjustments": [
    { "id": "…", "grantDate": "2025-01-01", "expiryDate": "2025-12-31", "days": 5, "note": "이월" }
  ]
}
```

- **키 이름은 `CONTEXT.md`의 영문 용어 그대로다.** 배열 이름이 `grants`가 아니라
  `adjustments`인 이유는 저장 파일에 **발생**이 없기 때문이다.
- **날짜는 `YYYY-MM-DD` 문자열.** 시각도 시간대도 없다. `Temporal.PlainDate`와 1:1이다.
- **일수는 숫자**다. 열거형이 아니다. 조정은 음수를 허용한다.
- **`id`는 `crypto.randomUUID()`.** Node와 브라우저 양쪽에 있어 v2에서 그대로 쓴다.
  휴가 기록에도 둔다 — 조정 레코드에는 자연키가 없고(발생일·소멸일·일수가 같은 포상 휴가 2건이
  가능하다), 한쪽만 `id`를 두면 UI가 키 종류로 분기한다.
- **`note`는 항상 존재하고 기본값은 빈 문자열.** 선택 필드보다 검증이 단순하다.

**위치는 Electron `app.getPath('userData')` 고정**이다(macOS
`~/Library/Application Support/<앱이름>/data.json`, Windows `%APPDATA%\<앱이름>\data.json`).
경로를 설정값으로 열지 않는다 — 열면 클라우드 동기화(Out of Scope)를 뒷문으로 끌고 들어온다.
직접 열어보고 싶은 요구는 설정 탭의 `[파일 위치 열기]`와 2칸 들여쓰기 저장으로 채운다.
앱은 **단일 인스턴스 락**을 건다.

**쓰기는 변경마다 즉시, 원자적으로 한다.** 임시 파일 → `fsync` → `rename`. 디바운스하지
않는다. 수십 KB를 하루 몇 번 쓰는데 지연을 두면 "앱이 죽으면 마지막 몇 초를 잃는다"만 새로
만든다.

**백업(`data.json.bak`)은 파괴적 조작 직전에만 남긴다.** 그 조작은 둘뿐이다 — 입사일 변경에
따른 기록 삭제, 가져오기 교체.

**읽기 실패는 이 규칙 하나가 결정한다: 읽지 못한 파일에는 쓰지 않는다.**

| 실패 | 동작 |
| --- | --- |
| **미래 버전** (`schemaVersion`이 앱보다 높음) | 읽기·쓰기 모두 중단, "앱을 업데이트하세요". **`[백업에서 복구]`를 띄우지 않는다** — 그 백업도 신버전이 남긴 것이다 |
| **깨진 파일** (JSON 파싱 실패 또는 구조 검증 실패) | 앱은 열되 오류 화면 + `[백업에서 복구]` / `[파일 위치 열기]`. 고를 때까지 파일에 쓰지 않는다 |
| **파일 없음** | 첫 실행. 입사일 미설정 상태 |

**파서는 구조만 본다.** 형식·타입·필수 필드·`entries`의 중복 `date`(하루 1건 불변식)까지다.
도메인 이상치는 통과시킨다 — 입사일 이전 휴가 기록은 8절의 삭제 제안을 거절하면 정상적으로
존재하고, 일수의 0.25 배수를 파서가 강제하면 "나중에 다른 단위를 열 수 있게" 열거형을 피한
의도가 죽고, 배정되지 않는 휴가는 이미 **초과**로 잔여에 음수로 뜬다. **도메인 이상치는
입력 UI가 막고 파서는 막지 않는다.**

`ParseError`는 셋을 구분한다 — `invalid-json` / `schema-mismatch` / `future-version`.
위 표가 셋을 다르게 다루기 때문이다.

**`schemaVersion`이 v1에서 실제로 하는 일은 마이그레이션 체인이 아니라 미래 버전 거부다.**
체인(1→2→3)의 자리는 만들지만 v1 시점에 비어 있다. 유일하게 실재하는 데이터 손실 경로는
"신버전이 필드를 늘려 쓴 파일을 구버전이 열어 모르는 필드를 조용히 날린 채 저장"이며, 이
검사는 SQLite를 썼어도 손으로 만들어야 했다(DB는 모르는 컬럼이 있는 파일을 그냥 열어준다).

**내보내기 파일 = 저장 파일이다.** 별도 포맷을 두지 않으므로 파서·검증·마이그레이션이 한
벌이고 v1과 v2가 같은 코드를 쓴다. **가져오기는 전체 교체**이며 직전에 백업을 남기고 화면에
"지금 데이터가 대체됩니다"를 명시한다. 병합은 기각했다 — 충돌 규칙이 여럿 필요한데 사용자가
그걸 판단할 근거가 화면에 없고, 실제 용도 둘(기기 옮기기, v2 이관)이 모두 통째로 옮기는 것이다.

**첫 실행에 파일을 만들지 않는다.** 입사일을 처음 저장할 때 파일이 생긴다. 즉
**파일 없음 = 입사일 없음**이며, `hireDate: null`인 파일을 미리 만들지 않는 이유는 그러면
타입이 `string | null`이 되어 **계산 엔진의 모든 순수 함수가 `null`을 받았을 때를 정의**해야
하기 때문이다. 파일을 안 만들면 코어에서 `hireDate`는 언제나 날짜다.

### 3. 연차 산정 규칙

이 절이 제품의 전부다. 검증 케이스는 [Testing Decisions](#testing-decisions)에 있다.

#### 3.1 잔여는 뺄셈이 아니라 배정으로 구한다

`잔여 = 발생 − (사용 + 예정)`을 **합계끼리의 뺄셈으로 구현하면 깨진다.** 휴가 기록에는 어느
발생분에서 나갔는지가 없다(`entry`는 `date` / `days` / `note` 뿐).

- **깨지는 지점 1** — 소멸일이 다른 발생분이 겹치면 **같은 입력에 잔여가 둘 나온다.**
  2024-07-01 입사·회계연도 기준으로 2025년 상반기에 월차 11일(2025-06-30 소멸)과 비례분
  7.5일(2025-12-31 소멸)이 동시에 유효하고, 여기서 5일을 쓰면 2025-07-01의 잔여가 월차에서
  뺐으면 7.5, 비례분에서 뺐으면 2.5다.
- **깨지는 지점 2** — 과거 휴가 기록이 영원히 누적된다. 소멸분을 발생에서만 빼고 사용에서는
  빼지 않아 **매년 1월에 이중 차감**이 난다. 2024-01-01 입사자가 2025년 10일·2026년 12일을
  쓰면 단순 뺄셈의 잔여가 2027-01-05에 −7이 된다.

그래서 **배정 모델**을 쓴다. 각 휴가 기록이 어느 발생 레코드에서 나갔는지를 정하고, 잔여는
유효한 레코드마다 남은 양을 구해 합산한다. **배정 결과는 저장하지 않고 조회 시점에 매번
계산한다** — 그래야 배정 규칙이 바뀌어도 과거 데이터를 고칠 일이 없다.

#### 3.2 발생 레코드 생성

발생일·소멸일 계산에서 월/년 더하기는 **월말 클램프**를 쓴다(2024-01-31 + 1개월 =
2024-02-29). `Temporal.PlainDate.add()`의 기본 동작(`constrain`)과 같아 예외 코드가 필요 없다.

규칙은 전부 일수가 아니라 **날짜 산술**(`+1년 −1일`)로 쓴다. "365일차 / 366일차"로 쓰면
윤년에서 어긋난다.

미래 발생분은 **`max(조회일, 가장 늦은 휴가 기록 날짜)`까지** 생성한다. 미래 **예정**이
미래 발생분에 배정되어야 하기 때문이다. 경계가 데이터에서 나오므로 설정값이 늘지 않는다.

**퇴사일 개념은 없다.** 근로관계가 계속된다고 가정한다.

**기준방식 `'hireDate'`(입사일 기준)**

| 종류 | 발생일 | 일수 | 소멸일 |
| --- | --- | --- | --- |
| **월차** 11건 | `입사일 + n개월` (n = 1..11) | 각 1 | 11건 전부 `입사일 + 1년 − 1일` |
| **연차** | `입사일 + k년` (k = 1, 2, 3, …) | `min(25, 15 + floor((k − 1) / 2))` | `발생일 + 1년 − 1일` |

월차의 마지막 소멸일과 연차 k=1의 발생일이 하루 차이로 맞물린다. **입사일 기준에서 두 종류가
겹치는 구간은 없다** — 누적 발생량 26일이 잔여로 뜨는 순간은 존재하지 않는다.

**기준방식 `'fiscalYear'`(회계연도 기준)** — 회계연도 개시일은 **1/1 고정**이고 설정값으로
열지 않는다.

| 종류 | 발생일 | 일수 | 소멸일 |
| --- | --- | --- | --- |
| **월차** 11건 | 입사일 기준과 **동일**(법정이므로 회계연도와 무관) | 각 1 | `입사일 + 1년 − 1일` |
| 첫 비례분 | 입사 후 첫 1/1 | `15 × m / 12` (m = 입사일부터 그 전해 12/31까지의 **완성 개월 수**) | 그 해 12/31 |
| **연차** | 매년 1/1 | `min(25, 15 + floor((k − 1) / 2))`, k = 그 1/1 시점의 **입사일 기준 완성 근속연수** | 그 해 12/31 |

- **비례부여에 절사가 필요 없다.** `15 / 12 = 1.25`이므로 m = 1..11의 결과가 전부 0.25 배수다
  (1.25, 2.5, 3.75, 5, 6.25, 7.5, 8.75, 10, 11.25, 12.5, 13.75). 사용 단위가 0.25까지 열려
  있으므로 전부 실제로 쓸 수 있는 값이고, **올림·내림·0.5 단위 설정값을 만들지 않는다.**
- **완성 개월 수**를 쓴다(달력상 걸친 달 수가 아니다). 2024-07-15 입사면 m = 5(2024-07-15 ~
  12-14) → 6.25일. **월차의 "1개월 개근"과 같은 셈법**이라 앱 안에서 개월을 세는 방법이 하나로
  유지된다. m = 0이면 레코드를 만들지 않는다. 회사가 달력 월 수로 준다면 차이는 조정으로 메운다.
- **가산휴가의 근속연수는 입사일에서만 나온다.** 2024-07-01 입사자의 2027-01-01 발생분은
  근속 2년 6개월 → 완성 2년 → 15일이며, 회계연도 순번(3번째)을 세지 않는다. 이 규칙이면
  일수 공식 하나를 두 기준방식이 그대로 공유하고, 회계연도 쪽은 **발생일만 1/1로 옮긴 것**이 된다.
- 이 방식은 입사일 기준보다 발생이 늦어질 수 있다. 퇴직 시 정산이 필요하지만 **앱은 퇴사를
  모르므로 정산하지 않는다.** 필요하면 조정으로 메운다.

#### 3.3 소멸의 경계

**`expiryDate`는 그 발생분을 쓸 수 있는 마지막 날이다.** 유효 조건은
`발생일 <= 대상일 <= expiryDate`. 화면에 뜨는 값이 "2025-12-31까지 쓸 수 있음"이어야 오해가
없다(소멸하는 날로 보고 `<`로 비교하면 사용자에게 2026-01-01을 보여주게 된다).

**소멸을 잔여 공식의 항으로 두지 않는다.** "발생"을 **조회 시점에 유효한(아직 소멸하지 않은)
발생분**으로 정의해서 공식을 3항으로 유지한다. 소멸분은 애초에 발생에 들어가지 않는다.

**앱이 판단할 수 없는 경계는 전부 무시한다** — 사용자 귀책 미사용(제60조 제7항 단서), 출근율
80% 미달(이건 소멸이 아니라 **미발생**이다), 사용 촉진 미실시(제61조).

#### 3.4 배정 규칙

1. 휴가 기록을 **날짜 오름차순**으로 처리한다.
2. 각 기록을 그 **휴가 날짜에 유효한 양수 발생 레코드**에 배정한다.
3. 후보가 여럿이면 **소멸 임박 순**으로 채운다.
4. 한 기록이 여러 레코드에 **쪼개져 배정될 수 있다**(0.25 단위이므로 자연스럽다).
5. 배정할 잔량이 모자라면 남은 일수는 **초과**로 간다.

**정렬 키**: `소멸일 ↑ → 발생일 ↑ → source(monthly → annual → adjustment) → 입력 순서`.
뒤쪽 키는 잔여 값을 바꾸지 않고 **내역 표시와 테스트를 결정론적으로** 만든다.

소멸 임박 순인 이유는 사용자 손실이 최소화되기 때문이다(3.1의 예에서 소멸 임박 순은 7.5,
소멸 늦은 순은 2.5로 5일 차이). 발생일 순(FIFO)은 거의 항상 같은 결과를 내지만, 조정의
소멸일은 사용자가 정하므로 **나중에 생긴 것이 먼저 소멸할 수 있고 그때 갈린다.**

#### 3.5 잔여 공식

```
잔여(조회일) = Σ (조회일에 유효한 양수 레코드의  일수 − 배정량)
             + Σ (조회일에 유효한 음수 조정 레코드의 일수)
             − (조회일에 아직 살아 있는 초과분)
```

`잔여 = 발생 − (사용 + 예정)`은 유지된다. 다만 **"예정"은 지금 살아 있는 발생분을 쓰는
예정만** 잔여에서 빠진다. 2025-12-01에 2025년분 5일이 남았고 2026-02월 휴가 3일을 등록하면,
그 3일은 2026-01-01 발생분에서 나가므로 오늘 잔여는 5다. **UI가 이를 인지시켜야 한다**(5절).

#### 3.6 초과 사용 — 잔여는 음수를 허용한다

배정 실패분을 잔여에서 뺀다. 음수가 뜨는 상황은 거의 전부 "사용자가 조정을 아직 안 넣었다"다.
**음수는 버그가 아니라 넣을 것이 남았다는 신호**이며, 트레이에 그대로 뜨는 것이 가장 강한
알림이다.

**초과분의 수명**: 초과 일수는 **그 휴가 날짜에 유효했던 발생 레코드들의 소멸일 중 가장 늦은
것**까지 살아 있다가 사라진다. 쉽게 말해 *초과는 그 연차 연도가 끝나면 없던 일이 된다.*
그 날짜에 유효한 레코드가 하나도 없었다면(발생 전 사용) 그 뒤 처음 생기는 발생분의 소멸일을
쓴다. 수명을 주지 않고 영구히 빼면 3.1의 누적 오차가 그대로 돌아온다.

기각한 대안: 잔여를 0에서 멈추기(초과를 놓친다), 잔여를 넘는 등록을 막기(조정을 나중에 넣는
정상 흐름을 막는다).

#### 3.7 조정 레코드

`source: 'adjustment'`는 **발생일과 소멸일을 모두 사용자가 넣는다.** 기본값은 발생일 =
입력한 날, 소멸일 = 그 시점 살아 있는 발생분 중 가장 늦은 소멸일.

- **소멸일이 입력인 이유**: 이월 사용기한이 회사마다 다르다(1년 더 / 6개월 / 무기한). 규칙이
  정하면 조용히 틀리고, 소멸시키지 않으면 이월분이 영원히 남아 매년 잔여를 부풀린다.
- **발생일이 입력인 이유**: 배정은 "휴가 날짜에 유효한 레코드"에만 하므로, 발생일이 입력한
  날로 고정되면 **과거의 초과를 조정으로 풀 수 없다.** 입력 필드 하나가 배정 규칙의 예외
  하나보다 싸다.

**음수 조정은 배정 대상이 아니라 합산 항이다.** 이미 마이너스이므로 사용을 배정할 수 없다.
소멸일이 지나면 음수 레코드도 사라지며, 이는 "그 해에만 덜 준다"를 정확히 표현한다.

**계산이 만든 발생 레코드는 사용자가 고칠 수 없다.** 조정은 덮어쓰기가 아니라 **덧붙이기**다.
고쳐쓰기 방식은 입사일이나 기준방식을 나중에 고쳐 재계산할 때 사용자 입력이 조용히 덮어써지고,
그걸 막으려면 "재계산할 때 사용자가 고친 건 건드리지 마라" + "고친 값인지 구분하는 방법"을
따로 만들어야 한다. 덧붙이기는 그 규칙이 아예 필요 없다. **이월·사규 추가분·포상 휴가가
전부 여기로 온다** — 이월을 자동 규칙으로 만들지 않는다(사규마다 변종이 많고 설정이 서너 개
늘고도 다 못 담는다. 1년에 한 번이라 손으로 넣는 비용이 낮다).

#### 3.8 출근율 80% 요건 — 100% 출근을 고정 가정한다

결근 입력 기능을 만들지 않는다. **이 가정은 스펙에 명시된 것이다.** 80%에 미달한 해는 사용자가
조정으로 깎는다. 결근일 입력은 소정근로일수 계산(휴일·공휴일 달력)과 "미발생 시 연 단위에서
월 단위로 되돌리기" 분기를 전부 끌고 온다.

#### 3.9 사용 단위와 휴가 기록의 모양

- **종일 1 / 반차 0.5 / 반반차 0.25.** 저장은 열거형이 아니라 **소수 일수**다(나중에 다른
  단위를 열 때 마이그레이션이 필요 없다).
- **휴가 기록은 하루 1건**이다. 사흘 휴가는 세 건이다. 기간 레코드는 "월 종일 + 화 반차"를
  표현할 방법이 없고 일수를 기간에 어떻게 배분하는지가 미정의다. 긴 휴가 등록의 번거로움은
  UI가 "기간 선택 → 여러 건 생성"으로 흡수한다(5절).
- **사용과 예정은 한 종류의 두 상태이고 날짜에서 파생된다.** 사용자가 상태를 지정할 수 없다.
  확정 방식(예정 → 사용)은 확정을 안 누른 과거 예정, 즉 **썩은 상태**를 반드시 만들고 그때
  잔여가 조용히 틀린다. **따라서 등록한 휴가를 안 쓰게 되면 상태 변경이 아니라 삭제다.**
- **연차 차감분만 기록한다.** 병가·경조사는 받지 않는다. 받는 순간 매 건마다 "이건 연차에서
  까이나?"를 물어야 하고 그 답이 사규마다 달라 앱이 판정할 수 없다.
- 오전·오후 반차 구분은 잔여에 영향이 없으므로 `note`로 충분하다.

#### 3.10 연차 연도는 파생이다

발생분을 묶어 보여줄 때 쓰는 표시용 이름이며 저장되지 않는다. 진실은 각 발생 레코드의
소멸일이다. 회계연도 기준에서는 그 구간 경계가 어긋나므로("2025년 연차" 상자를 만들면 2024-07-01
입사자의 월차를 어느 상자에 넣을지 답이 없다) 소멸일만 들고 있으면 두 기준방식이 다 돌아간다.

### 4. 트레이 표시

**트레이는 잔여를 숫자로만 상시 띄운다.** 아이콘도 단위 표기("일", "연차")도 없다 — Windows
예산이 두 글자뿐이라 아이콘이 들어갈 자리가 물리적으로 없고, macOS만 아이콘을 붙이면 비대칭이
정밀도를 넘어 "무엇을 보여주는 물건인가"까지 갈라진다.

| | macOS | Windows |
| --- | --- | --- |
| 경로 | `setTitle()` (네이티브 텍스트) | **정사각** canvas → `nativeImage` → `setImage()` |
| 표시 | 잔여 **그대로**: `12.75`, `-24.75`, `0` | 잔여의 **내림 정수**: `12`, `-25`, `0` |
| 정확한 값 | 트레이에 이미 있다 | 툴팁과 팝오버 |
| 입사일 미설정 | **가로 대시 하나**, 숫자 없음 | 같음 |
| 소멸 임박 | 아무것도 하지 않는다 | 같음 |

**툴팁은 양쪽 다 정확한 값을 갖는다** — `연차몇개 — 잔여 12.75일` 형태. Windows에서 트레이
숫자와 팝오버 숫자가 갈리는 유일한 경우이고, 그 간극을 메우는 게 툴팁의 존재 이유다.
입사일 미설정 상태의 툴팁은 `연차몇개 — 입사일을 입력하세요`다.

#### 4.1 Windows 정사각 제약은 사실이다

Win32 알림 영역 아이콘은 `SM_CXSMICON × SM_CYSMICON`, 정의상 정사각이다. Electron 메인테이너가
같은 사례(macOS 메뉴바 숫자 앱을 Windows로 옮기는 것)에 "알림 영역 아이콘은 정사각으로만
보이며 이는 Windows의 제약"이라고 답했고, 탈출구였던 taskbar toolbar(deskband)는 Windows 11에서
제거됐다.

**더 나쁜 사실**: `Tray.setImage`는 Windows에서 `GetHICON(SM_CXSMICON)`을 부르지만, `.ico`
**파일 경로**가 없으면 그 size 인자를 무시하고 원본 크기 그대로 HICON을 만든다. 우리 canvas
경로는 파일이 아니므로 **Electron이 대신 맞춰주는 것이 없고, 정사각 비트맵을 직접 그려
넘겨야 한다.**

**정사각 예산은 "편한 두 글자"다.** 프로토타입 실측 cap height(device px):

| 후보 | 16px (100%) | 20px | 24px | 32px |
| --- | --- | --- | --- | --- |
| `12.75` 그대로 | **3.3** (죽는다) | 4.4 | 5.5 | 7.4 |
| 두 글자 `12` | **9.0** | 11.9 | 14.8 | 18.3 |
| 세 글자 `-24` (최악) | **5.4** (빠듯하나 읽힌다) | 6.9 | 8.7 | 11.6 |

**한 줄일 때 병목은 높이가 아니라 폭이다.** 16px 정사각에 세로 여유는 남는데 글자 수가 늘면
폭이 먼저 막힌다. 두 줄 배치(`-24` 위 `.75`)는 값이 정확한 유일한 후보였지만 16px에서 두 줄
사이 여백이 사실상 0이라 붙어 보인다. 아이콘만 후보는 "항상 눈에 띄는 게 이 앱의 존재 이유"와
정면 충돌한다.

#### 4.2 내림(`Math.floor`)이다. 0 방향 절사(`Math.trunc`)가 아니다

| 잔여 | `Math.floor` | `Math.trunc` |
| --- | --- | --- |
| `12.75` | `12` | `12` |
| `-24.75` | `-25` | `-24` |
| `-0.25` | `-1` | **`0`** |

`trunc`는 `-0.25`를 `0`으로 보여줘 **초과 사용을 트레이에서 완전히 숨긴다.** 3.6절이 음수를
의도적으로 노출하기로 했으므로 그 결정을 무효화한다.

`floor`는 **표시값 ≤ 실제 잔여** 불변식을 부호와 무관하게 지키는 유일한 선택이다. 이 불변식이
있어서 사용자가 트레이 숫자를 "적어도 이만큼"으로 읽으면 틀리지 않는다. **이건 표기 취향이
아니라 계약이다.** 반올림은 양수에서도 이 불변식을 깨므로(`11.6` → `12`) 같은 이유로 기각.

대가는 `-0.25`가 `-1`로 보이는 것이다. 과장 방향이 "문제가 실제보다 심각해 보인다"는 안전한
쪽이고, 정확한 값은 툴팁과 팝오버에 있다.

#### 4.3 비대칭은 분기가 아니라 예산 파라미터다

코어에 `process.platform`이 들어가면 "브라우저·Node·웹뷰 어디서든 동작"이 깨지고 v2가 못
받는다. 셸에 `if (isMac)` 두 갈래 포매팅을 두면 규칙이 두 곳에 흩어진다. 그래서 코어가 순수
함수 하나를 내보낸다.

```
formatTrayLabel(balance: number, opts: { maxGlyphs: number }): string
```

- `maxGlyphs`가 잔여의 정확한 표기를 담을 수 있으면 그대로 돌려준다.
- 담지 못하면 **내림 정수**를 돌려준다.

**셸은 예산만 정한다** — macOS는 `Infinity`, Windows는 `3`(부호 한 글자 + 숫자 두 글자).
플랫폼 지식이 셸의 상수 두 개로 줄고, 규칙은 코어 한 곳에만 산다. v2 PWA는 자기 예산을 넣어
같은 함수를 쓴다. **렌더링(`setTitle` 대 정사각 canvas)은 문자열이 정해진 뒤의 문제이므로
코어가 알 필요가 없다.**

#### 4.4 경계 상태

| 상태 | 트레이 |
| --- | --- |
| 잔여 `0` | `0`. 특별 취급 없음 |
| 잔여 음수 | 부호 그대로 `-3`, 최악 `-25` |
| 입사일 미설정 | **가로 대시 하나**(6절), 숫자 없음. 클릭하면 설정 탭이 열린다 |
| 소멸 임박 | **아무것도 하지 않는다** |

음수의 반전 표시(검은 사각에 숫자 파냄)와 Windows 한정 빨강은 기각했다. 반전은 16px에서 파낸
획이 뭉개져 대비를 잃고 "반전 = 음수"를 학습해야 한다. 빨강은 macOS 템플릿 이미지가 알파만
쓰므로 라이트/다크 자동 대응을 포기해야 색이 생긴다.

#### 4.5 재계산 트리거

잔여는 날짜가 바뀌면 **실제로 변한다** — 발생일(매월 개근, 1년+1일, 회계연도 1/1)과 소멸일이
모두 날짜 경계에 걸려 있고, 발생분이 소멸하면 그 발생분에 배정된 초과도 함께 사라진다.
자정을 넘겨도 그대로면 트레이가 틀린다.

1. **데이터 변경** — 휴가 기록·조정·설정이 바뀔 때.
2. **로컬 자정** — **다음 자정까지의 지연을 매번 새로 계산해 한 번씩 예약한다.**
   `setTimeout(24시간)` 반복은 틀린다: 드리프트가 쌓이고, 절전 중에는 타이머가 멈추며,
   시간대·서머타임 변경으로 자정 간격이 24시간이 아닐 수 있다. 타이머는 **KST 자정**에 건다.
3. **절전 복귀와 시각 변경** — Electron `powerMonitor`의 `resume`·`shutdown` 계열과 시스템
   시각·시간대 변경. 며칠간 뚜껑을 덮어둔 노트북이 실제 사용 패턴이고, 그 경우 2번의 예약된
   타이머는 이미 지나가 있다. **복귀 시 무조건 다시 계산한다.**

계산이 순수 함수이므로 재계산은 싸다. "오늘"을 코어가 인자로 받는 것이 이 트리거들의 전제다.

#### 4.6 트레이 우클릭 — 종료

**v1 스펙이 이 결정을 누락했다 — 「의도적으로 남긴 구멍」이 아니다.** 4절 어디에도, 5절
팝오버 어디에도 「종료」라는 단어가 없었다. 논의되고 기각된 것이 아니라 범위를 잠글 때 빠진
것이고, 지금까지 사용자가 앱을 끄는 유일한 방법은 활성 상태 보기와 작업 관리자였다.

**트레이 우클릭 메뉴 하나 — 항목은 `[종료]`뿐이다.** 팝오버는 손대지 않는다. 좌클릭이 이미
여는 동작을 갖고 있어 `[열기]`는 같은 일을 하는 두 번째 경로일 뿐이다. 나중에 `설정` 같은
항목이 들어올 수는 있다 — 구조가 그것을 막지 않되, 지금 미리 자리를 만들어 두지도 않는다.

- **문구는 양 OS 모두 `종료`다.** macOS가 앱 이름을 붙이는 관례(`Quit AppName`)는 여러 앱의
  메뉴가 한 막대를 공유하는 애플리케이션 메뉴에서 온 것이고, 트레이 아이콘에서 나온 메뉴는 그
  맥락이 아니다. 사용자가 방금 그 아이콘을 눌러 연 메뉴라 무엇을 종료하는지 모호할 자리가
  없다. 플랫폼 분기를 만들지 않는 것이 6절이 트레이 글리프에서 한 것과 같은 태도다.
- **확인 대화상자를 띄우지 않는다.** 저장(`writeFileAtomic`)이 전부 동기라 `app.quit()`이
  쓰기 도중에 끼어들 수 없고, 종료로 잃을 것이 없다. 잃을 것이 없는 조작에 확인을 붙이면
  확인 대화상자가 의미를 잃는다 — 이 앱에서 확인을 묻는 자리는 파괴적인 둘(가져오기 교체,
  입사일 변경 시 기록 삭제)뿐이고 그 경계를 흐리지 않는다.
- **팝오버가 열려 있을 때 우클릭하면 팝오버가 닫히고 메뉴가 뜬다.** 종료 메뉴에는 끝난 뒤
  보여줄 결과가 없으니 열어 둘 이유가 없다(23번의 대화상자 붙잡음과 다른 이유가 여기 있다).
  **`blur` 숨김에 기대지 않는다.** `Tray.popUpContextMenu()`는 동기 호출이라 메뉴가 떠 있는
  동안 JS 이벤트 루프가 막혀 `blur` 콜백이 돌 기회가 없다 — 처음엔 "blur가 먼저 돈다"고
  가정했으나 실물 검증에서 뒤집혔다(팝오버가 메뉴 아래 그대로 남아 있었다). 그래서 `tray.ts`가
  `right-click`에서 `popUpContextMenu`를 부르기 **직전에** `onWillShowMenu` 콜백을 부르고,
  `index.ts`가 거기서 팝오버를 명시적으로 닫는다.
- **단축키를 주지 않는다.** 이 앱은 `app.dock.hide()`로 액세서리 앱이라 애플리케이션 메뉴
  막대 자체가 없다. `Cmd+Q`를 주려면 Dock을 되살려 메뉴를 만들거나(트레이 상주 앱 전제를
  깬다) `globalShortcut`으로 전역에서 가로채야 하는데(다른 앱의 종료를 훔친다), 둘 다 메뉴
  항목 하나 값을 못 한다.

**구현은 `tray.setContextMenu()`가 아니라 `right-click` 이벤트 + `popUpContextMenu(menu)`를
쓴다.** `setContextMenu`를 쓰면 Windows에서 좌클릭도 이 메뉴를 열어 팝오버 토글이 죽는다 —
이 변경의 유일한 실제 위험이고, macOS에서는 발현하지 않는다.

**메뉴를 만드는 코드는 `tray.ts` 안에 둔다.** 항목이 하나인 지금 파일을 나누면 함수 하나를
감싼 껍데기 파일이 생긴다. `tray.ts`는 이미 트레이라는 OS 표면 전부(이미지·툴팁·테마
재그리기·클릭)를 맡고 있어 메뉴가 그 안에 있는 것이 경계와 맞는다. **항목이 셋을 넘으면 그때
나눈다** — 미리 나눠두는 것은 준비처럼 보이지만 실제로는 어떤 항목이 올지 모르는 채로 모양을
먼저 정하는 것이다.

**`app.quit()`은 `index.ts`가 부른다.** `createTray`가 `{ onClick, onWillShowMenu, onQuit }`
옵션 객체로 콜백을 받는다. `tray.ts`는 `app`을 import하지 않는다 — 그리는 것과 클릭을 받는
것만 한다.
여기에 종료를 넣으면 "트레이가 앱을 끈다"가 되어 층이 섞이고, 앱의 수명 주기는 `index.ts`의
몫이며 실제로 `app.quit()`을 부르는 자리는 지금 거기 하나뿐이다.

### 5. 팝오버 UI

**탭 3개(요약 / 이력 / 설정), 폭 380px, 별도 창 없음.** `ui-design` Skill을 적용하고 실제
메뉴바 앱(runcat, Itsycal, Stats)의 기성 패턴을 우선한다. 시각 언어는 **시스템 네이티브,
장식 없음, 강조색은 시스템 블루 하나**다.

#### 5.1 요약 탭

- **잔여는 헤더 한 줄에 작게.** 큰 숫자로 반복하지 않는 이유는 트레이에 이미 있기 때문이다.
  다만 **소수를 그대로 쓴다**(`12.25일`). **반올림·절사 금지** — Windows에서는 이 값이 정확한
  잔여를 볼 수 있는 유일한 화면이다.
- **`발생 / 사용 / 예정 / 잔여` 4줄 표.** 각 행 오른쪽에 무엇인지 한 줄로 적는다
  (`발생 18 — 지금 살아 있는 발생분`). 목적이 회사 시스템 숫자와의 대조이므로 숫자만 있으면
  무엇과 대조하는지 알 수 없다. 초과가 있으면 그 위에 `초과` 행이 하나 더 붙는다.
- **각주 한 줄.** 4줄의 `예정`에는 **배정된 몫만** 적고, 표 아래에
  `등록한 예정은 4일이지만 1일은 내년 발생분에서 나갑니다 — 올해 잔여에 없습니다`를 둔다.
  **각주가 유일한 해답이다** — 등록 총량(4)을 쓰면 `발생 − 사용 − 예정 ≠ 잔여`가 되어 4줄이
  검산되지 않고, 배정분(3)만 쓰면 산술은 맞지만 사용자가 등록한 4일째가 요약에서 사라진다.
- **살아 있는 발생분 리스트**를 소멸 임박 순으로. 각 행에 `남은 양/총량`과 소멸일.
  소멸까지 **60일 이내면 날짜 대신 `D-31`을 경고색으로** 띄운다.
- `[휴가 등록]` 버튼.
- 초과일 때: 헤더 잔여를 경고색으로, 4줄에 `초과` 행 추가, 상단에 원인 한 줄과
  **`조정을 추가` 링크**. 이 링크는 설정 탭으로 점프하며 조정 폼을 열어둔 채로 넘긴다 —
  원인 표시와 조치가 한 동선이어야 한다.

#### 5.2 등록 흐름

```
[휴가 등록] → 달력 시트 → 날짜 클릭 → 단위·메모 → [등록]      하루: 3클릭
                              ↘ [기간으로] → 종료일 클릭 ↗       기간: 5클릭
```

- **날짜를 한 번 누르면 그 하루로 확정**되고 바로 2단계로 넘어간다. 기간은 2단계에서
  `[기간으로]`를 눌러 종료일을 하나 더 고른다. 흔한 쪽(하루)을 짧게 두는 선택이다.
- 2단계는 `종일 / 반차 / 반반차` + 메모(선택) + 기간일 때만 `주말 제외`(**기본 켜짐**).
- **기간은 UI가 하루 1건씩 펼쳐 넣는다.** 3/20~3/24를 주말 제외로 넣으면 휴가 기록 3건이 생긴다.
- 시트는 팝오버를 덮는다. 즉 **등록은 모드 전환**이다.
- **`[오늘]` `[내일]` 바로가기를 만들지 않는다.** 진입은 달력 하나다. 대가는 Further Notes에 있다.
- **끌어서 기간 지정도 하지 않는다** — 380px 팝오버의 셀에서 오조작이 생긴다.

#### 5.3 이력 탭 — 리스트와 달력 두 뷰

| | 예정 | 사용 |
| --- | --- | --- |
| 리스트 | 맨 위 **예정 섹션**으로 분리 + 파란 `예정` 태그 | 연차 연도별 섹션 |
| 달력 | 파란 점 | 회색 점 |

- **달력이 두 몫을 한다** — 등록 시트이자 이력 탭의 두 번째 뷰다.
- **연차 연도별로 접고 현재 연도만 펼친 채로 연다.** 기록 58건 규모에서 이것 없이는 스크롤이
  끝나지 않는다. **이력 리스트만 스크롤한다.**
- **소멸분은 이력 탭 맨 아래로 보낸다.** 평소에 볼 것이 아니다.
- **수정·삭제는 뷰마다 다르다.** 리스트는 행에 마우스를 올리면 오른쪽에 `수정 / 삭제`가 뜨고
  수정은 그 자리에서 날짜·단위를 고친다. 달력은 날짜를 누르면 아래에 그날의 기록이 펼쳐지고
  거기서 단위 변경(`1 / ½ / ¼`)과 삭제를 한다.

#### 5.4 설정 탭

- `hireDate` · `grantBasis` · 조정 목록과 입력 · `[파일 위치 열기]` · 내보내기 / 가져오기.
- **입사일이 없으면 설정 탭만 활성이고 요약·이력은 비활성**이며 **조정 섹션도 감춘다** —
  입사일도 없는데 조정을 넣을 이유가 없다. 온보딩이 말해야 하는 것은
  `입사일을 넣으면 연차를 계산합니다` 한 줄이다.
- **조정 입력은 네 필드다**: `일수 / 발생일 / 소멸일 / 메모`. 소멸일 기본값은 그 시점 살아
  있는 발생분 중 가장 늦은 소멸일. 음수도 넣을 수 있다.
- **별도 창을 만들지 않는다.** 창을 쓰는 안은 등록이 1클릭까지 짧아지는 대신 "왜 그 숫자인지"가
  전부 창으로 넘어간다.
- **입사일을 바꿀 때** "새 입사일 이전의 휴가 기록과 조정 레코드를 지울까요?"를 묻고 사용자가
  고른다. 삭제 직전에 백업이 남는다. **거절할 수 있어야 한다** — 그래서 파서가 "입사일 이전
  휴가 기록"을 거부하지 않는다(2절).

#### 5.5 읽기 실패 화면 — 탭이 아니다

2절의 읽기 실패는 **팝오버 전체를 차지**하고 버튼 둘(`[백업에서 복구]` / `[파일 위치 열기]`)을
갖는다. 미래 버전일 때는 버튼 없이 안내만 띄운다. 탭 3개 구조와 층위가 다르며, "입사일이
없으면 설정 탭만 활성"과 같은 종류의 상태 분기다.

#### 5.6 크기

- **폭 380px 고정.** 달력 한 주가 7칸 × 48px로 들어가는 최소 폭이다.
- **높이는 탭 내용에 맞춘다.** 고정하면 탭마다 요구 높이가 크게 달라(요약 ~340 / 이력 달력
  ~455 / 설정 ~330 / 등록 시트 ~400) 어느 값으로 고정해도 세 탭 중 둘이 헐렁하거나 잘린다.
  메뉴바 앱의 통상 동작이기도 하다.

#### 5.7 소멸을 알아채는 경로는 둘뿐이다

트레이가 소멸에 아무 표시를 하지 않으므로 이 화면이 그 경로 전부를 갖는다.

1. 요약 탭 발생분 행의 **D-day 배지**(60일 이내, 경고색)
2. 이력 달력에서 소멸일 아래의 **빨간 밑줄**. 그날을 누르면 `2025년 이월 3일 소멸`이 뜬다

OS 알림은 만들지 않는다(Out of Scope).

### 6. 아이콘과 트레이 글리프 — 별개의 두 그림이다

**하나에서 파생시킬 수 없다.** 품질이 서로 반대인 것이 실측으로 확인됐다.

| | 트레이 글리프 | 앱 아이콘 |
| --- | --- | --- |
| 모양 | **가로 대시 하나** (`–`) | 시스템 블루 squircle + 흰 달력 |
| 뜻 | "숫자가 들어갈 자리인데 아직 계산할 수 없다" | 제품 정체 |
| 어디에 | 트레이, **입사일 미설정일 때만** | DMG · NSIS · 작업 표시줄 · Dock |
| 파일 | **없다.** 런타임에 canvas로 그린다 | `.icns` + `.ico` |
| 라이트/다크 | macOS 한 장(템플릿), Windows는 잉크 인자 하나 | 대응 불필요(자체 배경) |
| 온보딩 화면 | 넣지 않는다 | 넣지 않는다 |

- 달력은 512px에서 좋고 **16px에서 고리 둘이 상단 띠에 먹혀 뜻을 잃는다**(「뚜껑 달린 빈 상자」).
- 대시는 16px에서 완벽하고 **512px에서 「빼기 버튼」이 된다**(파란 사각에 흰 가로줄은 제거·접기
  버튼의 관용 표기다).
- **512px 앱 아이콘을 16px로 축소하면 파란 얼룩이 된다** — 흰 획이 1px 미만으로 얇아져
  파랑에 섞여 대비를 잃는다. **따라서 "입사일 미설정 = 앱 아이콘"은 구현할 수 없다.**
  그 자리에 들어가는 것은 앱 아이콘이 아니라 **세 번째 그림(대시)** 이다.

**16px에서 사는 획의 일반 규칙: 축에 정렬된 정수 픽셀 획뿐이다.** 1px 곡선은 40% 회색으로
번지고(야자수), 획이 여섯이면 서로 붙는다(한글 「연」). 달력이 죽는 방식은 다르다 — 획은
선명한데 2px 고리가 1px 머리띠와 붙어 **선명하지만 뜻이 틀린 도형**이 된다.

**대시가 이긴 이유는 트레이 글리프가 장식이 아니라 상태 표시라는 것이다.** 대시는 아이콘이
아니라 **비어 있는 숫자 자리**이고, 다른 후보는 전부 "무슨 앱인가"를 말하려다 16px에서 실패한다.

#### 6.1 확정 기하 (프로토타입이 산출한 결정적 스니펫)

```
w = max(2, round(size * 0.56 / 2) * 2)
h = max(2, round(size * 0.125 / 2) * 2)
fillRect((size - w) / 2, (size - h) / 2, w, h)
```

| size | 16 | 20 | 24 | 32 | 40 | 48 |
| --- | --- | --- | --- | --- | --- | --- |
| w × h | 8×2 | 12×2 | 14×4 | 18×4 | 22×6 | 26×6 |
| x, y | 4, 7 | 4, 9 | 5, 10 | 7, 14 | 9, 17 | 11, 21 |

**폭과 두께를 짝수로 강제하는 것이 이 후보의 존재 이유를 지킨다.** `round(size * 0.125)`로
단순화하면 20px에서 두께 3px이 나와 세로 중앙이 반 픽셀 어긋나고, 그 반 픽셀이
안티에일리어싱을 불러 **"번지지 않는다"는 유일한 장점을 지운다.** 폭도 같은 이유로 짝수다
(홀수면 16px에서 좌 4 / 우 3으로 어긋난다). **단순화하지 마라.**

#### 6.2 라이트/다크

트레이 글리프는 파일이 아니라 함수다 — `drawGlyph(size, tone)`의 `tone`이
`'mono' | 'light' | 'dark'`다.

| | macOS | Windows |
| --- | --- | --- |
| 그리는 것 | 알파만(잉크 색 무의미) | 잉크 색을 직접 고른다 |
| 라이트/다크 | `img.setTemplateImage(true)` **한 장으로 끝** | 테마마다 다시 그린다 |
| 트리거 | 없음(OS가 반전한다) | `nativeTheme.on('updated')` |

**`nativeTheme.on('updated')`는 4.5절의 재계산 트리거 셋과 다른 축이다.** 저쪽은 값이 바뀌는
것이고 이쪽은 같은 값을 다시 그리는 것이다. **섞지 마라.** macOS는 이 리스너가 필요 없다.
이 이벤트는 값이 실제로 바뀔 때만 오므로 리스너에서 무조건 다시 그려도 낭비가 없다.

#### 6.3 자산 목록

**512px 원본 하나 → `.icns`(macOS) + `.ico`(Windows).** **트레이 글리프는 이 목록에 없다** —
런타임 canvas 렌더이므로 빌드 산출물이 아니다. **16px 아이콘 파일을 만들지 마라.**

**앱 아이콘의 최종 드로잉은 결정이 아니라 제작이다.** 정해진 것은 "달력 + 시스템 블루
squircle, 트레이 글리프와 별개"까지이고, 획 두께·모서리 반경 같은 수치는 그림을 그릴 때 정한다.

### 7. 프로젝트 구조와 툴체인 (스캐폴딩 지시)

이 절과 8절은 **의도적으로 파일 경로를 담는다.** 이 스펙의 완료 조건이 "구현 에이전트가
스펙만 읽고 빈 저장소에 스캐폴딩을 시작할 수 있다"이기 때문이다.

| | 결정 |
| --- | --- |
| 저장소 | 같은 저장소. v2 PWA는 나중에 `apps/web`으로 붙는다 |
| 구조 | pnpm workspace + Turborepo. 패키지는 v1에 **정확히 둘** |
| 코어 소비 | **Just-in-Time** — `exports`가 `./src/index.ts`. `dist` 없음, 빌드 스크립트 없음 |
| 날짜 | **Temporal**, `temporal-polyfill`을 코어의 정식 `dependencies`로 |
| 시간대 | **고정 `Asia/Seoul`** |
| 셸 빌드 | `electron-vite` 5 + Vite 7 + `@vitejs/plugin-react` 5.2 |
| 패키징 | `electron-builder` **26.15.7** (정확히 핀) |
| 테스트 | Vitest 4. **코어만** |
| 린트·포맷 | Biome 2.5 하나 |
| 타입체크 | TypeScript 7 (네이티브 컴파일러) |
| 매니저·런타임 | pnpm 11 + Node 24 LTS |
| Electron | 44 계열 (Chromium 152 / Node 24) |

#### 7.1 왜 워크스페이스인가 — 경계를 pnpm이 강제한다

단일 패키지 안의 `src/core/` 디렉터리 분리를 기각한 근거는 패키지 수가 아니라 **경계를 무엇이
지키는가**다. 실측했다.

- `packages/core`가 `electron`을 import하면 → `TS2307: Cannot find module 'electron'`
- `apps/desktop`이 `temporal-polyfill`을 자기 `dependencies`에 선언하지 않고 import하면 → 같은 오류

단일 패키지에서는 `src/core/grants.ts`가 `electron`을 import해도 **아무 일도 일어나지 않는다.**
그 대가는 v1이 아니라 v2에서 치른다. 확정 전제("코어는 브라우저·Node·웹뷰 어디서든 동작")를
지키는 것이 **사람의 기억이 아니라 pnpm의 엄격한 `node_modules`** 가 된다.

Electron의 main·preload·renderer가 같은 타입을 공유해야 하는 압력은 **이것과 다른 문제다.**
셋은 전부 `apps/desktop` 한 패키지 안이고, 그건 `electron-vite`가 푼다.

#### 7.2 코어를 빌드하지 않는다 (Just-in-Time)

`packages/core/package.json`의 `exports`가 `./src/index.ts`를 직접 가리킨다. 빌드 스크립트도
`dist`도 없다. 소비자(Vite / 나중의 Next.js)가 컴파일한다.

`"@yeoncha/core": "workspace:*"`는 이 선택과 **무관하게** 소비자에 들어간다. 두 줄이 다른
층이다 — `workspace:*`는 pnpm이 읽고 "어느 패키지"를 정하며, `exports`는 번들러·tsc가 읽고
"어느 파일"을 정한다.

**`apps/web`이 나중에 붙는 것은 이 결정을 흔들지 않고 더 세게 만든다.**

1. Next.js에 `transpilePackages`가 있어 한 줄이면 된다.
2. 빌드 산출물을 두면 "코어를 고쳤는데 다시 빌드하지 않아 앱이 옛 코드를 본다"는 함정이 생긴다.
   **오류가 나지 않고 숫자만 틀린다.** 이 앱에서 그건 곧 **잔여**가 틀린다는 뜻이고, 제품
   전체가 그 숫자 하나다. 소비자가 늘수록 함정도 는다.
3. 컴파일 대상이 앱마다 다르다(`apps/desktop`은 Chromium 152 + Node 24, `apps/web`은 여러
   브라우저). 빌드 산출물을 두면 코어가 대상 하나를 미리 골라야 하고 그 하나는 어느 쪽에도
   딱 맞지 않는다.

되돌리기도 싸다 — 빌드 스크립트를 넣고 `exports`를 `dist`로 바꾸는 두 군데다.

#### 7.3 날짜는 Temporal이다 → [ADR-0002](../../docs/adr/0002-temporal-plaindate-for-dates.md)

`temporal-polyfill`을 **코어의 정식 `dependencies`** 로 두고, **네이티브가 있는 렌더러에서도
폴리필을 쓴다.** Electron 44의 렌더러(Chromium 152)에는 `Temporal`이 있지만 메인 프로세스의
Node 24와 Vitest가 도는 Node 24에는 없다. 명명 import(`import { Temporal } from
'temporal-polyfill'`)면 세 환경의 동작이 완전히 같고 **환경 분기가 0**이다. 크기는 19.8KB
gzip으로 DMG 120MB 앱에서 반올림 오차다.

**"오늘"은 고정 `Asia/Seoul`이다.** 셸이 `Temporal.Now.plainDateISO('Asia/Seoul')`로 만들어
코어에 넘긴다. 근거는 연차가 회사의 날짜 개념이라는 것보다 **v1과 v2가 같은 파일에서 같은
숫자를 내야 한다**는 것이 더 세다 — 로컬 시간대를 쓰면 해외에 있는 폰의 PWA와 집의 데스크톱이
하루 다른 **잔여**를 띄우고, 그게 하필 5.7절의 소멸 인지 경로(D-day)에서 갈린다.
**설정값으로 빼지 않는다.** 되돌리기는 셸의 한 줄이다.

#### 7.4 셸 빌드는 `electron-vite` 5 + Vite 7

버전 지형이 갈랐다 — Vite 8이 `latest`인데 `electron-vite` stable 5.0.0은 **Vite 5~7까지**이고
Vite 8은 6.0.0-beta.1에만 있다. `@vitejs/plugin-react`는 6.x가 Vite 8 전용이고 **5.2.0이
Vite 4~8 전부**를 받는다. **Vite 8이 우리에게 주는 것이 없으므로 베타를 쓰지 않는다.**

`electron-vite`를 빼고 Vite(렌더러) + esbuild(main·preload)를 직접 엮는 안도 검토했다. 진짜
비용은 빌드가 아니라 **개발 루프**다 — dev 서버 + main watch + 변경 시 electron 재기동, 그리고
렌더러가 dev에서는 `http://localhost`·프로덕션에서는 `file://` + `base: './'`인 분기를 손으로
짜야 한다. `electron-vite`는 정확히 그 셋을 위해 존재한다.

**출력 경로를 갈라둔다** — `electron-vite`는 `out/`, `electron-builder`의 `directories.output`은
`release/`. 프로토타입에서 둘 다 `dist/`를 써서 **asar가 자기 자신을 삼켜 320MB가 된 사고**를
실제로 밟았다.

#### 7.5 `turbo.json`과 검증 명령어

```json
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "lint": { "dependsOn": [] },
    "typecheck": { "dependsOn": ["^typecheck"] },
    "test": { "dependsOn": [] },
    "build": { "dependsOn": ["lint", "typecheck", "^test"], "outputs": ["out/**"] }
  }
}
```

```json
"scripts": {
  "verify":    "turbo run lint typecheck test",
  "build":     "turbo run build",
  "format":    "biome check --write .",
  "lint":      "turbo run lint",
  "typecheck": "turbo run typecheck",
  "test":      "turbo run test"
}
```

- **`lint`가 turbo 태스크인 근거는 실측이다.** 루트에서 `biome check .`를 한 번 돌리는 쪽이
  싸 보였지만 재보니 반대였다(웜 0.09s 대 **0.04s**). 루트 Biome은 매번 전체를 훑지만 패키지
  태스크가 되면 turbo가 lint 결과도 캐시해 안 바뀐 패키지를 아예 건너뛴다.
- **`build`가 `lint`·`typecheck`·`^test`에 의존한다.** 린트가 깨진 코드나 검증 케이스가
  깨진 코어로 바이너리가 나가지 않는다. 실제로 코어에 `let x = 1`을 심으니 `#lint`가 실패하고
  `#build`가 실행되지 않으며 산출물도 생기지 않았다.
- `^typecheck`는 `build`의 `dependsOn`에서 뺐다 — `build`가 자기 패키지의 `typecheck`에
  의존하고 그것이 이미 `^typecheck`에 의존하므로 중복이다.
- `format`만 Biome을 직접 부른다. 파일을 고치는 명령이라 캐시가 해롭다.
- **대가**: 쉼표 하나 때문에 `pnpm build`가 멈춘다. 대응은 `pnpm format`이고 Biome의 지적은
  거의 다 `FIXABLE`이다.

**실측**: `pnpm verify` 콜드 1.19s / 웜 **0.49s**(`FULL TURBO`), 셸만 고쳤을 때 518ms,
코어를 고쳤을 때 1.09s, `turbo run build` 6태스크 1.98s.

```
│                              private: true, 버전을 두지 않는다(8절)
├── pnpm-workspace.yaml     ← packages/* apps/*, allowBuilds (7.8절의 순서를 따를 것)
├── turbo.json
├── biome.json              ← vcs.useIgnoreFile: true

├── CONTEXT.md              ← 이미 있다. 고치지 않는다
├── docs/adr/               ← 0001 셸 프레임워크, 0002 날짜 라이브러리
├── .github/
│   ├── RELEASE_BODY.md     ← README와 같은 우회 안내 문장
│   └── workflows/{ci.yml,release.yml}
├── packages/core/          ← @yeoncha/core   (dependencies: temporal-polyfill 만)
│   ├── package.json        ← exports: { ".": "./src/index.ts" }, 빌드 스크립트 없음
│   └── src/
└── apps/desktop/           ← @yeoncha/desktop

```

`tsconfig.base.json`의 검증된 설정:

```json
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "preserve",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "allowImportingTsExtensions": true,

  }
}
```

`noUncheckedIndexedAccess`를 켠 이유가 있다 — 3.4절의 **배정** 알고리즘이 **발생** 배열을
소멸 임박 순으로 훑으며 인덱싱하는 코드이고, 달력 격자도 배열 인덱싱이다. **이 앱에서 배열
접근이 곧 도메인 로직이다.**

`@yeoncha` 스코프는 퍼블리시하지 않으므로 npm 등록이 필요 없다.

**`CONTEXT.md`는 고치지 않는다.** 이 스펙이 쓰는 구현 이름(`@yeoncha/core`, `computeGrants`,
`parse`, `schemaVersion`, `settings`, `entries`, `adjustments`)은 전부 구현 용어이지 도메인
용어가 아니다. 2절 저장 파일의 키가 **발생일·소멸일·일수**와, 코어 내보내기가
**발생·배정·잔여·초과**와 각각 1:1이다.

"그 달의 1일이 무슨 요일인가", "그 달이 며칠인가", "월 이동"은 `PlainDate.dayOfWeek` /

### 8. GitHub Release 빌드 파이프라인

**워크플로 둘로 가른다.**

| 파일 | 트리거 | 러너 | 하는 일 |
| --- | --- | --- | --- |
| `ci.yml` | `push: [main]`, `pull_request`, `workflow_dispatch` | macOS + Windows | `install --frozen-lockfile` → `pnpm verify` → `pnpm build`. **패키징하지 않는다** |
| `release.yml` | `push: tags: ['v*']` | 같은 둘 + 수집 잡 하나 | 검증 후 `electron-builder`, 아티팩트 업로드, 릴리스 생성 |

#### 8.1 왜 둘인가

지도의 확정 전제("AI 에이전트가 OS별 바이너리를 함께 업로드한다")가 정하는 것은 **누가
하는가**이지 **어떤 이벤트인가**가 아니다.

**main 푸시마다 릴리스하지 않는 이유는 소음이 아니라 버전이다.** 버전의 유일한 출처가
`apps/desktop/package.json`이므로(8.3절) 문서를 고친 커밋에도 릴리스가 나가면 **같은 버전
번호를 가진 릴리스가 여러 개** 생기거나 커밋마다 버전을 올려야 한다. 전자는 "v1.2.0을 받았는데
어느 v1.2.0인가"가 되고, 후자는 오타를 고칠 때마다 마이너를 올린다.

**그런데 태그 푸시에만 걸면 main이 아무 검증도 받지 못한다.** 이 프로젝트에는 그러면 안 되는
강한 이유가 있다 — 트레이·팝오버·구조·아이콘 결정이 전부 **"Windows에서 아무것도 실행하지
못했다"** 를 구멍으로 남겼다. 검증이 릴리스 시점에만 돌면 Windows가 깨진 것을 **릴리스를
자르는 순간에** 알게 된다. 가장 나쁜 시점이다. `ci.yml`의 Windows 잡이 그 구멍을 **커밋
단위로** 좁히는 유일한 장치다.

`ci.yml`은 `electron-builder`를 부르지 않으므로 Electron 배포본을 내려받지 않아 잡당 비용이 작다.
**`fail-fast: false`가 이 워크플로의 존재 이유와 직결된다** — Windows가 깨졌는데 macOS가 먼저
실패해 취소되면 정확히 보고 싶었던 것을 못 본다.

**에이전트의 릴리스 절차는 네 단계다.** `apps/desktop/package.json`의 `version` 올리기 → 커밋
→ main 푸시 → `git tag v<version> && git push --tags`.

함정 하나: **워크플로가 `GITHUB_TOKEN`으로 푸시한 태그는 다른 워크플로를 트리거하지 않는다.**
즉 "CI가 자동으로 태그를 밀어 릴리스를 트리거"는 동작하지 않는다. 우리 설계는 에이전트가
로컬 세션에서 사용자 자격증명으로 태그를 미는 것이라 걸리지 않는다. 자동 태깅을 나중에 붙이려면
PAT가 필요해진다.

#### 8.2 릴리스를 쓰는 잡은 하나다 — 이 결정에는 반드시 이유가 붙어야 한다

`electron-builder`에 **내장 publish가 있다.** 그래서 이유를 모르면 "왜 굳이 아티팩트를 거쳐
가지?"라며 되돌려진다. **되돌리면 깨진다.**

`electron-publish`의 `getOrCreateRelease()`는 릴리스 목록을 훑어 draft가 있으면 재사용하고
없으면 `createRelease()`를 부른다. 그리고 **`createRelease()`에는 422 `already_exists` 재시도가
없다** — 소스에서 422를 처리하는 곳은 **에셋 업로드 경로뿐**이다. macOS 잡과 Windows 잡은
거의 동시에 시작하므로 둘 다 "draft 없음"을 보고 둘 다 생성을 시도할 수 있고, **한쪽이 그냥
실패한다. 실패가 확률적이라 더 나쁘다** — 세 번에 한 번 깨지는 릴리스 파이프라인은 고장 난
것보다 다루기 어렵다.

electron-builder 문서의 회피책("사람이 draft를 먼저 만들어 두고 CI는 붙이기만 한다")은 릴리스마다
수동 단계를 넣는 것이라 "에이전트가 릴리스를 낸다"는 전제를 깬다.

```
build (macos-latest)  ─┐  --publish never  → upload-artifact: dist-macos-latest
build (windows-latest) ─┤  --publish never  → upload-artifact: dist-windows-latest
                        └→ release (ubuntu-latest, needs: build)
                              download-artifact: pattern dist-*, merge-multiple
                              태그 ↔ 앱 버전 일치 검사
                              softprops/action-gh-release@v3
```

**쓰는 잡이 하나면 경쟁 조건이 존재하지 않는다.** 이건 방어가 아니라 제거다.

- **릴리스 생성 수단은 `softprops/action-gh-release@v3`이다.** `gh release create`도 러너에
  깔려 있지만 **이미 존재하는 릴리스에 대한 동작을 1차 문서에서 확인할 수 없었다.**
  에이전트는 실패한 워크플로를 **재실행**하게 되므로 이 축에서 갈렸다 — `softprops` v3는
  생성·업로드 양쪽의 `already_exists`를 명시적으로 처리하고 `overwrite_files` 기본값이
  `true`라 **재실행이 멱등이다.**
- 수집 잡은 `ubuntu-latest`. 파일을 옮겨 붙일 뿐이라 Node도 pnpm도 필요 없다.
- **릴리스는 draft로 만들지 않고 바로 publish한다.** 통제 지점은 이미 "태그를 미는 것"이다.
- **아티팩트 이름은 매트릭스마다 다르게 준다**(`dist-${{ matrix.os }}`). `upload-artifact` v4부터
  아티팩트가 **불변**이라 같은 이름 재업로드가 실패한다. 수집은 `pattern: dist-*` +
  `merge-multiple: true`.
- **릴리스 잡에만 `permissions: contents: write`.** `GITHUB_TOKEN`의 기본 권한은 리포지토리·조직
  설정에 따라 달라 문서상 고정 기본값이 없다. `permissions:`를 쓰면 적지 않은 스코프는 전부
  `none`이 되므로 빌드 잡은 읽기만 갖는다.
- **빌드 잡은 `--publish never`를 명시한다.** 암묵적 publish는 v27에서 제거 예정이라고 문서가
  경고한다. 자동 감지에 기대면 업그레이드 때 조용히 깨진다.
- **검증을 앞세운다** — `pnpm verify` 다음 `pnpm build`(또는 `electron-builder`). `turbo.json`의
  `build`가 이미 검증을 물고 있지만 그 그래프에 **코어의 `lint`가 들어오는지는 해석이 갈린다**
  (`core`에는 `build` 태스크가 없어 `build → lint` 간선이 생기지 않는다). `verify`를 앞에 두면
  두 해석 어느 쪽에서도 코어가 린트되고, 웜 캐시에서 비용이 거의 0이다. 그리고 CI 로그에서
  "검증에서 깨졌다"와 "패키징에서 깨졌다"가 스텝 이름으로 갈린다.
- **turbo 캐시는 CI에서 쓰지 않는다.** 원격 캐시도, `actions/cache`로 `.turbo`를 잡는 것도.
  잡이 매번 새 러너라 캐시 히트를 보려면 저장·복원 비용을 먼저 내야 하는데 `pnpm verify`
  콜드가 1.19초다. **캐시가 아낄 것보다 캐시 자체가 비싸다.**

#### 8.3 산출물과 버전

**릴리스에 붙는 자산은 정확히 둘이다** — `yeonchamyeotgae-<version>-arm64.dmg`와
`yeonchamyeotgae-<version>-x64.exe`.

- **macOS는 `dmg`만.** mac 기본 타깃은 `dmg` + `zip`이고 `zip`이 있는 유일한 이유는
  Squirrel.Mac 자동 업데이트다. 자동 업데이트는 Out of Scope이므로 zip은 할 일이 없다.
  **명시적으로 `target: [dmg]`를 적어야** 기본값이 zip을 딸려오지 않는다.
- **macOS는 arm64만.** universal도, arm64·x64 두 개도 아니다. 가른 것은 용량이 아니라
  **러너**다 — `macos-latest`는 arm64이고 x64 macOS 러너는 **유료 large 계열**이며, 겹쳐서
  **pnpm 11은 `darwin-x64` 바이너리를 배포하지 않는다.** `arch: universal`은 유료 러너를 피하는
  유일한 길이지만 **최악이다**: x64를 한 번, arm64를 한 번 패키징한 뒤 병합하므로 빌드 시간과
  다운로드가 2배가 되고 fat binary가 되어, 그 커진 파일을 **x64 사용자 0명을 위해 실제
  사용자(arm64)가 내려받는다.** 되돌리는 순서는 (1) arm64 러너에서 `--x64`를 그냥 시도
  (무료, 네이티브 모듈이 0개라 아마 된다), (2) 안 되면 pnpm 12로 올리고 Intel 러너를 매트릭스에
  추가. `arch` 한 줄과 매트릭스 한 항목이다.
- **Windows는 `nsis`.** `portable`을 기각한 것은 SmartScreen이 아니라 **데이터가 어디 사느냐**다.
  저장 파일이 `userData` 고정이므로 portable exe는 **실제로 portable하지 않다** — 파일을 옮겨도
  데이터는 따라오지 않는다. 이름이 약속을 지키지 못하는 선택지다. 트레이 앱은 계속 떠 있는
  물건이라 안정된 설치 위치와 제거 경로가 있는 편이 맞다. `oneClick: true` 기본값을 쓴다.
- **파일 이름(`artifactName`)은 ASCII로 뽑는다.** 기본 매크로가 그대로 다운로드 파일명이
  되면 릴리스 URL이 퍼센트 인코딩으로 덮이므로 `artifactName:
  "yeonchamyeotgae-${version}-${arch}.${ext}"`로 분리한다.
- **`productName`도 ASCII다 — 이 절의 원래 결정(한국어 `productName` + ASCII `executableName`)은
  31번 티켓에서 뒤집혔다.** macOS 헬퍼 번들(Contents/Frameworks/\*.app) 이름은
  `productName`에서만 파생되고 `executableName`으로 대체할 수 없어, 한글을 쓰면 Finder 복사
  (DMG → 응용 프로그램) 후 헬퍼 실행 파일 이름의 유니코드 정규화(NFC/NFD)가 `Info.plist`의
  `CFBundleExecutable`과 어긋나 앱이 실행 직후 `SIGTRAP`(종료 코드 133)으로 죽는다 — 빌드
  시점 훅으로는 고칠 수 없는 설치 시점 문제라, 정규화가 애초에 갈릴 수 없게 `productName`
  자체를 ASCII(`yeonchamyeotgae`)로 바꿨다. 최상위 `executableName`은 더 이상 두지 않는다
  (`productName`이 이미 ASCII라 기본값이 곧 ASCII다).
- **사용자에게 보이는 이름(메뉴 막대, 시작 메뉴, DMG 볼륨, macOS `.app` 표시 이름)은 더 이상
  `productName`에서 나오지 않는다** — 각각 `mac.executableName`, `nsis.shortcutName`,
  `dmg.title`(리터럴), 그리고 `mac.extendInfo.CFBundleDisplayName`(강제 종료·Activity
  Monitor용)으로 개별 지정해 한국어를 유지한다. `mac.executableName`은 헬퍼와 분리된 파생
  경로라 한글이어도 SIGTRAP과 무관하지만, Finder 복사 시 같은 NFD 재정규화를 겪는다는 사실은
  남아 있다 — 크래시가 없는 이유는 "이미 떠 있는 메인 프로세스는 자기 실행 경로를 재검증하지
  않는다"는 관찰 하나에 기댄 것으로, Electron/Chromium/macOS가 바뀌면 조용히 재발할 수 있는
  가정이다. 전체 조사와 실측 근거는
  [`31번 티켓`](issues/31-macos-finder-install-launch.md)을 본다.

**버전의 유일한 출처는 `apps/desktop/package.json`의 `version`이다.** electron-builder는
`<projectDir>/package.json`을 읽고, `apps/desktop`에서 실행하면 그 파일이 곧 메타데이터다.
**루트 `package.json`은 관여하지 않으므로 버전을 두지 않는다.**

**태그는 `v` + 그 값이다.** 방향이 `package.json` → 태그다. 반대 방향(태그에서 파싱해
`extraMetadata.version`으로 주입)도 기술적으로 되지만 문서의 권고가 아니고, 더 나쁜 점은
**앱이 자기 버전을 모른 채 빌드된다**는 것이다.

**릴리스 잡이 일치를 검사한다** — `apps/desktop/package.json`의 `version`과 `GITHUB_REF_NAME`
에서 `v`를 뗀 값이 다르면 실패시킨다. 이 검사가 없으면 태그는 `v1.2.0`인데 앱이 자기를
`1.1.0`이라고 말하는 릴리스가 **아무 오류 없이** 나간다. 조용히 틀리는 종류다.

**빌드 번호는 붙이지 않는다.** electron-builder가 `buildVersion`을 만들 때 읽는 환경변수 목록에
GitHub Actions 것이 하나도 없어 `buildVersion === version`이 되고, 그게 우리가 원하는 바다.

#### 8.4 서명 억제 — `electron-builder.yml`의 세 줄

프로토타입을 로컬에서 패키징했을 때 **electron-builder가 키체인의 `Apple Development`
인증서를 찾아 묻지 않고 자동 서명했다.** 서명하지 않기로 했으므로 **명시적으로 꺼야 한다.**

```yaml
mac:
  identity: null          # 인증서를 꽂을 때 이 줄을 지운다
  hardenedRuntime: false  # identity: null과 짝
win:
  signExecutable: false   # 서명만 끈다. 아이콘·버전 리소스 편집은 유지된다
```

- **끄는 방법은 `identity: null`이고 환경변수가 아니다.** 소스상 `identity === null`이면
  **키체인 조회 자체가 일어나지 않는다.** 반면 `CSC_IDENTITY_AUTO_DISCOVERY=false`는 자동 탐색
  단계만 끄고, **환경변수라 로컬 셸에서 빠뜨리면 위 사고가 그대로 재발한다.** 설정 파일에
  박으면 로컬과 CI가 같은 동작을 한다.
- **`win.signAndEditExecutable: false`를 쓰면 안 된다.** 이름이 비슷하지만 리소스 편집까지
  꺼져 **6.3절의 `.ico`가 exe에 붙지 않는다.** `signExecutable`이 "서명만 끄고 resedit은 유지"를
  정확히 표현한다.
- `hardenedRuntime: false`는 문서 경고("서명을 끄면 Hardened Runtime도 꺼라")를 따른 것인데
  그 경고문이 ad-hoc 서명 문맥이라 `identity: null`에도 적용되는지 문면상 모호하다. **확인되지
  않았으므로 안전한 쪽으로 둔다.**
- **`identity: null`은 "서명 안 함"이 아니라 "electron-builder의 서명 단계를 건너뜀"이다 —
  이 둘은 다르다(32번 티켓).** 서명 단계를 건너뛰면 `.app` 번들 전체를 감싸는
  `_CodeSignature/CodeResources` 봉인이 아예 생기지 않고, `codesign --verify --deep
  --strict`가 `code has no resources but signature indicates they must be present`로
  실패하는 상태로 나간다. 로컬 Finder 복사 + `open` 검증은 격리 속성이 없어 이 문제를
  드러내지 않지만, 실제 GitHub Release 다운로드는 격리 속성이 붙어 Gatekeeper가 이 검증을
  강제하고 **"손상되었기 때문에 열 수 없습니다"로 거부한다** — README가 안내하는
  "확인되지 않은 개발자" 흐름조차 뜨지 못하는, 더 나쁜 실패다. 그래서 `afterPack` 훅
  (`scripts/adhoc-sign.cjs`)이 패키징 직후 `codesign --deep --force --sign -`로 번들
  전체를 직접 ad-hoc 서명해 봉인을 채운다. `identity: null` 자체(키체인 인증서 자동
  탐색 억제)는 그대로 유지된다 — 이 훅은 `-`(인증서 없음)로만 서명해 진짜 인증서를
  집어 쓰는 사고와 무관하다.

**나중에 켤 때의 4단계 — 이게 "서명 훅"의 실체다.** 워크플로 YAML에는 주석 블록 하나만 둔다.

1. **`mac.identity: null`을 지운다.** ← **가장 중요하다. 지우지 않으면 `CSC_LINK`를 넣어도
   위 코드가 그 앞에서 반환해 조용히 서명되지 않는다.**
2. `mac.hardenedRuntime: true`로 되돌린다(공증의 전제다).
3. `mac.notarize: true`를 켠다.
4. 리포지토리 시크릿을 넣고 빌드 잡의 `env:`에 연결한다 — `CSC_LINK`, `CSC_KEY_PASSWORD`,
   `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`.

**빈 시크릿을 미리 `env:`에 꽂아두지 않는다.** 워크플로 diff가 0이 되어 매력적이지만 존재하지
않는 시크릿은 빈 문자열로 렌더되고 **electron-builder가 빈 `CSC_LINK`를 미설정으로 취급하는지
확인되지 않았다.** 서명을 켜지도 않았는데 빌드가 깨지는 위험을 지금 지불할 이유가 없다.

**`@yeoncha/core`는 `devDependencies`에 둔다.** electron-builder는 `pnpm list --prod`로 의존성을
수집하므로 `dependencies`에 두면 `packages/core`를 `node_modules/@yeoncha/core`로 성실히
복사하는데, **Electron은 `.ts`를 실행할 수 없다.** 정상 경로는 Vite가 번들 시점에 인라인하는
것이다. 그리고 이 배치가 **`externalizeDepsPlugin` 함정을 동시에 없앤다** — 그 플러그인이
external로 빼는 대상이 `dependencies`이므로 core가 `devDependencies`에 있으면 애초에 대상이
아니다. **`exclude: ['@yeoncha/core']` 설정을 넣지 마라. 불필요하다.**

> **불변식**: `apps/desktop/package.json`의 `dependencies`가 **비어 있다.** `react`·`react-dom`은
> 렌더러 전용이라 Vite가 번들하고, `electron`은 언제나 devDependency이며, `temporal-polyfill`은
> core와 함께 번들에 들어간다. 여기에 항목이 하나라도 생기면 `externalizeDepsPlugin`과
> electron-builder의 `--prod` 수집이 동시에 깨어나 패키징 이야기가 달라진다.

**확인 방법**: 첫 패키징 후 `npx asar list <app>/Contents/Resources/app.asar`. 우리 번들
코어(`out/`에서 온 것)만 보이고 **`node_modules/@yeoncha/core`가 없어야 한다.** 프로토타입의
`app.asar` 201KB가 대조군이다.

내려받아 두 경고를 만나는 순간이 스크린샷을 찍을 유일하고 자연스러운 시점이다.**

#### 8.6 러너 설정

```yaml
- uses: actions/checkout@v7
- uses: pnpm/setup@v2
  with: { version: 11, runtime: node@24, cache: true, install: false }
- run: pnpm install --frozen-lockfile
```

- **`actions/setup-node`를 쓰지 않는다.** `pnpm/action-setup`의 후계자가 `pnpm/setup`이고
  pnpm v11 이상은 이쪽을 쓰며 `actions/setup-node`를 대체한다. 두 액션이 한 스텝이 되면서
  **순서 함정도 사라진다**(`setup-node`의 pnpm 캐싱은 `pnpm store path`를 실행해야 해서 pnpm이
  PATH에 먼저 있어야 했다).
- **`install: false`를 명시한다.** 기본값이 `true`라 알아서 install을 돈다. pnpm은 CI를 감지하면
  frozen으로 기울지만 **`--frozen-lockfile`을 손으로 적어 로그에 보이게 하는 편이 낫다.**
- **Electron 캐시는 붙이지 않는다.** Electron 42부터 postinstall이 없어져 바이너리가 pnpm
  스토어 캐시에 들어가지 않는다. 잡으려면 `~/Library/Caches/electron`·`electron-builder`
  (Windows는 `%LOCALAPPDATA%`)를 따로 캐시해야 한다. `ci.yml`은 애초에 Electron을 받지 않고
  `release.yml`은 한 달에 몇 번 돈다.

**액션 버전**: `actions/checkout@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`,
`pnpm/setup@v2`, `softprops/action-gh-release@v3`. `softprops`는 서드파티라 커밋 SHA 핀이
공급망 관점에서 낫지만 **v1에서는 태그로 둔다** — 사용자 한 명짜리 도구에 지금 지불할 값이
아니다. 판단이 바뀌면 한 줄이다.

### 9. 반드시 밟게 되는 함정

**전부 실제로 밟고 고친 것들이다.** 이 절이 스펙에 없으면 구현 에이전트가 다시 밟는다.

1. **turbo 캐시는 git 저장소가 있어야 동작한다.** `git init` 전에는 동일 재실행에도
   `Cached: 0`이 나온다. **빈 저장소에 스캐폴딩할 때 `git init`이 `turbo` 설치보다 먼저다** —
   이건 스캐폴딩 순서를 바꾸는 지시다. (CI에서는 turbo 캐시에 기대지 않으므로 `fetch-depth`
   조정은 필요 없다. `actions/checkout` 기본값을 쓴다.)
2. **`allowImportingTsExtensions: true`가 필요하다.** `exports`가 `./src/index.ts`인 이상
   `TS5097`이 난다. `noEmit`과 짝으로 켠다.
3. **Biome은 기본적으로 `.gitignore`를 보지 않는다.** 그냥 돌리면 `.turbo/cache/`까지 긁어
   44파일에 오류 34개가 난다. `vcs: { enabled: true, clientKind: "git", useIgnoreFile: true }`를
   켜면 12파일로 줄고 깨끗해진다.
4. **Biome 2.5의 제외 패턴은 `!**/out`이다.** `!**/out/**`로 쓰면
   `lint/suspicious/useBiomeIgnoreFolder`가 뜬다.
5. **Biome 2.5에서 `linter.rules.recommended: true`는 deprecated다.**
   `"rules": { "preset": "recommended" }`로 쓴다.
6. **`allowBuilds` 목록은 순서를 지켜 확정한다.** `esbuild: true`가 없으면
   `[ERR_PNPM_IGNORED_BUILDS]`로 **install이 종료 코드 1**이고, 더 나쁜 것은 **pnpm이 install
   도중 `pnpm-workspace.yaml`에 플레이스홀더를 써넣어 CI 체크아웃이 더러워진다**는 것이다.
   `strictDepBuilds` 기본값이 `true`라 미승인 빌드 스크립트가 하나라도 있으면 죽는다.
   **지시**: electron-builder를 포함한 **전체 설치를 한 번 돌려** pnpm이 써넣는 플레이스홀더를
   전부 확인하고 값을 정해 커밋한 **다음에** 첫 CI를 돌린다. 현재까지 알려진 값 —
   **`esbuild: true`(필수)**, `electron-winstaller: false`(Squirrel Windows 타깃을 쓰지 않는다),
   **`electron` 항목은 불필요**(42부터 postinstall이 없어 pnpm이 플래그하지 않는다).
7. **`minimumReleaseAge` 공급망 정책이 걸려 있다.** 갓 릴리스된 버전은 거부된다(실제로 turbo
   2.10.12가 막혀 2.10.11로 내렸다). 필요하면 `pnpm-workspace.yaml`의
   `minimumReleaseAgeExclude`에 명시한다. 거부된 항목이 lockfile에 남으면
   `pnpm clean --lockfile` 후 재설치한다. **`--frozen-lockfile`은 resolution을 건너뛰므로 CI에는
   사실상 무해하다** — 영향을 받는 것은 로컬 `pnpm add`/`update`다. 실무 규칙 하나로 충분하다:
   **막 나온 버전으로 lockfile을 갱신한 직후에 릴리스를 자르지 않는다.**
8. **플랫폼별 lockfile 문제는 존재하지 않는다.** pnpm은 optionalDependencies를 플랫폼과 무관하게
   lockfile에 다 적고 설치할 때만 자기 것을 고른다(`@typescript/typescript-win32-x64`,
   `@esbuild/win32-*`, `@biomejs/cli-win32-*`, `@turbo/windows-*` 전부 기록되는 것을 실측).
   **`supportedArchitectures`를 설정하지 마라.** Windows 러너의 `--frozen-lockfile`은 그냥
   성공한다. (TS 7의 패키지 이름은 `@typescript/native-preview-*`가 아니라
   **`@typescript/typescript-<os>-<arch>`** 형식이다.)
9. **`electron.build` 문서 사이트를 설정 근거로 쓰지 마라.** 그 사이트는 `master` 브랜치
   (= **v27 알파**)를 렌더링한다. 조사 중 실제로 **존재하지 않는 옵션(`mac.sign.identity`)이
   만들어졌고** 소스 확인으로 걸러졌다. 근거로 쓸 것은 **`26.15.7` 태그**의 `website/docs/`나
   `packages/app-builder-lib/src/options/*.ts` 원문이다.
10. **electron-builder 버전은 `26.15.7`로 정확히 핀한다.** npm `latest` 태그가 **26.15.3에
    멈춰 있어** `pnpm add -D electron-builder`를 그냥 치면 26.15.3이 들어온다. pnpm v11
    워크스페이스를 다루는 코드가 26.15.x 소스에 있으므로 최신 패치가 안전하다.
11. **electron-builder 저장소 문서 전체에 "pnpm"이라는 단어가 한 번도 나오지 않는다.**
    pnpm 지원은 소스와 테스트 픽스처에만 있다. **패키징에서 문제가 나면 문서가 아니라 소스와
    이슈 트래커를 봐야 한다.** 모르면 없는 문서를 찾느라 시간을 쓴다.
12. **`electron-vite` 출력(`out/`)과 `electron-builder` 출력(`release/`)을 갈라 둔다.**
    프로토타입에서 둘 다 `dist/`를 써 **asar가 자기 자신을 삼켜 320MB**가 됐다.
13. **`externalizeDepsPlugin`에 `exclude: ['@yeoncha/core']`를 넣지 마라.** 코어를
    `devDependencies`에 두는 것으로 대체된다(8.4절). 넣으면 불필요한 설정이 남는다.
    **이 축의 실패는 개발 중에 보이지 않고 패키징된 앱만 실행 시점에 깨진다** — 첫 패키징에서
    `asar list`로 확인하는 것이 그래서 필수다.
14. **트레이 라벨은 `Math.floor`다.** 프로토타입 코드가 `Math.trunc`로 구현돼 있다.
    그대로 옮기면 `-0.25`가 `0`으로 보여 **초과 노출 결정이 조용히 무효화된다**(4.2절).
15. **6.1절의 짝수 강제를 단순화하지 마라.** `round(size * 0.125)`로 줄이면 20px에서 반 픽셀이
    남아 이 글리프를 고른 유일한 근거(안티에일리어싱 0)가 사라진다.

## Testing Decisions

**좋은 테스트는 외부 동작만 고정한다.** 함수 내부 구조가 아니라 **입력과 출력**을 본다.
이 앱에서는 그게 자연스럽다 — 코어가 전부 순수 함수이고, "오늘"까지 인자이므로 날짜 경계
동작도 표로 표현된다.

**저장소가 비어 있으므로 참고할 기존 테스트(prior art)가 없다.** 이 절이 최초 기준이며,
이후 테스트는 여기서 확립한 모양(표 기반, 순수 함수, 날짜를 인자로)을 따른다.

### seam은 셋이다

가장 높은 곳에 세 개, 그 이상 만들지 않는다.

| seam | 테스트가 고정하는 것 |
| --- | --- |
| **계산** `(입사일, 기준방식, 휴가 기록, 조정, 오늘) → 발생 목록 + 잔여` | 아래 케이스 테이블 14건이 이 경계에 그대로 앉는다 |
| **표시** `formatTrayLabel(잔여, { maxGlyphs })` | `Math.floor` 대 `Math.trunc`가 `-0.25`에서 갈리는 것 |
| **직렬화** `parse` / `serialize` | 미래 `schemaVersion` 거부, 구조 검증, 중복 `date` 거부 |

**셸(`apps/desktop`)은 v1에서 자동 테스트하지 않는다.** 트레이·IPC·파일 I/O는 프로토타입이
실측으로 확인했고, Electron 통합 테스트 하네스는 사용자 한 명짜리 도구에서 값을 못 한다.
그 대신 8.1절의 `ci.yml`이 양 OS에서 빌드가 되는 것을 커밋마다 확인한다.

| B | 2024-12-31 | 월차 11건 | **11** | 최초 1년의 마지막 날. **이날은 아직 유효하다** |
| C | 2025-01-01 | 연차 15일 (소멸 2025-12-31) | **15** | 월차 소멸과 15일 발생이 같은 경계. **26이 뜨는 순간은 없다** |

| --- | --- | --- |

**J. 미래 예정** — I 데이터 + `2026-02-10 ~ 02-12` 3일 예정, 조회일 2025-12-01

3일은 2026-01-01 발생분에 배정된다. 잔여 = **5**(2025년분 15 − 10). 단순 뺄셈이면 2.

**K. 초과 사용** — 2024-01-01 입사, 2025-03월에 18일 사용 (15일 배정, 3일 미배정)

| 조회일 | 잔여 | |
| --- | --- | --- |
| 2025-06-01 | **−3** | 초과가 트레이에 그대로 뜬다 |
| 2026-01-05 | **15** | 2025년분이 소멸하며 **초과 3일도 함께 사라진다** |

**L. 조정으로 초과 풀기** — K에 조정 `발생일 2025-01-01 / 소멸일 2025-12-31 / +5일` 추가

2025-03월 18일이 연차 15 + 조정 3으로 배정된다(소멸일 동률 → 발생일 동률 → `annual` →

소급되면 2026-01-05 잔여가 **17**(조정 잔량 2 + 2026년분 15)이고, 발생일이 입력일로 고정됐다면
**20**이 되어 초과 3일이 공짜로 생긴다.

| 조회일 | 잔여 |
| --- | --- |
| 2024-02-28 | **0** |
| 2024-02-29 | **1** |

**N. 회계연도 겹침의 최댓값** — 2024-01-15 입사, 회계연도 기준

월차 11건(소멸 2025-01-14)과 비례분 `15 × 11/12 = 13.75`(2025-01-01 발생)가 2주간 겹친다.

| 조회일 | 잔여 |
| --- | --- |
| 2025-01-10 | **24.75** |
| 2025-01-15 | **13.75** |

### 표시 seam이 고정할 것

| 잔여 | `maxGlyphs: Infinity` (macOS) | `maxGlyphs: 3` (Windows) |
| --- | --- | --- |
| `12.75` | `12.75` | `12` |
| `-24.75` | `-24.75` | `-25` |
| `-0.25` | `-0.25` | `-1` (**`0`이면 실패다**) |
| `0` | `0` | `0` |

### 직렬화 seam이 고정할 것

- `schemaVersion`이 앱보다 높으면 `future-version`으로 거부한다.
- JSON 파싱 실패는 `invalid-json`, 구조·타입·필수 필드 위반은 `schema-mismatch`.
- `entries`에 중복 `date`가 있으면 거부한다(하루 1건 불변식).
- **도메인 이상치는 통과시킨다** — 입사일 이전 휴가 기록, 0.25 배수가 아닌 일수, 소멸일이
  발생일보다 이른 조정. 이걸 거부하면 **앱이 자기가 쓴 파일을 못 읽는다**(5.4절의 삭제 거절).
- `serialize(parse(x)) === x`가 성립하는 왕복(2칸 들여쓰기).

## Out of Scope

[지도](map.md)의 Out of scope 섹션과 일치한다.

- **코드서명·공증(notarization).** Windows는 2024년부터 EV 인증서도 SmartScreen 즉시 평판을
  주지 않아 **지불해도 목표를 달성하지 못하고**, macOS만 서명하는 것은 사용자 0~1명 단계에서
  연 $99의 값을 못 한다. 파이프라인에 훅 자리만 비워둔다(8.4절).
  **재검토 트리거**: 실제 사용자가 경고 때문에 못 쓰겠다고 보고하면 macOS 서명부터 켠다.
- **자동 업데이트.** macOS 자동 업데이트는 코드 서명이 전제라 서명을 뺀 이상 성립하지 않는다.
  v1은 Release 페이지 수동 재다운로드다.
- **과거 회사 기록 보관(이직 이력).** 이직하면 계속근로연수가 리셋되어 잔여는 새 입사일
  하나에서만 나오므로, 전 직장 기록을 남겨도 **잔여가 달라지지 않는다.** 스키마에 회사 개념을
  넣지 않는다. 입사일 교체 시 이전 기록을 지울지 묻는 것으로 끝낸다.
- **HR·그룹웨어 시스템 연동.** 회사 시스템에서 잔여를 자동으로 끌어오는 것.
- **팀 공유·서버 백엔드·다중 사용자.** 서버가 생기는 순간 개인 도구가 아니다.
- **클라우드 동기화.** 단 **로컬 파일 내보내기·가져오기는 범위 안**이다(v2 이관 경로로 필요).
- **캘린더 연동**(Google Calendar, macOS 캘린더). 휴가 등록 시 일정 생성.
- **v2 PWA 구현 자체.** 코어를 재사용 가능하게 만드는 것까지가 v1의 몫이다.
- **소멸 알림·사용 촉진.** OS 알림으로 소멸 임박을 알리는 것. 알림 권한과 백그라운드 스케줄링을
  끌고 들어오며 "진짜 단순한 앱" 전제와 맞지 않는다. 소멸 인지는 5.7절의 두 경로가 전부다.
- **결근일 입력과 출근율 판정**(3.8절). 100% 출근을 고정 가정한다.
- **퇴사·퇴직 정산**(3.2절). 앱은 퇴사를 모른다.
- **회계연도 개시일 설정**(3.2절). 1/1 고정이다.
- **"오늘"의 시간대 설정**(7.3절). `Asia/Seoul` 고정이다.
- **저장 경로 설정**(2절). 열면 클라우드 동기화를 뒷문으로 끌고 들어온다.

## Further Notes

### 확정 전제 — 이 스펙 안에서 재논의하지 않는다

지도가 못 박은 것들이다. 뒤집으려면 목적지를 다시 그려야 한다.

- 코어 계산 엔진은 **순수 TypeScript 패키지**. Rust/WASM 아님.
- UI는 **React**.
- 배포는 **GitHub Release**. AI 에이전트가 OS별 바이너리를 올린다(태그를 미는 것도 에이전트다).
- v2는 Next.js 기반 **PWA**가 유력하며 코어 패키지가 그대로 넘어갈 수 있어야 한다.
- **잔여 = 발생 − (사용 + 예정)**. 예정도 잔여에서 차감한다.
- **진짜 단순한 앱이다.** 기능 추가 제안은 *"이게 없으면 잔여가 틀리는가"* 를 통과해야 한다.
- **용어는 [`CONTEXT.md`](../../CONTEXT.md)가 유일한 출처다.**

### 아직 검증하지 못한 것

이 스펙의 결정 중 실측으로 닫히지 않은 것들이다. **구현이 처음 확인하게 된다.**

   (a) 16px 알림 영역에서 `-25`와 `12`가 읽히는가, (b) 대시 8×2px이 보이는가,
   (c) 달력 셀·380px 폭·시스템 폰트가 성립하는가,
   (d) 트레이 우클릭에 `[종료]` 메뉴가 뜨고 **좌클릭이 여전히 팝오버를 토글하는가**(4.6절 —
   `setContextMenu`였다면 여기서 죽는다), (e) 종료 후 알림 영역에 아이콘이 남지 않는가.
   **틀렸을 때의 후퇴**: 숫자는 24px 이상에서만 쓰고 16px에서는 아이콘으로 내려간다.
   대시는 두께를 4px로 올린다(24px에서 이미 쓰는 값). **어느 쪽도 결정 구조를 바꾸지 않는다.**
2. **`@yeoncha/core`가 번들에 실제로 인라인되는지**(8.4절). 문서화된 동작이지만 실행으로
   확인하지 않았다. **틀리면 패키징된 앱만 실행 시점에 죽는다** — 개발 중에는 보이지 않는다.
   첫 패키징에서 `asar list`로 확인한다.
3. **`electron-vite` 통합 자체를 돌려보지 않았다.** 실험 워크스페이스는 esbuild로 main을
   번들해 세 타깃 빌드와 개발 루프를 대신 확인했다.
4. **워크플로를 실제로 돌리지 않았다.** `allowBuilds`의 완전한 목록도 첫 전체 설치에서 확정된다.
5. **`hardenedRuntime: false`가 `identity: null`에도 필요한지**(8.4절). 문서 경고문이 모호해
   안전한 쪽으로 뒀다. 32번 티켓에서 `hardenedRuntime: false` + ad-hoc 서명(afterPack 훅)
   조합으로 만든 v0.1.3 릴리스 DMG가 `codesign --verify --deep --strict` 통과, `spctl`
   "rejected"(정상적인 미서명 거부, "damaged" 아님)로 확인됐다 — 지금 조합이 실행을 막지는
   않는다는 근거는 생겼다. 다만 이 경고문은 원래 **공증(notarization)** 문맥의 것이라,
   실제로 유료 서명·공증을 켤 때(8.4절의 "나중에 켤 때의 4단계") `hardenedRuntime: true`가
   필요한지는 여전히 별도로 확인해야 한다 — 그 시점까지는 열려 있다.
6. **macOS 메뉴바에서 템플릿 반전을 눈으로 확인하지 못했다.** `setTemplateImage(true)`는
   검증된 메커니즘이고 캡처는 CSS `invert`로 흉내 낸 것이다.
7. **`.dmg`/`.zip`의 quarantine 차이와 `nsis`/`portable`의 SmartScreen 차이.** 어느 1차 문서에서도
   확인하지 못했다. **8.3절의 결정은 이 축에 기대지 않는다**(각각 자동 업데이트 범위와 데이터
   위치 논거로 결정했다). 첫 릴리스를 다른 기기에서 내려받아 8.5절의 안내가 맞는지 확인한다.
8. **트레이 폰트를 정하지 않았다.** 프로토타입은 플랫폼 기본 스택을 썼다. 숫자만 그리므로
   tabular numerals 여부가 폭에 영향을 준다.
9. **Windows 알림 영역의 실제 DPI 분포를 모른다.** 16px(100%)이 여전히 흔한지에 따라 1번의
   후퇴가 필요한지가 갈린다.

### 의도적으로 남긴 구멍

**빠뜨린 것이 아니다.** 각각 지금 넣지 않기로 한 것이며 불가능한 게 아니다.

- **오늘 등록이 3클릭이다.** 가장 흔한 조작인데 별도 창 안이었다면 1클릭이었다. 진입을 달력
  하나로 유지하는 대가다. 써보고 거슬리면 트레이 우클릭 메뉴나 바로가기를 다시 검토한다.
- **README 스크린샷을 v1에 넣지 않는다**(8.5절). 첫 릴리스를 내려받는 순간이 찍을 시점이다.
- **사용자가 이월 조정을 넣기를 까먹으면 잔여가 실제보다 적게 보인다.** 완화책은 두 겹이다 —
  발생분 행의 소멸일·D-day가 타이밍을 알리고, 초과가 나면 음수가 트레이에 그대로 떠서
  "넣을 것이 남았다"를 알린다.
- **대시가 음수 잔여의 부호와 혼동될 여지가 있다.** 숫자가 붙으면 구분되지만 대시 하나만 있는
  상태를 "부호만 남고 숫자가 잘렸다"로 읽을 수 있다. 툴팁이 이 간극을 메운다.
- **Temporal 폴리필을 네이티브로 갈아탈 시점을 정하지 않았다.** Node LTS와 주요 브라우저에
  전부 들어온 뒤에 다시 볼 일이고, 그때 바꾸는 것은 import 한 줄이다.

### ADR은 둘이다

지도의 목적지는 ADR 하나(셸 프레임워크)를 명시했고, **이 스펙이 두 번째를 하나 추가한다.**

- **[ADR-0001 — 셸 프레임워크로 Electron을 쓴다](../../docs/adr/0001-electron-as-shell-framework.md)**
- **[ADR-0002 — 날짜는 Temporal.PlainDate로 다룬다](../../docs/adr/0002-temporal-plaindate-for-dates.md)**

날짜 라이브러리를 ADR로 올린 근거는 세 조건을 다 만족한다는 것이다. 특히 **되돌리기 비용**이
결정적이다 — 폴리필을 네이티브로 바꾸는 것은 import 한 줄이지만, `Temporal`을 `Date` 기반
라이브러리로 바꾸는 것은 **코어의 모든 날짜 산술을 다시 쓰는 것**이고 그게 제품 전부다.
그리고 근거 없이는 놀라운 선택이 둘 있다 — 네이티브가 있는 렌더러에서도 폴리필을 쓰는 것,
그리고 시간대를 고정하는 것. 둘 다 "최적화"라며 되돌릴 수 있는 모양이고 되돌리면 v1과 v2가
다른 숫자를 낸다. ADR이 정확히 이걸 막는다.

**"릴리스를 쓰는 잡이 하나"는 ADR로 만들지 않았다.** 근거 없이는 놀랍다는 조건은 만족하지만
되돌리기가 CI 파일 한 줄이고, 그 한 줄이 있는 자리에서 8.2절의 이유를 주석으로 지킬 수 있다.
코드베이스 전체를 관통하는 결정이 아니라 파이프라인 국소 결정이므로 스펙과 워크플로 주석에
남긴다. ADR을 늘리면 ADR을 읽지 않게 된다.

### 이 스펙이 앞선 결정을 교정한 곳

- **트레이의 "입사일 미설정 = 앱 아이콘"은 구현할 수 없다** → **대시**로 바꿨다(6절).
  512px 앱 아이콘을 16px로 줄이면 파란 얼룩이 된다.
- **`externalizeDepsPlugin({ exclude: ['@yeoncha/core'] })`는 넣지 않는다** → 코어를
  `devDependencies`에 두는 것으로 대체된다(8.4절).
- **`supportedArchitectures`는 필요 없다** → 플랫폼별 lockfile 문제는 존재하지 않는다(9절 8번).
- **`allowBuilds`의 `electron` 항목은 불필요하다** → 필요한 것은 `esbuild: true`다(9절 6번).
- **CI에서 `fetch-depth` 조정은 필요 없다** → turbo 캐시에 기대지 않는다(9절 1번).
- **"팝오버가 열린 채 우클릭하면 `blur`가 먼저 돌아 자연히 닫힌다"는 가정은 틀렸다** →
  `popUpContextMenu`가 동기 호출이라 메뉴가 떠 있는 동안 `blur`가 돌 기회가 없다. `createTray`에
  `onWillShowMenu` 콜백을 추가해 메뉴를 띄우기 직전에 명시적으로 닫는 것으로 바꿨다(4.6절,
  30번 티켓 실물 검증에서 발견).

### 새로운 결정이 필요해지면

**이 스펙에서 얼버무리지 마라.** 구현 중에 결정이 필요해지면 그건 앞선 결정 티켓이 덜 닫혔다는
신호다. 해당 티켓([지도](map.md)의 Decisions so far에서 찾는다)을 다시 열고, 거기서 결정하고,
스펙을 갱신한다.
