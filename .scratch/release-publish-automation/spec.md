# 대화형 릴리스 게시 자동화

Status: ready-for-agent

## Problem Statement

릴리스 담당자는 새 버전을 게시할 때마다 데스크톱 앱 버전을 직접 수정하고, 릴리스 준비
커밋을 만들고, `main`을 push하고, 같은 버전의 Git 태그를 만들고, 다시 push한 뒤 GitHub
Actions와 GitHub Release를 따로 확인해야 한다. 각 단계의 순서와 버전 일치 조건을 사람이
기억해야 하므로 반복 작업이 번거롭고, 실패한 CI 커밋에 태그를 붙이거나 잘못된 버전의
Release를 만드는 실수가 발생하기 쉽다.

현재 GitHub Release는 `v*` 태그 push를 시작점으로 삼고 데스크톱 앱 manifest의 버전을
유일한 버전 출처로 사용한다. 따라서 태그를 릴리스 브랜치로 대체할 수 없으며, 버전 변경은
태그가 가리킬 커밋에 포함되어야 한다. 이미 버전 커밋이 `origin/main`에 push된 경우도 있어
매번 같은 준비 단계를 강제로 반복해서도 안 된다.

릴리스 담당자는 기존 pre-push 검증과 원격 CI·Release 워크플로를 우회하지 않으면서, 하나의
명령으로 현재 상태에 맞는 안전한 다음 단계를 안내받고 실제 macOS 설치 파일이 공개됐는지까지
확인하고 싶다.

## Solution

루트에 대화형 `pnpm publish-release` 명령을 제공한다. 명령은 저장소와 GitHub의 현재 상태를
먼저 검사하고, 새 버전이 필요하면 patch·minor·major·직접 입력 선택지와 계산된 버전을
보여준다. 기본 추천은 patch 증가이며 모든 실행은 사용자와 상호작용한다.

명령은 선택한 버전을 데스크톱 앱 manifest에 반영하고 한국어 릴리스 준비 커밋을 만든다.
원격 변경 전에 대상 커밋, 버전, 태그와 포함될 로컬 커밋을 요약하고 명시적 확인을 받는다.
그 뒤 `main`을 push하고 정확히 그 커밋의 CI 성공을 기다린다. CI가 성공한 경우에만 같은
커밋을 가리키는 `v<version>` 주석 태그를 만들고 해당 태그 하나만 push한다.

태그 push로 시작된 Release 워크플로가 끝날 때까지 기다린 뒤, GitHub Release가 초안이나
시험판이 아닌 공개 상태이고 대상 커밋과 macOS Apple Silicon DMG 이름이 모두 기대값과
일치하는지 확인한다. 이 확인까지 통과해야 명령이 성공한다.

현재 manifest가 아직 사용되지 않은 버전이고 그 버전 커밋이 이미 `origin/main`에 있다면
버전 수정, 커밋과 `main` push를 건너뛰고 확인 후 태그 단계부터 진행한다. 실패 시 자동으로
커밋이나 태그를 삭제하거나 훅을 우회하지 않고, 보존된 상태와 안전한 재시도 방법을 알려준다.

## User Stories

1. 릴리스 담당자로서 하나의 명령으로 릴리스 게시 흐름을 시작하고 싶다. 그래야 여러 수동 명령의 순서를 외우지 않아도 된다.
2. 릴리스 담당자로서 현재 앱 버전과 최신 공개 릴리스 버전을 함께 보고 싶다. 그래야 어떤 버전을 게시하는지 판단할 수 있다.
3. 릴리스 담당자로서 patch·minor·major 선택지를 보고 싶다. 그래야 SemVer 의도를 명확하게 표현할 수 있다.
4. 릴리스 담당자로서 patch 증가 버전을 기본 추천으로 받고 싶다. 그래야 일반적인 수정 릴리스를 빠르게 준비할 수 있다.
5. 릴리스 담당자로서 Enter만 눌러 추천 patch 버전을 선택하고 싶다. 그래야 반복 릴리스의 입력 비용을 줄일 수 있다.
6. 릴리스 담당자로서 필요한 경우 버전을 직접 입력하고 싶다. 그래야 일반 증가 규칙으로 표현하기 어려운 다음 버전을 선택할 수 있다.
7. 유지보수자로서 잘못된 SemVer 입력이 거부되기를 원한다. 그래야 워크플로와 패키지 도구가 해석할 수 없는 버전이 저장되지 않는다.
8. 유지보수자로서 기존 태그나 공개 릴리스보다 높지 않은 버전이 거부되기를 원한다. 그래야 버전 계보가 역행하거나 중복되지 않는다.
9. 유지보수자로서 시험판 버전이 이 명령으로 게시되지 않기를 원한다. 그래야 현재의 안정 릴리스 계약을 유지할 수 있다.
10. 릴리스 담당자로서 버전 변경이 데스크톱 앱의 권위 있는 버전 출처에만 반영되기를 원한다. 그래야 중복된 버전 출처가 생기지 않는다.
11. 릴리스 담당자로서 버전 변경이 자동으로 커밋되기를 원한다. 그래야 manifest 수정과 커밋을 반복해서 수동 수행하지 않아도 된다.
12. 유지보수자로서 자동 커밋 메시지가 한국어 릴리스 규칙을 따르기를 원한다. 그래야 저장소 커밋 기록이 일관된다.
13. 릴리스 담당자로서 원격 변경 전에 최종 커밋, 버전, 태그와 push 대상을 확인하고 싶다. 그래야 실수한 입력을 취소할 수 있다.
14. 릴리스 담당자로서 확인을 거부하면 원격 저장소가 변경되지 않기를 원한다. 그래야 검토가 실제 통제 지점으로 기능한다.
15. 유지보수자로서 명령이 `main`에서만 실행되기를 원한다. 그래야 기능 브랜치나 임시 브랜치를 실수로 릴리스하지 않는다.
16. 유지보수자로서 작업 트리가 깨끗하지 않으면 명령이 변경 전에 중단되기를 원한다. 그래야 사용자 변경을 릴리스 준비 커밋에 섞지 않는다.
17. 유지보수자로서 실행 전에 원격 브랜치와 태그를 새로 조회하기를 원한다. 그래야 오래된 로컬 참조를 기준으로 중복 릴리스를 만들지 않는다.
18. 릴리스 담당자로서 로컬과 원격 `main`이 갈라졌다면 자동 병합 없이 중단되기를 원한다. 그래야 릴리스 명령이 소스 통합 결정을 대신하지 않는다.
19. 릴리스 담당자로서 로컬 `main`이 원격보다 뒤처졌다면 자동 pull 없이 중단되기를 원한다. 그래야 예기치 않은 코드가 자동으로 합쳐지지 않는다.
20. 릴리스 담당자로서 원격보다 앞선 로컬 커밋이 있다면 그 목록을 확인하고 포함 여부를 승인하고 싶다. 그래야 게시될 변경 범위를 알 수 있다.
21. 릴리스 담당자로서 이미 준비한 미게시 버전이 현재 커밋에 있다면 새 버전으로 다시 올리지 않기를 원한다. 그래야 버전이 불필요하게 건너뛰지 않는다.
22. 릴리스 담당자로서 미게시 버전 커밋이 이미 `origin/main`에 있다면 `main` push를 생략하고 싶다. 그래야 이미 끝난 단계를 반복하지 않는다.
23. 유지보수자로서 현재 버전의 원격 태그가 이미 있으면 중복 태그 생성 전에 중단되기를 원한다. 그래야 존재하는 Release 이력을 덮어쓰지 않는다.
24. 유지보수자로서 태그는 반드시 릴리스 대상 커밋을 가리키기를 원한다. 그래야 manifest 버전과 배포 소스의 출처가 일치한다.
25. 유지보수자로서 릴리스 태그가 `v<version>` 형식의 주석 태그이기를 원한다. 그래야 기존 워크플로 트리거와 태그 기록 계약을 유지할 수 있다.
26. 유지보수자로서 태그 메시지가 태그 이름과 같은 버전을 명시하기를 원한다. 그래야 태그 자체를 조회해도 릴리스 정체를 알 수 있다.
27. 릴리스 담당자로서 `main` push가 기존 pre-push 훅을 그대로 실행하기를 원한다. 그래야 기본 검증과 전면 Electron 제품 흐름을 우회하지 않는다.
28. 릴리스 담당자로서 `main` push 후 정확히 같은 커밋의 원격 CI를 기다리고 싶다. 그래야 다른 커밋의 성공 결과를 릴리스 근거로 잘못 사용하지 않는다.
29. 릴리스 담당자로서 해당 CI가 실패하거나 취소되면 태그가 생성되지 않기를 원한다. 그래야 실패한 커밋이 릴리스 후보로 고정되지 않는다.
30. 릴리스 담당자로서 CI 실행이 GitHub에 나타나는 짧은 지연을 명령이 처리하기를 원한다. 그래야 실행 검색의 일시적 빈 결과가 즉시 실패로 오해되지 않는다.
31. 릴리스 담당자로서 CI 성공 뒤 해당 버전 태그 하나만 push하고 싶다. 그래야 관계없는 로컬 태그를 함께 게시하지 않는다.
32. 유지보수자로서 태그 push도 기존 pre-push 검증을 다시 실행하기를 원한다. 그래야 첫 버전에서 안전 계약을 최적화 명목으로 약화하지 않는다.
33. 릴리스 담당자로서 태그 push가 시작한 정확한 Release 워크플로를 기다리고 싶다. 그래야 다른 릴리스 실행 결과와 섞이지 않는다.
34. 릴리스 담당자로서 워크플로 성공만이 아니라 GitHub Release 공개 상태를 확인하고 싶다. 그래야 작업 시작을 게시 완료로 오해하지 않는다.
35. 릴리스 담당자로서 Release가 정확한 태그와 전체 커밋 SHA를 대상으로 하는지 확인하고 싶다. 그래야 다른 코드가 잘못 배포되지 않는다.
36. 릴리스 담당자로서 예상한 macOS Apple Silicon DMG가 Release 자산에 있는지 확인하고 싶다. 그래야 사용자가 실제 설치 파일을 받을 수 있다.
37. 릴리스 담당자로서 성공 결과에서 버전, 태그, 커밋, Release URL과 DMG 이름을 보고 싶다. 그래야 게시 결과를 기록하고 공유할 수 있다.
38. 릴리스 담당자로서 필요한 Git 또는 GitHub 도구와 인증이 없으면 변경 전에 명확히 실패하기를 원한다. 그래야 중간 상태를 만들기 전에 환경을 복구할 수 있다.
39. 릴리스 담당자로서 `main` push 실패 시 로컬 커밋이 보존되기를 원한다. 그래야 원인을 고친 뒤 같은 준비 작업을 재사용할 수 있다.
40. 릴리스 담당자로서 태그 push 실패 시 로컬 태그가 보존되기를 원한다. 그래야 태그를 다시 만들지 않고 안전하게 재시도할 수 있다.
41. 릴리스 담당자로서 Release 워크플로 실패 시 원격 태그가 자동 삭제되지 않기를 원한다. 그래야 실패 원인을 추적하고 같은 워크플로를 재실행할 수 있다.
42. 유지보수자로서 명령이 원격 태그 삭제, 강제 push 또는 검증 훅 우회를 하지 않기를 원한다. 그래야 복구 과정이 새로운 파괴적 변경을 만들지 않는다.
43. 릴리스 담당자로서 실패 지점별로 현재 보존된 상태와 다음 재시도 방법을 보고 싶다. 그래야 무작정 처음부터 다시 시작하지 않는다.
44. 유지보수자로서 릴리스 본문은 기존의 체크인된 안내를 계속 사용하기를 원한다. 그래야 업로드 자동화가 릴리스 문안 계약까지 확장되지 않는다.
45. 유지보수자로서 자동화된 테스트와 실제 GitHub 게시 증거가 구분되기를 원한다. 그래야 가짜 명령 테스트를 실제 배포 성공으로 오해하지 않는다.

## Implementation Decisions

- 루트 패키지는 인자 없이 시작하는 대화형 `publish-release` 명령을 제공한다. 확인을 생략하는
  `--yes` 또는 그와 동등한 비대화형 경로는 제공하지 않는다.
- 오케스트레이션은 저장소가 지원하는 macOS 셸 환경에서 실행되는 셸 스크립트로 구현한다.
  JSON 처리나 버전 계산에 저장소의 고정된 Node 런타임을 보조적으로 사용할 수 있지만 별도의
  전역 패키지를 요구하지 않는다.
- 실행 전 필수 도구, GitHub CLI 인증, 저장소 루트, `main` 브랜치, 깨끗한 작업 트리와 `origin`
  접근을 확인한다. 사전 조건 실패는 파일, 커밋, 태그와 원격 참조를 변경하지 않는다.
- 원격 `main`과 `v*` 태그를 fetch한 뒤 로컬 `main`의 ahead·behind·diverged 상태를 판별한다.
  behind 또는 diverged 상태는 자동 pull·merge·rebase 없이 중단한다.
- 로컬 `main`이 ahead 상태이면 포함될 커밋을 최종 요약에 표시한다. 대화형 확인을 받은 경우에만
  현재 `main` 전체를 릴리스 대상으로 push한다.
- 데스크톱 앱 manifest의 `version`이 버전의 유일한 로컬 출처다. 최신 공개 안정 Release와
  원격 태그도 조회해 이미 사용된 버전을 판별한다. 태그는 있지만 Release가 없는 버전은 새
  버전으로 덮어쓰지 않고 기존 워크플로 복구 대상으로 보고 중단한다.
- 현재 manifest 버전이 아직 사용되지 않았고 현재 커밋에 이미 포함되어 있으면 이를 준비된
  릴리스 버전으로 제안한다. 그 커밋이 `origin/main`과 같으면 manifest 수정, 커밋과 `main`
  push를 생략한다.
- 새 버전이 필요하면 현재 안정 버전을 기준으로 patch·minor·major 결과와 직접 입력 선택지를
  표시한다. patch가 기본 추천이며 빈 입력은 patch를 선택한다.
- 직접 입력을 포함한 모든 후보는 숫자로 구성된 정식 SemVer이고 기존 안정 버전보다 높아야
  한다. prerelease와 build metadata는 현재 안정 릴리스 전용 명령에서 허용하지 않는다.
- 선택한 버전은 데스크톱 앱 manifest에 반영한다. 자동 커밋은 버전 변경에 필요한 명시적 파일만
  stage하며 다른 파일을 포괄적으로 stage하지 않는다.
- 자동 커밋 메시지는 `릴리스: v<version> 준비` 형식을 사용한다. 이미 준비된 버전 커밋을
  감지한 경우 중복 커밋을 만들지 않는다.
- 첫 원격 변경 전에 버전, 전체 커밋 SHA, 로컬 ahead 커밋, `main` push 필요 여부, 생성할 태그와
  원격 이름을 출력하고 명시적 확인을 받는다. 거절하거나 입력 스트림이 대화형이 아니면 원격을
  변경하지 않고 종료한다.
- `main` push는 일반 Git push를 사용하고 기존 pre-push 훅을 우회하지 않는다. 훅의 기본 검증과
  전면 Electron 제품 흐름이 실패하면 push와 후속 태그 생성을 중단한다.
- `main` push 뒤 정확한 전체 커밋 SHA로 시작된 CI push 실행을 찾는다. GitHub의 최종 일관성에
  따른 검색 지연은 제한된 재시도로 흡수하되, 다른 커밋이나 pull request 실행의 성공을
  대체 증거로 사용하지 않는다.
- 해당 CI가 성공해야만 태그 단계로 진행한다. 실패, 취소, 건너뜀, 시간 초과 또는 실행을 찾지
  못한 상태는 모두 실패이며 태그를 생성하지 않는다.
- 릴리스 태그는 동일한 전체 커밋 SHA를 가리키는 `v<version>` 형식의 주석 태그다. 태그 메시지는
  태그 이름과 동일하다.
- push는 `--tags`가 아니라 이번에 생성하거나 확인한 태그 하나를 명시한다. 태그 push에서도
  기존 pre-push 검증이 다시 실행되는 현재 계약을 유지한다.
- 이미 같은 이름의 로컬 또는 원격 태그가 있으면 대상 SHA와 무관하게 새 태그 생성이나 덮어쓰기를
  시도하지 않는다. 원격 태그 삭제와 강제 push도 하지 않는다.
- 태그 push 뒤 정확한 태그로 시작된 Release 워크플로를 기다린다. 성공 뒤 공개된 GitHub Release가
  draft와 prerelease가 아니고, 태그와 대상 전체 SHA가 기대값과 같은지 확인한다.
- 성공 판정에는 `yeonchamyeotgae-<version>-arm64.dmg` 자산 존재 확인이 포함된다. 이는 현재
  macOS Apple Silicon 단일 지원 계약을 따른다.
- 성공 시 버전, 태그, 전체 SHA, Release URL과 확인한 DMG 이름을 요약한다. 단순 태그 push나
  워크플로 시작은 성공으로 보고하지 않는다.
- 실패 시 이미 만들어진 로컬 버전 커밋, 로컬 태그 또는 원격 태그를 자동 삭제하지 않는다.
  실패 단계, 보존 상태와 안전한 재실행·워크플로 재실행 방법을 출력한다.
- 릴리스 본문은 기존 체크인된 정적 안내를 계속 사용한다. 릴리스 노트 입력이나 커밋 기반 자동
  생성은 추가하지 않는다.
- 릴리스 안내 문서는 새 단일 명령을 기본 절차로 설명하되, 태그가 GitHub Release의 정체성과
  트리거라는 기존 계약 및 수동 복구에 필요한 핵심 명령을 보존한다.
- 기존 CI, Release, pre-push 책임을 스크립트 안으로 복제하지 않는다. 스크립트는 이 경계들을
  순서대로 호출하고 결과를 확인하는 오케스트레이터다.

## Testing Decisions

- 주 테스트 seam은 셸 명령을 임시 Git 저장소에서 블랙박스로 실행하는 하나의 Node 테스트
  하네스다. PATH 앞에 기록 가능한 가짜 GitHub CLI와 필요한 외부 명령을 두고, 표준 입력,
  표준 출력, 종료 코드, manifest 결과, Git 커밋·태그 상태와 외부 명령 순서를 관찰한다.
- 테스트는 내부 셸 함수 이름이나 구현 줄을 단언하지 않는다. 사용자에게 보이는 프롬프트와
  요약, 저장소 상태, 생성된 커밋·태그, push 순서, 실패 시 원격 변경 부재처럼 외부 행동만
  검증한다.
- 정상 경로는 patch 기본값, minor, major와 유효한 직접 입력을 각각 검증한다. 자동 커밋 메시지,
  `main` push, 정확한 SHA의 CI 대기, 주석 태그와 해당 태그 하나의 push, 공개 Release와 예상
  DMG 확인 순서를 관찰한다.
- 이미 준비된 미게시 manifest 버전이 `origin/main`에 있는 fixture에서는 manifest 변경과 커밋,
  `main` push 없이 태그와 Release 확인만 수행하는지 검증한다.
- 로컬 `main`이 ahead인 fixture에서는 커밋 목록이 최종 확인에 표시되고, 승인한 경우 그 HEAD를
  push하며 거부한 경우 원격 변경이 없는지 검증한다.
- 비 `main` 브랜치, dirty 작업 트리, behind, diverged, 누락된 필수 도구, GitHub 인증 실패와
  fetch 실패는 로컬 버전 변경 전에 실패해야 한다.
- 잘못된 SemVer, prerelease, build metadata, 현재 이하 버전, 기존 로컬 태그, 기존 원격 태그와
  태그만 있고 Release가 없는 버전은 중복 생성이나 원격 변경 없이 실패해야 한다.
- 사용자 최종 확인 거절과 비대화형 표준 입력은 `main`이나 태그 push를 호출하지 않아야 한다.
- `main` push 실패와 pre-push 실패는 태그를 만들지 않아야 한다. 이미 생성한 로컬 버전 커밋은
  보존되고 출력에서 이를 알려야 한다.
- CI 검색은 정확한 SHA와 push 이벤트만 선택해야 한다. 실행 검색 지연 뒤 성공하는 경우,
  실패·취소되는 경우와 제한 안에 실행을 찾지 못하는 경우를 각각 검증하며 성공하지 않은 모든
  경우에 태그가 없어야 한다.
- 태그 push 실패는 로컬 주석 태그를 보존하고 원격 태그가 없음을 알려야 한다. 스크립트가 태그
  삭제나 훅 우회 인자를 호출하지 않았는지도 명령 로그로 검증한다.
- Release 워크플로 실패, 잘못된 대상 SHA, draft 또는 prerelease, 예상 DMG 누락은 명령 전체를
  실패시켜야 하며 이미 push된 원격 태그를 삭제하지 않아야 한다.
- 기존 pre-push 테스트는 dirty 상태, HEAD 일치, 기본 검증과 전면 제품 흐름 순서 및 훅 우회 금지
  계약을 계속 담당한다. 새 게시 테스트가 훅 내부 동작을 복제하지 않는다.
- 기존 워크플로 정적 검사는 CI와 Release가 macOS에서 전체 제품 검증을 수행하고 단일 게시 잡을
  유지하는지 계속 담당한다. 게시 스크립트 테스트의 가짜 GitHub 성공은 실제 워크플로 실행
  증거가 아니다.
- 구현 완료 전 마지막 변경 이후 새 블랙박스 테스트, 기존 훅 테스트, 워크플로 정적 검사,
  `pnpm verify`를 실행한다. push를 동반하는 실제 end-to-end 수용은 사용자의 별도 명시적 릴리스
  실행에서만 수행한다.

## Out of Scope

- GitHub Release를 `release/<version>` 브랜치로 생성하거나 릴리스 브랜치 전략을 도입하는 일
- Git 태그를 없애거나 현재의 `v*` Release 워크플로 트리거를 변경하는 일
- 확인을 생략하는 `--yes`, 자동화 전용 비대화형 모드 또는 예약 릴리스 기능
- prerelease, release candidate, build metadata 또는 여러 안정 채널 지원
- changelog 작성, 실행 중 릴리스 노트 입력 또는 커밋에서 릴리스 본문 자동 생성
- 원격 태그 삭제, 태그 이동, 강제 push, 자동 rollback 또는 실패한 커밋의 자동 revert
- `--no-verify`, `HUSKY=0` 또는 다른 방식으로 pre-push 훅을 우회하는 일
- 태그 push의 두 번째 pre-push 검증을 생략하거나 최적화하는 일
- CI나 Release 워크플로의 제품 검증, 패키징 또는 단일 게시 잡 구조 변경
- 코드 서명, 공증, 자동 업데이트, 다중 아키텍처 또는 Windows·Linux 릴리스 지원
- 앱 기능, 연차 발생·배정·초과·잔여·소멸 계산, UI, 저장 형식 또는 사용자 데이터 변경
- 현재 실패 중인 제품 흐름 테스트 자체를 수정하는 일
- 명세 게시와 동시에 스크립트를 구현하거나 실제 커밋, push, 태그 또는 Release를 생성하는 일

## Further Notes

- GitHub Release는 태그에 연결되므로 태그 생성은 사용자에게 노출되는 수동 단계에서는 사라져도
  자동화 내부의 필수 단계로 남는다.
- 현재 권위 있는 릴리스 절차는 manifest 버전 변경, 제품 검증과 빌드, 버전 커밋과 `main` push,
  동일 버전 태그 push 순서다. 새 명령은 이 순서를 대체하지 않고 안전하게 오케스트레이션한다.
- `main`과 태그를 따로 push하고 각 push에서 pre-push 훅을 실행하며, 원격 CI 성공 뒤에만 태그를
  만든다는 중복 비용은 의도적으로 수용한 안전 결정이다.
- 자동 테스트는 가짜 원격과 명령 로그를 이용하므로 실제 GitHub 권한, 네트워크, macOS 패키징,
  Release 공개 또는 DMG 다운로드를 증명하지 않는다. 최초 실제 사용 결과를 별도의 운영 증거로
  기록해야 한다.
- 명세 작성 시점의 최신 `main` CI는 제품 흐름 테스트 두 건이 실패한 상태다. 이 명세 구현과
  별개로 해당 실패가 해결되고 정확한 릴리스 커밋의 CI가 성공하기 전에는 태그가 생성되어서는
  안 된다.
