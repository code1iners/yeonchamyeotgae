# 데스크톱 테스트 실행선 분리

Status: ready-for-agent

> **제품 흐름 지원 범위 (2026-09-05):** [ADR-0003](../../docs/adr/0003-macos-only-desktop-build.md)과
> [ADR-0004](../../docs/adr/0004-windows-release-resumption.md)에 따라 실제 제품 흐름·OS 수용
> 검증 대상은 macOS다. 릴리스는 Windows x64 패키지를 별도 Windows 러너에서 만들지만,
> Windows 기본 검증 결과를 실제 Windows 트레이·포커스 수용 증거로 사용하지 않는다.

연차몇개의 자동 검증을 무창 기본 검증, 비활성 Electron 제품 흐름, 전면 Electron 제품
흐름으로 분리한다. 로컬 개발과 에이전트 작업은 사용자의 다른 앱을 방해하지 않고 반복할 수
있어야 하며, CI·릴리스와 push 직전에는 각 목적에 맞는 전체 검증을 수행해야 한다.

## Problem Statement

사용자는 에이전트가 일반 테스트를 실행할 때마다 실제 Electron 팝오버가 나타나고 포커스를
가져가 다른 작업 흐름이 끊기는 문제를 겪는다. 현재 데스크톱 패키지의 기본 Vitest 실행은
단위 테스트뿐 아니라 실제 Electron 앱을 실행하는 제품 흐름까지 자동 수집한다. 따라서
`pnpm test`와 `pnpm verify`처럼 자주 실행하는 기본 명령도 네이티브 창을 반복해서 연다.

제품 흐름 자체를 없애거나 창을 완전히 숨기면 빌드된 앱의 렌더링, 팝오버 표시·숨김, 저장과
전체 사용자 흐름을 검증하는 기존 회귀 안전망을 잃는다. 반대로 모든 제품 흐름을 전면 실행으로
유지하면 에이전트와 개발자가 안전하게 반복할 기본 검증선이 없다. 빠른 반복, 실제 Electron
회귀 검증, 운영체제 수용 검증이 서로 다른 증거임에도 하나의 실행 방식에 섞여 있는 것이
문제다.

push 직전 검증도 별도 계약이 없다. 사용자는 push를 단위 테스트와 코드 리뷰가 끝난 명시적
경계로 보고 이때는 전면 제품 흐름까지 다시 확인하기를 원한다. 훅이 검사한 작업 트리와 실제
push되는 커밋이 달라지는 것도 막아야 하며, 에이전트가 실패한 훅을 임의로 우회해서는 안 된다.

## Solution

검증을 목적에 따라 세 실행선으로 분리한다.

- 기본 검증은 린트, 타입 검사와 모든 단위 테스트만 실행하며 Electron 프로세스나 창을 만들지
  않는다.
- 비활성 제품 흐름은 빌드된 Electron 앱을 실제로 실행하고 창을 표시하되 포커스를 요청하지
  않는다. CI·릴리스와 명시적인 로컬 제품 검증은 이 실행선을 사용한다.
- 전면 제품 흐름은 프로덕션과 같은 표시·포커스 경로를 사용한다. 사용자가 명시적으로 요청한
  경우와 macOS 수용 검증, 그리고 모든 push 직전에만 실행한다.

루트 명령은 각 실행선의 의도를 이름으로 드러낸다. `pnpm verify`는 무창 기본 검증,
`pnpm test:product`는 비활성 제품 흐름, `pnpm test:product:foreground`는 전면 제품 흐름,
`pnpm verify:product`는 기본 검증 뒤 비활성 제품 흐름까지 수행하는 전체 자동 검증이다.

Husky pre-push 훅은 깨끗한 작업 트리에서 기본 검증과 전면 제품 흐름을 순차 실행한다. 훅은
전면 창과 포커스 이동을 미리 알리고, 검증 실패나 실행 환경 문제를 만나면 복구 안내와 함께
push를 차단한다. 원격 CI와 릴리스는 사용자 작업 흐름이 없는 격리 환경에서 비활성 전체
검증을 다시 수행한다.

## User Stories

1. 개발자로서 일반 테스트가 네이티브 창을 열지 않기를 원한다. 그래야 테스트 중에도 다른 앱에서 작업을 계속할 수 있다.
2. 개발자로서 일반 테스트가 현재 앱의 포커스를 빼앗지 않기를 원한다. 그래야 입력 중인 내용이 엉뚱한 창으로 전달되지 않는다.
3. 개발자로서 린트, 타입 검사와 단위 테스트를 하나의 빠른 명령으로 실행하고 싶다. 그래야 작은 변경을 자주 검증할 수 있다.
4. 개발자로서 기본 검증과 Electron 제품 흐름을 명령 이름으로 구분하고 싶다. 그래야 실행 전에 창 동작과 비용을 예측할 수 있다.
5. 개발자로서 실제 Electron 렌더링을 유지한 채 포커스만 빼앗지 않는 제품 흐름을 원한다. 그래야 회귀 안전망과 작업 연속성을 함께 지킬 수 있다.
6. 개발자로서 비활성 제품 흐름에서도 팝오버가 실제로 표시되고 숨겨지는지 확인하고 싶다. 그래야 완전히 숨긴 렌더러 테스트를 제품 검증으로 오해하지 않는다.
7. 개발자로서 비활성 제품 흐름이 최초 표시 후 포커스를 갖지 않음을 자동으로 확인하고 싶다. 그래야 구현 실수로 포커스 탈취가 다시 생기지 않는다.
8. 개발자로서 파일 대화상자 흐름이 끝난 뒤에도 비활성 제품 흐름이 포커스를 요청하지 않기를 원한다. 그래야 긴 제품 흐름 중간에 작업이 방해받지 않는다.
9. 개발자로서 비활성 표시를 지원하지 않는 환경에서 전면 창이 몰래 열리지 않기를 원한다. 그래야 실패가 사용자 방해로 바뀌지 않는다.
10. 개발자로서 비활성 표시 실패가 명확한 테스트 실패로 보고되기를 원한다. 그래야 환경 문제와 제품 회귀를 구분할 수 있다.
11. 에이전트 사용자로서 에이전트가 반복하는 `pnpm verify`가 화면을 건드리지 않기를 원한다. 그래야 에이전트 작업과 내 작업을 동시에 진행할 수 있다.
12. 에이전트 사용자로서 전면 제품 흐름이 실행되기 전에 그 사실을 알고 싶다. 그래야 포커스 이동을 예상할 수 있다.
13. 에이전트 사용자로서 에이전트가 자의적으로 전면 검증을 실행하지 않기를 원한다. 그래야 최종 수용 경계 밖에서는 작업 흐름이 보호된다.
14. 에이전트 사용자로서 에이전트가 훅 실패를 임의로 우회하지 않기를 원한다. 그래야 검증되지 않은 변경이 push되지 않는다.
15. 유지보수자로서 기본 단위 테스트와 제품 흐름의 수집 범위가 겹치지 않기를 원한다. 그래야 같은 제품 흐름이 의도치 않게 여러 번 실행되지 않는다.
16. 유지보수자로서 전체 자동 검증이 싼 검사부터 순서대로 실패하기를 원한다. 그래야 린트나 타입 오류가 있을 때 Electron을 불필요하게 빌드하고 실행하지 않는다.
17. 유지보수자로서 CI가 macOS와 Windows에서 같은 비활성 제품 흐름을 실행하기를 원한다. 그래야 운영체제별 회귀를 커밋 단위로 발견할 수 있다.
18. 릴리스 담당자로서 패키징 전에 기본 검증과 제품 흐름이 모두 통과하기를 원한다. 그래야 검증되지 않은 앱을 배포하지 않는다.
19. 릴리스 담당자로서 CI 통과를 실제 운영체제 포커스·블러·트레이 동작의 증거로 오해하지 않기를 원한다. 그래야 자동 검증과 수용 검증의 경계를 정확히 보고한다.
20. macOS 수용 검증자로서 프로덕션과 같은 전면 표시 경로를 명시적으로 실행하고 싶다. 그래야 실제 메뉴 막대 환경의 동작을 확인할 수 있다.
21. Windows 수용 검증자로서 프로덕션과 같은 전면 표시 경로를 명시적으로 실행하고 싶다. 그래야 실제 시스템 트레이 환경의 동작을 확인할 수 있다.
22. 개발자로서 push 전에 모든 단위 테스트와 전면 Electron 제품 흐름이 다시 통과하기를 원한다. 그래야 로컬에서 발견할 수 있는 회귀를 원격 전송 전에 막을 수 있다.
23. 개발자로서 push 훅이 전면 창을 열기 전에 이를 로그로 알리기를 원한다. 그래야 테스트가 포커스를 가져가는 시점을 예측할 수 있다.
24. 개발자로서 미커밋 수정이나 새 파일이 있으면 push가 차단되기를 원한다. 그래야 훅이 검사한 코드와 실제 push되는 커밋이 달라지지 않는다.
25. 개발자로서 빌드 산출물과 캐시처럼 Git이 무시하는 파일 때문에 push가 막히지 않기를 원한다. 그래야 정상적인 검증 부산물을 손으로 지우지 않아도 된다.
26. 개발자로서 훅이 실패하면 어떤 명령으로 복구할지 알고 싶다. 그래야 Node, pnpm 또는 Husky 설치 문제를 해결할 수 있다.
27. 개발자로서 저장소를 새로 설치하면 훅이 함께 준비되기를 원한다. 그래야 사람마다 수동으로 Git 훅을 복사하지 않는다.
28. 유지보수자로서 로컬 훅을 우회하더라도 원격 CI가 전체 자동 검증을 다시 수행하기를 원한다. 그래야 클라이언트 훅만을 신뢰하지 않는다.
29. 유지보수자로서 Linux에서 지원되지 않는 비활성 표시 동작을 성공으로 가장하지 않기를 원한다. 그래야 지원하지 않는 플랫폼의 결과를 macOS·Windows 증거와 섞지 않는다.
30. 문서 독자로서 테스트 실행 정책의 권위 문서가 하나이기를 원한다. 그래야 UI 스펙과 개발 안내 사이의 중복 계약이 서로 어긋나지 않는다.

## Implementation Decisions

- 테스트 실행 정책의 권위 문서는 이 스펙이다. 기존 기능 스펙과 개발·릴리스 안내는 실행
  정책을 중복하지 않고 이 문서를 참조한다.
- `pnpm verify`는 린트, 타입 검사와 모든 단위 테스트를 실행한다. 데스크톱 단위 테스트의
  수집 범위는 소스 아래의 테스트로 한정하고 Electron 제품 흐름을 포함하지 않는다.
- `pnpm test:product`는 데스크톱 앱을 먼저 빌드한 뒤 전체 Electron 제품 흐름을 비활성
  모드로 실행한다.
- `pnpm test:product:foreground`는 같은 빌드와 같은 제품 흐름을 전면 모드로 실행한다.
  시나리오를 복제하거나 별도의 축소 테스트 묶음을 만들지 않는다.
- `pnpm verify:product`는 `pnpm verify`가 성공한 뒤 `pnpm test:product`를 순차 실행한다.
  빠른 검사와 제품 흐름을 병렬화하지 않는다.
- 비활성 모드는 제품의 일반 실행 경로를 바꾸지 않는 테스트 전용 입력으로 전달한다. 이
  모드에서는 팝오버 표시가 `showInactive()`를 사용하고, 대화상자 종료를 포함한 모든 제품
  경로의 네이티브 `focus()` 요청을 억제한다.
- 비활성 모드가 요청됐는데 지원되는 표시·포커스 계약을 만들 수 없으면 실패한다. 전면 표시,
  화면 밖 이동 또는 완전히 숨긴 창으로 자동 폴백하지 않는다.
- 일반 실행과 전면 제품 흐름은 기존 `show()`와 `focus()` 동작을 보존한다. 제품의 트레이,
  팝오버, 데이터와 사용자 상호작용 계약은 변경하지 않는다.
- 전면 제품 흐름은 사용자의 명시적 요청, macOS 수용 검증, 또는 사용자가 명시적으로
  시작한 push의 pre-push 훅에서만 실행한다. 에이전트는 이 조건 밖에서 자율적으로 실행하지
  않는다.
- CI와 릴리스의 macOS 잡은 `pnpm verify:product`를 실행한다. 기존 후속 빌드와
  패키징 단계의 역할은 유지한다.
- Husky를 개발 의존성으로 추가하고 패키지 설치의 `prepare` 단계에서 저장소 훅을 준비한다.
  훅은 macOS와 Windows에서 동작하는 POSIX 호환 명령만 사용한다.
- pre-push 훅은 검증 전에 Git이 무시하지 않는 수정 파일과 새 파일이 없는지 확인한다. 하나라도
  있으면 테스트를 실행하지 않고 정리·커밋 방법을 안내한 뒤 push를 차단한다. Git이 무시하는
  의존성, 빌드 산출물과 캐시는 허용한다.
- 깨끗한 작업 트리에서는 pre-push가 전면 창과 포커스 이동을 예고하고 `pnpm verify`를 먼저
  실행한다. 성공한 경우에만 `pnpm test:product:foreground`를 실행한다.
- 훅이 Node 또는 pnpm을 찾지 못하거나 Husky가 준비되지 않았거나 검증이 실패하면 push를
  차단하고 `pnpm install`, `pnpm run prepare`, Husky 초기화 파일과 Node/PATH 확인 방법을
  안내한다.
- Git의 `--no-verify`와 Husky의 `HUSKY=0` 기능 자체는 제거하지 않는다. 다만 에이전트는
  사용자의 별도 명시적 지시 없이 이를 사용할 수 없으며, 우회 여부와 관계없이 원격 CI가
  전체 자동 검증을 다시 수행한다.
- 제품 흐름은 기존과 같이 임시 사용자 데이터와 결정론적 시드를 사용하고 성공·실패 모두에서
  Electron 및 보조 프로세스와 임시 데이터를 정리한다.
- 제품 흐름·OS 수용 검증 대상은 macOS다. Windows 패키징은 별도 릴리스 러너에서 수행하며,
  Windows, Linux와 Wayland용 표시·포커스 대체 경로는 만들지 않는다.
- 저장 스키마, 계산 API, 프로세스 간 통신 계약, 화면 문구와 접근성 계약은 변경하지 않는다.

## Testing Decisions

- 테스트 seam은 기존 빌드 Electron Playwright 제품 흐름 하나를 유지한다. 비활성·전면 모드는
  같은 시나리오와 사용자 관찰값을 사용하며 네이티브 창 표시 정책만 달라진다.
- 테스트는 명령 이름, 프로세스 종료 상태, 실제 BrowserWindow 상태, 사용자에게 보이는 UI와
  격리 저장 결과를 관찰한다. 내부 함수 호출이나 React 상태만을 합격 근거로 삼지 않는다.
- 기본 검증의 수집 목록에는 코어와 데스크톱 단위 테스트만 나타나고 Electron 제품 흐름은
  없어야 한다. `pnpm verify` 동안 Electron 프로세스와 창이 만들어지지 않아야 한다.
- 비활성 제품 흐름은 빌드 앱의 전체 기존 시나리오가 통과하고 팝오버가 실제로 표시·숨김
  상태를 오가는지 확인한다.
- 비활성 제품 흐름은 최초 표시 직후와 네이티브 대화상자 종료 뒤 실제
  `BrowserWindow.isFocused()`가 `false`인지 확인한다.
- 비활성 모드에서 포커스 계약을 만들 수 없게 강제한 회귀 검사는 전면 창을 열지 않고 명확히
  실패해야 한다.
- 전면 제품 흐름은 비활성 흐름과 정확히 같은 전체 시나리오를 프로덕션 표시 경로로 실행한다.
  이 자동 결과만으로 실제 운영체제 포커스·블러·트레이 클릭을 검증했다고 표현하지 않는다.
- pre-push 훅은 수정된 추적 파일, 스테이징된 파일과 무시되지 않은 새 파일 각각에서 검증 전에
  실패해야 한다. 무시된 빌드·캐시 파일만 있을 때는 검증을 계속해야 한다.
- pre-push 훅은 기본 검증 실패 시 전면 제품 흐름을 시작하지 않고, 기본 검증 통과 후 전면
  제품 흐름 실패 시 push를 차단해야 한다.
- Node 또는 pnpm을 찾지 못하는 훅 테스트는 비검증 성공으로 폴백하지 않고 실행 가능한 복구
  안내와 함께 실패해야 한다.
- CI 정의는 macOS에서 `verify:product`를 호출하고, 릴리스 정의는 macOS `verify:product`와
  Windows 기본 `verify` 뒤에 각 OS를 패키징하는지 정적으로 확인한다. 실제 잡 결과는 macOS의
  비활성 Electron 회귀 증거로만 기록하고 Windows 결과는 패키징 증거로만 기록한다.
- macOS 실제 포커스, 바깥 클릭 blur, 메뉴 막대 클릭과 팝오버 위치는 기존 수용 티켓의 전면
  검증으로 별도 확인한다.
- 기존 선례는 격리된 사용자 데이터, 결정론적 시드, 두 번째 인스턴스와 주입된 blur를 사용하는
  Electron 제품 흐름이다. 새 테스트 묶음을 만들지 않고 이 seam에 창 포커스 관찰을 추가한다.
- 구현 완료 전 마지막 변경 이후 무창 기본 검증, 비활성 전체 제품 검증, 전면 pre-push 훅의
  성공·실패 경로와 Git diff 검사를 각각 최신 상태로 확인한다.

## Out of Scope

- 연차 발생, 배정, 초과, 잔여, 소멸과 연차 연도 계산 규칙 변경
- 저장 형식, 데이터 파일 위치, 스키마 버전 또는 마이그레이션 변경
- 팝오버의 제품 UI, 정보 위계, 문구, 접근성 또는 사용자 기능 변경
- 실제 운영체제 포커스·블러·트레이 검증을 자동 CI만으로 대체하는 일
- Linux, Wayland, 가상 디스플레이 또는 완전 headless Electron 지원
- 모든 Git 클라이언트에서 Node 버전 관리자를 자동 구성하는 일
- pre-commit 훅, 커밋 메시지 검사, 자동 포맷, lint-staged 또는 코드 리뷰 자동화
- 훅 우회 기능 자체 제거 또는 서버 측 Git 훅 구축
- push, 태그 생성, 배포 또는 릴리스 실행
- 기존 macOS·Windows 수용 티켓의 완료 처리
- 이 스펙 게시와 동시에 구현 티켓을 만들거나 제품 코드를 수정하는 일

## Further Notes

- `showInactive()`는 창을 표시하지만 포커스를 주지 않는다. 비활성 제품 흐름에서도 창 자체는
  화면에 보일 수 있으며, 완전 무창 검증이 필요할 때는 `pnpm verify`를 사용한다.
- 비활성 제품 흐름의 창 상태 검증은 운영체제에서 다른 앱이 계속 포커스를 가졌다는 완전한
  실물 증거가 아니다. 자동 테스트 증거와 macOS 수용 증거를 구분해 보고한다.
- push는 에이전트가 자율적으로 수행하는 동작이 아니다. 사용자의 별도 push 요청이 pre-push
  전면 제품 흐름 실행까지 승인하는 경계다.
- 이 스펙은 승인된 실행 정책을 게시한 것이며 구현 완료를 뜻하지 않는다. 구현 티켓은 사용자가
  별도로 요청할 때 이 스펙에서 분할한다.
